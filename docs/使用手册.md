## 1. 它是什么

一个自托管的「捕捉 → 转写 → 每日成文 → 核验 → 导出」闭环。你随时用手机记下一句话或一段短语音，
服务端负责转写、归类、检索历史素材，在当天有内容时生成一篇随想草稿；**只有你确认之后**它才会把稿件
写成一份 Markdown 文件，交给 Hexo 之类的静态站点生成器。

三件需要你提供的东西：一个 OpenAI 兼容的模型接口（转写 / 生成 / 可选 Embedding）、一个 SMTP 服务器（可选）、
一个导出目录（可选）。都不配置时，实例照常收内容，只是不转写、不生成、不发信、不导出。

> 2026-09-24 起，项目**不再做电脑端客户端**，交付面也**只有 Hexo**（即一份 Markdown 文件）。
> 电脑端实现与 WordPress 发布已从产品中删除；从旧版本升级上来时，启动迁移会删掉 WordPress 目标及其发布记录，
> 详见 [`开发指导.md`](开发指导.md) 附录 A.17 与本文第 8 节。

## 2. 你需要准备什么

| | 要求 |
| --- | --- |
| 服务端 | 一台能跑 Docker 与 Docker Compose 的机器（Linux / NAS / Windows 或 macOS 上的 Docker Desktop 都行；amd64 与 arm64 都有镜像）；磁盘按你的音频量估（一条语音约几十 KB） |
| 网络 | 手机能访问到服务端端口。**推荐 HTTPS 或放在 VPN / 局域网内**，理由见 [§10](#10-数据与隐私) |
| 客户端 | Android 8.0（API 26）及以上，从 [Releases](https://github.com/Nero-UMU/DailyMusings/releases) 下载 APK |
| 导出目录（可选） | 一个挂载给实例的 Markdown 目录（给 Hexo 用），在管理页「发布设置」里指定 |

客户端产物与 SHA-256 见 [`发布校验值.md`](发布校验值.md)：Android 装 APK，首次进入设置页填入服务端地址并配对。
该文档里 1.0.0 的旧校验值是方向调整**之前**的构建，已标注为历史留档；当前源码对应的 APK 已在 2026-09-24 重新构建并记录了新的 SHA-256。

## 3. 部署

### 3.1 一份 compose 文件起服务

最短路径只需要一个文件：把仓库根的 [`compose.yaml`](../compose.yaml) 存成任意目录下的 `docker-compose.yaml`（或者照 [`快速部署.md`](快速部署.md) 里那份精简版抄一份），然后

```bash
docker compose up -d
docker compose logs app | grep -A2 '已创建管理员账号'
```

**什么都不用预先准备**：每个参数都有默认值，状态默认落在与这份 compose 同级的 `./data` 与 `./config` 两个目录里——不需要 `.env`、不需要 Secret 文件、不需要预先建目录、也不需要 `chown`。要看/改哪几个参数（端口、数据目录、配置目录、初始管理员密码、时区）见 [`快速部署.md`](快速部署.md) 的参数表。

最后那条命令打印的是一次性管理员初始密码。**它只在这里出现一次**，不写进日志文件，也再也看不到；
所以请当场记下，或者直接在下一步登录时用掉。（在 compose 里设了 `DM_ADMIN_PASSWORD` 的话它不再回显，就用你自己设的那串。）

健康检查：`curl http://<你的地址>:18321/api/system/health` 返回 `{"healthy":true,...}`。它覆盖四件事：
迁移已应用、数据库可写、媒体目录可写、后台任务执行器活着。外部服务（模型、SMTP）**故意不参与**这个检查，
它们挂了不会让实例显得不健康，而是用管理页的「测试连接」单独看（§9）。

### 3.2 Secrets：两种给法，值都不外流

**2026-09-24 第二轮起，密钥不再是「只能由 Docker Secrets 提供」**：模型密钥与 SMTP 密码都可以直接在
管理页里填（模型管理页 / 通知管理页）。值会**加密存放在配置目录中**（由该目录里的 DataProtection 密钥环保护），
因此仍然满足原来的三条承诺：不进配置表、不进可读导出、不进内容备份；页面也读不回它，
只告诉你「有没有、来源是哪里」。解析顺序是「管理页填的 → Secret 文件 → 环境变量」。

如果你更愿意用文件提供密钥（例如密钥由外部工具注入、不想让它落在配置目录里），把四份纯文本文件放进一个目录、再把这个目录挂到 `/run/secrets`（根 `compose.yaml` 里那行注释就是它；`deploy/secrets.example/` 是示例目录），文件名就是下面这四个固定名字：

| 文件 | 用途 |
| --- | --- |
| `deepseek-api-key` | DeepSeek 文章生成接口的凭据 |
| `openai-api-key` | OpenAI 兼容语音转写接口的凭据 |
| `embedding-api-key` | Embedding 接口的凭据（不用可留空文件） |
| `smtp-password` | SMTP 的密码 |

三个模型的 Base URL 和 API Key 相互独立；使用同一家兼容接口时可以填写相同的 Base URL，但每张模型卡片只会保存和测试自己的 API Key。

这些值不会出现在配置文件、日志、导出包或备份包里（§10.4）。管理页里永远看不到已保存的值，只显示
「有没有、来源是哪里」。模型管理页只填写 API Key，不显示也不要求用户理解内部 Secret 名。

**用 Secret 文件时权限要设对，否则所有模型调用都会失败**：容器不是以你的身份运行的（它跑成 uid 1654 的 `app`），而这个目录是 bind mount，容器读到的就是宿主机上的权限位。文件若是 `600`、属主是你，容器里就读不到——文件明明在、名字也对，可每次调用都报 `transcription.secret_missing` / `embedding.secret_missing`。**目录本身**的属主不用管（容器入口会纠正它，缺失的目录也会自动创建），但文件的权限位它不动，所以要自己设：

```bash
chmod 700 <你的 secrets 目录>        # 目录本身只留给你
chmod 644 <你的 secrets 目录>/*      # 文件必须让容器读得到
```

> 旧版本里的第四份 `wordpress-application-password` 已随 WordPress 一并删除；留着这个文件不会报错，但没有任何东西会读它。

### 3.3 数据放在哪

默认是**与这份 compose 同级的两个目录**：`./data`（SQLite、录音、备份包、可读导出、全部稿件）与 `./config`（`runtime.json`、登录密钥环、管理页保存的凭据）。看得见、好备份，`docker compose down` 不会碰它们。

想放到别处（例如接到 NAS 的共享目录）就设这两个变量：

```dotenv
DM_DATA_DIR=/srv/dailymusings/data
DM_CONFIG_DIR=/srv/dailymusings/config
```

（在这份 compose 同级放一个 `.env` 文件写这两行，或者启动前把它们导出成环境变量；也可以直接改 compose 里的挂载。）不想用宿主机目录、想要具名卷，就把那两行挂载换成 `dm-data:/var/lib/dailymusings` 与 `dm-config:/var/lib/dailymusings-config`，并在文件末尾补上 `volumes:` 与两个卷名。

- **数据目录**：SQLite、录音、备份包、可读导出，以及所有稿件。草稿和已发布稿件分别位于
  `<数据目录>/markdown/<发布设置中的相对目录>`，默认即 `markdown/drafts` 与 `markdown/posts`。
- **配置目录**：`runtime.json`、DataProtection 密钥环和管理页加密保存的凭据。它能签发管理员登录 Cookie，应该单独保护，不要混入普通内容备份。

**目录不需要预先创建、也不需要 chown**：不存在时 Docker 会创建，容器入口脚本在启动的第一瞬间把属主纠正为容器用户 uid 1654（只在属主不对时才递归纠正，所以之后每次启动只是一次检查），随后立即降权——**服务进程本身不是 root**。万一日志里出现「无法纠正 … 的属主」，在宿主机上 `sudo chown -R 1654:1654 <那个目录>` 就行；Docker Desktop（Windows / macOS）上这条提示可以忽略。

### 3.4 端口、反代与 HTTPS

Compose 默认把容器 18321 映射到宿主机 `${DM_PORT:-18321}`，容器内固定是 18321。若要从公网访问，请在前面放一个
终止 TLS 的反向代理（Caddy / Nginx / Traefik 都行），并把端口映射写成 `127.0.0.1:18321:18321` 之类的方式
限制为只监听本机，避免明文端口直接暴露。

**端口只有这一处**：容器部署下管理页的「监听端口」是只读的（部署设了 `DAILYMUSINGS_LOCK_LISTENING_PORT=1`），
因为容器内的端口改了只会让映射指向没人监听的地方。要换端口就改端口映射左边那个数字，再 `docker compose up -d`；
`runtime.json` 里如果还留着早先的端口覆盖，它会被忽略。

如果确实用明文 HTTP 访问：登录页会说明「密码、设备令牌、录音与文章都可能被同一网络中的他人截获」并要求你**主动确认**。
这条提醒只在登录时出现；登录后和手机端不会反复占用页面。**确认不会让连接变安全**，它只是说明风险（§10.3）。

## 4. 第一次登录与设备配对

1. 打开 `http://<地址>:18321/`，用 `admin` + 第 3.1 步打印的初始密码登录。
2. 首次登录**强制同时更换账号名和密码**。
3. 回「状态」页（`/`）的「设备配对」区点「生成配对码」：一次性、十分钟有效。
4. 在客户端「设置」页填入服务端地址、点「测试连接」确认可达，再填配对码点「配对」。

配对后客户端只保存服务端地址与设备令牌；令牌以哈希保存在服务端，「设备」页（`/devices`）列出全部
已配对设备，可逐个轮换或撤销，撤销在下一次请求即生效。

## 5. 配置

管理页有**八个功能区**（2026-09-24 第二轮重做，见 [`开发指导.md`](开发指导.md) 附录 A.18）：

| 分区 | 路由 | 管什么 |
| --- | --- | --- |
| 状态 | `/` | 今日随想数量（录音 / 手写）、稿件与发布计数、设备与队列计数、能力状态、存储占用、基础健康检查 |
| 设备 | `/devices` | 生成配对码；已连接 / 已撤销设备；撤回授权、更换令牌、删除已撤销设备的记录 |
| 数据管理 | `/data` | 从新到旧看每一条随想（[时间，类型，状态，内容]），修订录音转写或手写文字，录音行带播放条；分页；永久删除、重试转写 |
| 模型管理 | `/models` | 转写 / 生成 / Embedding 的接口地址、模型名、超时、维度、启用、API Key 与真实连接测试；测试使用页面当前值和合成的最小输入调用实际模型，没有 Secret 名输入项 |
| 通知管理 | `/notifications` | 邮件通知的全部设置：SMTP、密码、收件地址、三个事件开关、发送测试邮件 |
| 发布设置 | `/publishing` | 立即生成、立即发布；每日生成/发布时间与自动发布；博客生成规范（目标字数、人称、可增删改的行文规范条目）；草稿/正式稿目录；Hexo front matter 模板 |
| 内容管理 | `/content` | 搜索、筛选、查看或删除未发布/已发布稿件；为稿件选择一个或多个主题；添加、查看和删除主题 |
| 系统设置 | `/system` | 监听端口、自动备份、备份与导出/恢复、保留策略（录音与随想内容）、语义索引、日志与调试、通知快捷入口、修改账号与密码 |

按日期看某一天（而不是从新到旧翻）用的是 `/inputs`：它不在菜单里，从数据管理页进得去。

**管理页写下的配置优先于部署配置**：模型、SMTP、通知、实例设置与检索参数的读取顺序都是
「管理页设置 → 环境变量 → 内置默认」，所以同一个实例既可以全部用环境变量配（老实例行为不变），
也可以全部在管理页里配。管理页保存后**下一次调用即生效，不需要重启**。

唯一的例外是**监听端口**：它决定设置接口本身在哪个端口上，所以不可能存在设置表里，只能写进磁盘上的
覆盖文件（默认在容器里的 `/var/lib/dailymusings-config/runtime.json`）。而容器部署里端口映射在启动时就固定了，
所以这一版**让部署独占这个设置**：compose 设了 `DAILYMUSINGS_LOCK_LISTENING_PORT=1`，系统设置页那一节因此是只读的，
改端口只有一处——端口映射左边那个数字，改完 `docker compose up -d`。同时 `runtime.json` 里残留的端口覆盖会被忽略，
不会出现「文件里的旧值与映射对不上」这种状态。
不在容器里跑（或没设这个开关）时，页面仍可保存端口覆盖，规则是保存后要让服务监听同一个端口再重启；
页面会把命令写出来。万一新端口不可用、页面再也打不开，设 `DAILYMUSINGS_IGNORE_RUNTIME_OVERRIDES=1` 或在宿主机删掉那个文件即可恢复。

几处容易踩的点：

- **内容时区**默认 `Asia/Shanghai`。生成时刻（默认 23:00）与导出时刻（默认次日 08:00，执行窗口 120 分钟）
  都是**该时区的墙上时间**，不是 UTC 瞬时。
- **两条保留策略都在系统设置里**：录音默认「草稿确认后保留 30 天」（`-1` = 永久、`0` = 确认后立即删除），
  只删音频文件，转写与输入记录保留；**随想内容**默认 `-1`（永不删除），设成 N 天会清空录音识别文本与手写文本
  （记录本身留下，因为历史文章的来源映射指着它）。
- **数据管理中的手动删除不同于保留策略**：确认删除后会永久移除该随想、录音、主题关联、Embedding 和文章中的对应来源关系；
  已经生成的文章正文不会被自动改写。
- **Embedding 是可选的**。换掉 Embedding 模型（或维度）会让旧索引整体失效：语义检索自动降级为主题标签与全文匹配，
  界面提示「语义检索重建中」，之后重建一次即可恢复。
- **自动发布**默认关闭，在发布设置页勾选即可开关，不需要再输一次密码（管理员身份本身就已经验证过了）。
  它只处理已确认的稿件，在正式稿目录写入 `draft: false`；生成完成时另在草稿目录写入 `draft: true`。
  勾选后记得点「保存发布设置」，开关会随保存一起生效。
- **发布权限**：改输出目录、front matter、自动发布开关或通知收件地址都必须用管理员身份。
- **主题由大模型在写文章时产生**：生成提示词会把现有主题清单交给模型，由它挑选或新建；你只能在内容管理里
  添加、为稿件分配和删除。**被任何稿件使用的主题不允许删除**——先取消这些稿件与主题的关联，再删除主题。

### 5.1 邮箱怎么填

**通知管理**页的「邮件」卡片里只有七项要你填（和 ani-rss 的通知设置一样）：**SMTP 地址、SMTP 端口、
发件人邮箱、密码、SSL、STARTTLS、收件人邮箱**，外加一个「启用」开关。**发件人邮箱同时就是 SMTP 用户名**，
所以没有单独的用户名要填；也**没有任何服务商预设**，主机与端口自己填。

**SSL 与 STARTTLS 是两个勾选框，按你的邮箱服务商告诉你的方式选**：

| 别的软件里写的 | 这里怎么勾 | 端口 | 线上发生什么 |
| --- | --- | --- | --- |
| SSL：是，STARTTLS：否 | **勾 SSL** | 465 | 连上第一件事就是 TLS 握手，问候语在隧道里 |
| SSL：否，STARTTLS：是 | **勾 STARTTLS** | 587 | 先明文打招呼，服务商声明 STARTTLS 后再升级加密 |
| 都不加密 | 两个都不勾 | 25 / 1025 | 只适合本机中继（测试用的收信口） |

- **端口与勾法必须配对**，否则会一直等到超时（或握手失败）；两者都对不上时先怀疑这里。
- **两个都勾会被拒绝保存**：那种组合没有意义，只会在握手阶段以看不懂的方式失败。
- **勾了密码却两个都不勾也会被拒绝**：明文连接不会把密码发出去。
- 「密码」这一栏填的是**邮箱服务商给你的授权码或专用密码**，不是你的邮箱登录密码（QQ/163 这类要在邮箱网页端的
  「POP3/IMAP/SMTP 服务」里生成授权码；Gmail 要开启两步验证后生成应用专用密码）。密码只写不读：**留空表示不改**，
  想换就填新的，想去掉就勾「清除已保存的密码」。
- 密码的存放：值会加密存放在实例根目录**之外**（配置目录下，与 DataProtection 密钥环同处），因此不进配置表、
  不进可读导出、不进备份，页面也读不回它（只告诉你「有没有、来源是哪里」）。解析顺序是
  「页面上填的 → Secret 文件（固定名 `smtp-password`）→ 环境变量」，所以用 Docker Secrets 的部署照旧可用。

填完点「**发送测试邮件**」：它真的发一封信到收件地址，并把失败原因（稳定错误码 + 说明）原样显示出来。
只做问候语探测的「测试连接」证明不了「能发出去」，所以两个按钮都在，但只有前者是结论。

邮件要真的发出去还差三步：勾选「启用」、填**收件人邮箱**、至少打开一个**通知事件**开关——
三者缺一，通知任务会安静地跳过（页面顶部就是这么写的）。

## 6. 日常使用

### 6.1 记录（手机端只有三件事）

手机端有且只有三个页面（2026-09-24 第二轮收窄，见附录 A.18）：

**今日随想**：屏幕中央一个大圆圈，点一下开始录音、再点一下停止。**先把音频落盘（fsync）再显示「已保存到本机」**，
所以断电也不会丢掉刚说的话。圆圈右上角的按钮切换成**手动输入**。圆圈下面是这一条记录的控制区：播放/暂停、
可拖动的进度条与当前/总时长、删除（二次确认），以及识别回来的文字。最下面是**上传按钮**——
**只有点了它才会传给服务器**，没有后台自动上传。上传时服务器会顺手把这段录音送进识别模型，
**识别文本随同一次响应回到手机上**并写进本机记录；万一模型慢或不可用，上传本身仍然成功，
文字会在之后打开日历页时自动补上。

**日历**：一行一条记录（录音与手写同级，都标着时间），从新到旧排。右上角筛选：从新到旧、从旧到新、
今日、昨日、本周、本月。点开一条看完整内容，录音的还能播放。

**设置**：服务器地址、测试连接、配对与解除配对、
本机记录占用与「清空本机记录」、实例上的模型名。

**本机的记录不会在上传成功后消失**：手机是「往期记录」的事实来源，删掉只发生在你明确点击删除的时候
（那时的确认框会写明：只删本机这一份，服务器上的不受影响）。删除「整条随想」在后台的数据管理页做。

### 6.2 回到服务端

服务端在当天有内容时生成文章（默认 23:00，错过的会在之后补跑，窗口 60 天）。生成后会自动写一份
`draft: true` 的 Markdown 到草稿输出目录，并排队执行「无来源陈述检查」；找不到依据的句子会被记录。
发布设置页可以立即提交今天的生成任务，但来源检查由后台任务自动完成。

### 6.3 核验与导出（都在后台管理里）

手机端不再有草稿页；稿件管理与发布都在后台：

- **内容管理**页用「全部 / 未发布 / 已发布」筛选或按标题、摘要、日期搜索稿件；点开可查看全文、选择一个或多个主题，
  或永久删除稿件。删除会清除数据库中的正文、历史版本和发布记录，并阻止调度器再次生成同一天；为避免误删外部改动，
  已输出的 Markdown 文件会保留。
- 同一页的**主题管理**列出每个主题被多少篇稿件、多少条素材使用。用户可以添加或删除主题，大模型只能添加；
  只要仍有稿件使用，删除就会被拒绝。
- **发布设置**页负责立即生成/发布、每日生成/发布时间、自动发布与执行窗口、博客生成规范、草稿/正式稿目录，以及 Hexo front matter 模板。
  草稿目录中的文件为 `draft: true`，正式发布目录中的文件为 `draft: false`。
- **博客生成规范**决定每篇文章怎么写，位置就在 Front matter 模板上方：**目标字数**（默认 300 字，指正文汉字数，不含 Markdown 标记）、
  **人称**（默认第一人称），以及一份**规范条目清单**。清单默认给五条——行文风格、结构与段落、标题、开头与结尾、用词禁区；
  每条都能改写、能删掉，也能自己添加（最多 20 条）。保存后，这些内容会作为「写作规范」**前置**在当天的随想之前发给文章模型，
  所以下一次生成就会按新规范写。把清单全部删掉也是有效的，那时只会告诉模型篇幅和人称；随时可以点「恢复默认清单」找回默认那五条。
- 点击「发布稿件」时，如果来源检查尚未完成，页面会提示等待检查完成。刷新后再发布即可；
  发布动作会确认当前工作版本并接受已记录的无来源陈述，然后把公开发布任务放入队列。同一天后来又生成并发布新稿时，旧发布记录会变为「已取代」，旧正式稿在未被外部修改的前提下删除，因此正式稿目录每天只保留一篇。
- 如果当天已经有正式稿，重新生成的新稿只会显示为未发布，原正式稿不会被删除；即使先确认新稿，自动发布也不会替换旧稿。只有点击「发布稿件」才会执行替换。
- 新稿到了设置的发布时间仍未发布时，开启「新草稿待处理或到发布时间仍未发布时发信」后会收到一封提醒。系统不会反复催促，也不会自动撤下旧稿；若继续不处理，下一次重新生成时界面改为最新稿，上一份未发布替代稿不再保留在可见版本槽。
- 到第二天后，这份替代稿仍保留在内容管理的「未发布」列表中。稿件卡片会出现「继续发布」；点击后再次确认，系统先完成来源确认，再把它作为原日期的正式稿发布，并安全替换该日期原先的正式稿。仍可使用已有的删除稿件功能放弃整篇稿件。

语音模型只填写四项：Base URL、API Key、API 类型和模型名。API 类型必须明确选择：

- `openai_transcription`：文件上传接口 `/audio/transcriptions`。
- `openai_chat_audio`：Chat Completions 音频输入接口 `/chat/completions`；适用于使用单个 `input_audio` Data URL 的接口（如百炼 `qwen3-asr-flash`）。
- `dashscope_async`：异步任务提交与轮询。

系统不会根据 URL、厂商或模型名称自动判断协议，模型名会原样发送。`dashscope_async` 需要公网可访问的音频 URL；
当前手机录音只有服务器内的私有文件，因此选择它时会明确提示缺少公网音频 URL，不会把本地路径提交给服务商。

## 7. 备份与恢复

### 7.1 备份

系统设置页点「立即备份」，或让它每天定时跑（默认 03:30，可用 `Maintenance:BackupEnabled` / `Maintenance:BackupLocalTime` 调整）。
备份包放在实例的 `backups/` 目录里，默认保留最近七份（`Backup:KeepCount`）。

包内含：SQLite 数据库快照、媒体（音频）、Markdown 输出、可读数据文件与一份清单。
**不含**：设备令牌及其派生的会话状态（恢复后所有设备都要重新配对）、DataProtection 密钥环、任何 Secret。

恢复前请先把旧实例的整个数据目录复制一份到别处——那是最后一道保险。

### 7.2 恢复（八步）

恢复是**暂存 + 重启生效**，不会当场替换正在运行的数据库：

1. 在系统设置页的「备份与导出」区选择备份包并点「校验并暂存」。服务端会先校验（是不是本产品的备份、schema 版本、
   是否含设备令牌、路径是否越界），并把包内清单显示出来。
2. 重启实例：`docker compose restart app`（或 `up -d --force-recreate`）。
3. 启动时应用恢复：替换数据库、合并媒体与 Markdown，并把原数据库保留为 `pre-restore-<时间戳>.db`。
4. 重启后确认健康检查全绿，且没有遗留的 `Running` 任务。
5. 抽样看：随想正文能打开、三个版本槽完整、来源映射仍然对得上。
6. 抽样看：语音能播放（如果备份时音频还没被保留策略删掉），原始转写与修订稿都在。
7. 确认导出包与备份包里没有任何 Secret。
8. **所有设备都要重新配对**（备份里没有它们的令牌）——回「状态」页签发新的配对码即可。

这一套流程在阶段五做过一次完整的实机验证（全新空目录 + 新 Secrets + 自带卷，恢复同一份备份）。

### 7.3 可读导出

系统设置页的「立即导出」会生成一个可阅读的包：每篇随想的 Markdown、输入/主题/来源映射的 JSON、以及尚未被
保留策略删除的音频，外加一份说明当前保留策略的清单。导出**不会**顺手删掉旧包——它是你自己的副本。

## 8. 升级

1. **先备份**（系统设置页「立即备份」）。
2. 换成新镜像并重启：

   ```bash
   docker compose pull && docker compose up -d
   ```

   （从源码构建的那条路径是 `docker compose -f compose.yaml -f deploy/compose.yaml up -d --build`。）

3. 数据库迁移在启动时自动执行，向前迁移、不承诺自动降级。出问题时用旧镜像 + 第 7 节的备份恢复，
   旧数据库在 `pre-restore-*.db` 里也有留档。

> **2026-09-29 起 `.env` 的键名收敛了。** 旧写法 `DAILYMUSINGS_CONFIG_DIR` / `DAILYMUSINGS_DATA_DIR` /
> `DAILYMUSINGS_INTERNAL_PORT` 变成 `DM_CONFIG_DIR` / `DM_DATA_DIR` / `DM_PORT`。`tools/deploy/deploy.ps1`
> 仍会读一次旧键并写回新键；手工部署请自己改过来，否则两个目录变量读不到，实例会以空数据落在新的 `./data`
> 与 `./config` 上（旧数据不会丢，见下面那条）。

> **从「命名卷」的旧版本升级上来时，要先搬一次数据，否则实例会是空的。**
>
> 旧版 Compose 用三个命名卷存放状态；这一版默认是 compose 同级的 `./data` 与 `./config` 两个宿主机目录，设了 `DM_DATA_DIR` / `DM_CONFIG_DIR` 就是那两个目录，想继续用卷就改成具名卷挂载（见 §3.3）。**Compose 不会自动搬数据**：
> 不搬的话，新实例会以空库启动并打印一个新的初始管理员密码 —— 而你的数据**并没有丢**，它还在旧卷里。
> 遇到这种情况先停下来照下面搬一遍，**不要**拿备份去覆盖。
>
> 先确认自己属于哪种情况：
>
> ```bash
> docker volume ls | grep dailymusings      # 有输出 = 旧版命名卷，需要搬
> ```
>
> - **用 `tools/deploy/deploy.ps1` 部署的**：不用做任何事。脚本在第一次 bind 部署时会自己把三个卷搬进两个目录，
>   比对文件数确认搬全了才继续，而且**不删除旧卷**。
> - **手工按本节命令升级的**：停掉容器，然后搬这三份 ——
>
>   ```bash
>   # 0) 目标目录必须先存在并属于容器用户（uid 1654）
>   sudo mkdir -p /srv/dailymusings/config/keys /srv/dailymusings/data
>   sudo chown -R 1654:1654 /srv/dailymusings/config /srv/dailymusings/data
>
>   # 1) 状态卷 → 数据目录
>   docker run --rm --user 0 -v dailymusings_dailymusings-state:/source:ro \
>       -v /srv/dailymusings/data:/target alpine sh -c 'cp -a /source/. /target/'
>   # 2) 配置卷 → 配置目录
>   docker run --rm --user 0 -v dailymusings_dailymusings-config:/source:ro \
>       -v /srv/dailymusings/config:/target alpine sh -c 'cp -a /source/. /target/'
>   # 3) 密钥环卷 → 配置目录下的 keys/  （这一条最容易漏）
>   docker run --rm --user 0 -v dailymusings_dailymusings-keys:/source:ro \
>       -v /srv/dailymusings/config/keys:/target alpine sh -c 'cp -a /source/. /target/'
>   ```
>
>   **第 3 条别漏**：DataProtection 密钥环（`key-*.xml`）与你在后台填的凭据（`ui-secrets/`，例如 SMTP 密码、
>   模型 API Key）都在那个卷里。漏了它，管理员会被登出，模型 Key 与 SMTP 密码会「凭空消失」——其实只是没搬过来。
>
>   搬完检查一眼再启动：`ls /srv/dailymusings/data` 应看到 `data/ media/ backups/ exports/ markdown/`；
>   `ls /srv/dailymusings/config/keys` 应看到 `key-*.xml` 与 `ui-secrets/`。
> - **全新机器**：什么都不用做，Compose 直接用两个空目录起步（管理员初始密码照第 3 章取）。
>
> 旧卷不会自动删除。确认新实例一切正常（随想与稿件的条数对得上、能登录、模型与 SMTP 可用）之后，
> 再由你自己 `docker volume rm` 掉它们。

> **从带 WordPress 的旧版本升级上来时请注意**：启动迁移 `0006_markdown_only` 会**删除所有 WordPress 目标及其发布记录**
> （这是不可逆的），把存活的 Markdown 目标重新编号，并清掉 `publish.wordpress.*` 设置。
> 你的稿件、版本、来源映射、输入与音频**不受影响**。如果那些发布记录对你有意义，请先备份，
> 或先在旧版本里导出可读包留档。另外旧版的 `deploy/secrets/wordpress-application-password` 不再被读取，
> 可以留着也可以删掉。

### 8.1 明确重置成全新实例

只有在确认**配置、管理员登录状态、模型/SMTP 凭据、数据库、录音、备份与全部稿件都可以永久丢弃**时，才运行：

```powershell
pwsh tools/deploy/reset-instance.ps1
```

脚本会停止 Compose，清空 `deploy/.env` 指定的配置目录和数据目录，并删除旧版遗留的命名卷；代码与 Docker Secret 文件不会被改动。
随后重新运行 `tools/deploy/deploy.ps1`（或 Compose 的 `up -d --build`），系统会创建空数据库并输出新的初始管理员密码。

## 9. 出问题先看哪里

| 现象 | 先看 |
| --- | --- |
| 实例整体不健康 | `/api/system/health` 的四个探针：迁移、数据库可写、媒体可写、任务执行器 |
| 模型/SMTP 不通 | 模型管理页或通知管理页的**测试连接**：模型测试只发送合成的最小输入，不会发送你的稿件或录音；SMTP 测试会真发一封测试邮件 |
| 客户端连不上 | 客户端设置页点「测试连接」，再确认地址、网络与端口 |
| 客户端说令牌失效 | 设备被撤销或轮换过 → 重新配对 |
| 日志里出现「无法纠正 … 的属主」 | 绑定挂载的宿主目录属主不对：在那台机器上 `sudo chown -R 1654:1654 <那个目录>` 再重启容器；Docker Desktop（Windows / macOS）上这条提示可以忽略 |
| 管理页的「监听端口」改不了 | 有意为之：容器部署由部署文件独占端口（`DAILYMUSINGS_LOCK_LISTENING_PORT=1`）。改端口在 compose 的端口映射里，改完 `docker compose up -d` |
| 忘记管理员密码 | 初始密码只打印一次、也不会回显，找不回来。有备份就恢复；没有只能重置实例（配置与数据都会清空，见 §8.1） |
| 录音上传了但没转写 | 今日页会显示转写状态与失败原因；「重试转写」可手动再来一次；转写失败不会丢输入 |
| 草稿没有生成 | 检查：当天有没有输入、转写是否失败（默认会暂缓生成）、生成接口是否启用、生成时刻是否已到 |
| 邮件没收到 | 通知管理页看收件地址与事件开关（三者缺一就不发）；用「发送测试邮件」真发一封，它会把失败原因说清楚；端口与安全方式不配对也会一直超时，见 §5.1 |
| 自动发布没执行 | 只自动发布已确认稿件；已超过执行窗口（默认 120 分钟）时会标记为「已过期」且不会补做，仍可手动发布 |
| 发布提示「来源检查尚未完成」 | 稍后刷新再发布。若一直不结束，检查生成模型配置和后台任务；超时任务会自动按策略重试 |
| 导出说「文件已被修改」 | 那个 md 被人（或别的程序）改过，服务端拒绝覆盖。要么在客户端把改动拿回来，要么自己处理那份文件后再导出 |
| 导出生成了 `…-2.md` | 目标文件名已被占用，而占用它的不是这个实例写过的文件，所以它让位而不是覆盖。想替换请先确认那份文件确实可以覆盖 |
| 语义检索不可用 | 客户端/管理页会提示「重建中」；系统设置页可手动「重建索引」 |
| 想临时看内容相关的日志 | 系统设置页「日志与调试」可开启**有上限、会自到期**的调试模式；开启前必须确认「可能把私人内容写进日志」。默认日志只有请求/任务 ID、状态、耗时、重试次数与脱敏错误码，**不含转写正文、提示词、模型响应或密钥** |

排查任务队列：管理页暂时只提供「导出/备份/索引/调试」这些入口，任务状态可以通过
`GET /api/jobs?limit=100`（设备令牌或管理员 Cookie）查看，或直接查数据库的 `processing_job` 表。
失败的临时错误最多重试三次（指数退避），达到上限进入最终失败状态并按配置发邮件。

## 10. 数据与隐私

- **存在哪**：数据目录保存数据库、音频、导出、Markdown 和备份；配置目录保存运行配置与密钥环。
- **谁能看到**：单用户实例。管理页与客户端都需要凭据；设备令牌以哈希保存、可单独撤销。
- **模型接口**：只有你配置的接口会收到你的内容（转写在启用后才发送音频、生成才发送素材）；不配置就什么都不发。
  本项目不捆绑任何模型服务，也不做默认遥测。
- **日志**：默认不记录内容，只记录标识、状态、耗时、重试与脱敏错误码；调试模式是手动、限时、且需要确认风险。
- **邮件**：只带元数据（日期、标题、状态），不含草稿正文。
- **导出与备份**：可读导出含 Markdown/JSON/尚未清理的音频；备份含数据库快照、媒体、Markdown 与非秘密配置，
  不含设备令牌、密钥环与任何 Secret。
- **导出的文件是给你自己的**：服务端只写进你挂载的那个目录，不会自己执行 Hexo、Git 或任何外部命令，
  也不会把内容发去任何站点。
- **明文 HTTP 的风险**：密码、设备令牌、录音与文章都可能被同一网络中的他人截获。请优先 HTTPS、
  局域网或 VPN——界面上的风险提示只是提示，不提供任何保护。

## 11. 迁移到另一台机器 / 卸载

- **迁移**：停止旧实例后，把数据与配置搬过去——默认形态下就是 `./data` 与 `./config` 两个目录，直接复制即可；用命名卷时把它们导出成 tar（见 §3.3 那条 `docker run … alpine tar` 的命令）。在新机器上用同样的挂载方式启动 Compose。复制配置内容会把登录密钥一并迁移，现有管理员会话仍可能有效；如果不希望如此，只迁移数据、让它重新初始化配置。
- **卸载**：`docker compose down` 只删除容器和网络，不会删除命名卷，也不会删除宿主机目录。确认备份后，再由你明确执行 `docker compose down -v` 或删除那两个目录。
