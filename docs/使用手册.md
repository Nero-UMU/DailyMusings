## 1. 它是什么

一个自托管的「捕捉 → 转写 → 每日成文 → 核验 → 发布」闭环。你随时用手机或电脑记下一句话或一段短语音，
服务端负责转写、归类、检索历史素材，在当天有内容时生成一篇随想草稿；**只有你确认之后**它才会发布到你自己的
博客（WordPress）或写成 Hexo Markdown。

三件需要你提供的东西：一个 OpenAI 兼容的模型接口（转写 / 生成 / 可选 Embedding）、一个 SMTP 服务器（可选）、
一个发布目标（可选）。都不配置时，实例照常收内容，只是不转写、不生成、不发信、不发布。

## 2. 你需要准备什么

| | 要求 |
| --- | --- |
| 服务端 | 一台能跑 Docker 与 Docker Compose 的 Linux 机器；磁盘按你的音频量估（一条语音约几十 KB） |
| 网络 | 手机/电脑能访问到服务端端口。**推荐 HTTPS 或放在 VPN / 局域网内**，理由见 [§10](#10-数据与隐私) |
| 客户端 | Android 8.0（API 26）及以上；或 Windows 10 1809 及以上（x64，**解压即用，不需要安装**） |
| 发布目标 | WordPress 站点与一枚 Application Password；或一个挂载给实例的 Markdown 目录（给 Hexo 用） |

客户端产物与 SHA-256 见 [`发布校验值.md`](发布校验值.md)：Android 装 APK，Windows 把 zip **解压到任意可写目录**、双击 `DailyMusings.Client.exe`（自带运行时，不需要管理员权限，也不需要单独装 .NET）。

## 3. 部署

### 3.1 从空目录起服务

```bash
git clone <本仓库> dailymusings && cd dailymusings
cp -r deploy/secrets.example deploy/secrets      # 该目录已被 .gitignore
# 往 deploy/secrets/ 里填真实的值（见 3.2）
docker compose -f deploy/compose.yaml up -d --build
docker compose -f deploy/compose.yaml logs app | grep INITIAL-ADMIN-PASSWORD
```

最后一行打印的是一次性管理员初始密码。**它只在这里出现一次**，不写进日志文件，也再也看不到；
所以请当场记下，或者直接在下一步登录时用掉。

健康检查：`curl http://<你的地址>:18321/api/system/health` 返回 `{"healthy":true,...}`。它覆盖四件事：
迁移已应用、数据库可写、媒体目录可写、后台任务执行器活着。外部服务（模型、SMTP、博客）**故意不参与**这个检查，
它们挂了不会让实例显得不健康，而是用管理页的「测试连接」单独看（§9）。

### 3.2 Secrets：只按名字引用

`deploy/secrets/` 里放四份纯文本文件，文件名就是配置里引用的名字：

| 文件 | 用途 |
| --- | --- |
| `openai-api-key` | 转写与生成接口的凭据 |
| `embedding-api-key` | Embedding 接口的凭据（不用可留空文件） |
| `smtp-password` | SMTP 的密码 |
| `wordpress-application-password` | WordPress 的 Application Password |

这些值不会出现在配置文件、日志、导出包或备份包里（§10.4）。管理页只保存**名字**，看不到值。

### 3.3 数据放在哪

两个 Docker 卷：

- `dailymusings-state`：**全部持久数据**——SQLite 数据库、音频、导出包、Markdown 输出、备份包。备份与迁移只需管它。
- `dailymusings-keys`：DataProtection 密钥环。它签发管理员登录 Cookie，属凭据等价物，**刻意放在实例根目录之外、且不进备份**；
  删掉它会让所有管理员被登出。

### 3.4 端口、反代与 HTTPS

Compose 默认把容器 18321 映射到宿主机 `${DAILYMUSINGS_HTTP_PORT:-18321}`。若要从公网访问，请在前面放一个
终止 TLS 的反向代理（Caddy / Nginx / Traefik 都行），并把 `DAILYMUSINGS_HTTP_PORT=127.0.0.1:18321` 之类的方式
限制为只监听本机，避免明文端口直接暴露。

如果确实用明文 HTTP 访问：登录页会说明「密码、设备令牌、录音与文章都可能被同一网络中的他人截获」并要求你**主动确认**；
客户端设置页会持续显示同一条提示。**确认不会让连接变安全**，它只是说明风险（§10.3）。

## 4. 第一次登录与设备配对

1. 打开 `http://<地址>:18321/`，用 `admin` + 第 3.1 步打印的初始密码登录。
2. 首次登录**强制同时更换账号名和密码**。
3. 回「状态」页（`/`）的「设备配对」区点「生成配对码」：一次性、十分钟有效。
4. 在客户端「设置」页填入服务端地址、点「测试连接」确认可达，再填配对码点「配对」。

配对后客户端只保存服务端地址与设备令牌；令牌以哈希保存在服务端，「设备」页（`/devices`）列出全部
已配对设备，可逐个轮换或撤销，撤销在下一次请求即生效。

## 5. 配置

管理页有八个页面：状态、设备、采集、模型与邮件、发布、实例设置、运维、账号。

| 想改什么 | 去哪里 |
| --- | --- |
| **查看**录了什么、转写成了什么、当天草稿长什么样（只读） | 采集页（`/inputs`） |
| 回放某一条录音 | 采集页（`/inputs`）里该行的播放器 |
| 把某天的音频／草稿拷出来 | 采集页（`/inputs`）看内容；整包用运维页的导出（见下） |
| 导出包与备份**下载到本地** | 运维页（`/operations`）列表最右列的「下载」 |
| 内容时区、生成时刻、发布时刻与执行窗口、音频保留天数 | 发布页（`/publishing`）的「内容与时间」 |
| 转写 / 生成 / Embedding 的接口地址、模型名、超时、维度、启用状态 | 模型与邮件页（`/models`） |
| SMTP 服务器、端口、发件人、密码名、超时 | 模型与邮件页（`/models`） |
| WordPress 目标、可见性、自动公开开关 | 发布页（`/publishing`） |
| WordPress 目标的站点地址、用户名、Secret 名、请求超时（按目标覆盖） | 发布页（`/publishing`）的「WordPress 站点设置」，留空即沿用部署配置 |
| Hexo Markdown 目标 | 发布页（`/publishing`），目标类型选 Markdown，填相对目录 |
| 监听端口（重启容器生效） | 实例设置页（`/settings`）的「监听端口」 |
| 调度轮询间隔、补跑窗口、每次生成上限 | 实例设置页（`/settings`）的「调度」 |
| 每晚自动备份开关与时刻、音频清理时刻、备份保留份数 | 实例设置页（`/settings`）的「维护与备份」 |
| 历史检索条数、候选扫描上限、相关性与词面阈值 | 实例设置页（`/settings`）的「历史检索」 |
| 通知收件地址、实例地址与三类事件开关 | 运维页（`/operations`）的「通知设置」 |
| 立即导出 / 立即备份 / 上传恢复包 / 立即清理一次音频 / 重建索引 / 调试模式 | 运维页（`/operations`） |
| 模型、SMTP、博客的连通性自检 | 模型与邮件页或运维页的「测试连接」 |
| 签发配对码 | 状态页（`/`）的「设备配对」 |
| 查看、轮换、撤销已配对设备 | 设备页（`/devices`） |

**管理页写下的配置优先于部署配置**：模型、SMTP、通知、实例设置与检索参数的读取顺序都是
「管理页设置 → 环境变量 → 内置默认」，所以同一个实例既可以全部用环境变量配（老实例行为不变），
也可以全部在管理页里配。管理页保存后**下一次调用即生效，不需要重启**。

唯一的例外是**监听端口**：它决定设置接口本身在哪个端口上，所以不可能存在设置表里，只能写进磁盘上的
覆盖文件（默认在容器里的 `/var/lib/dailymusings-config/runtime.json`）。在实例设置页改完端口后需要两步：
把 `deploy/.env` 里的 `DAILYMUSINGS_INTERNAL_PORT` 改成同一个值，再
`docker compose -f deploy/compose.yaml up -d --force-recreate`。容器的端口映射在启动时就固定了，
所以不重建容器的话，映射会指向一个没人监听的端口。页面会把这两条命令直接写出来。
万一新端口不可用、页面再也打不开，设 `DAILYMUSINGS_IGNORE_RUNTIME_OVERRIDES=1` 或在宿主机删掉那个文件即可恢复。

几处容易踩的点：

- **内容时区**默认 `Asia/Shanghai`。生成时刻（默认 23:00）与发布时间（默认次日 08:00，执行窗口 120 分钟）
  都是**该时区的墙上时间**，不是 UTC 瞬时。
- **音频保留**默认「草稿确认后保留 30 天」（在发布页设置），可设为保留更久、`-1` = 永久、`0` = 确认后立即删除。
  到期只删音频文件，转写与输入记录保留，条目上会显示「没有音频」。运维页只提供「立即清理一次」，策略本身在发布页。
- **Embedding 是可选的**。换掉 Embedding 模型（或维度）会让旧索引整体失效：语义检索自动降级为主题标签与全文匹配，
  客户端会提示「语义检索重建中」，之后重建一次即可恢复。
- **自动公开**默认关闭，开启时要求你重新输入管理员密码（这是一个安全开关，不是一个普通偏好）。
- **发布权限**：设备令牌可以手动发布与导出 Markdown，改发布目标、开自动公开、改通知收件地址都必须用管理员身份。

## 6. 日常使用

### 6.1 记录

客户端「今日」页：按住录音按钮说一句，或直接写一句。**客户端先把内容安全落到本机，然后才显示「已保存」**；
联网后自动上传，断网就排队，队列里能看到失败原因并手动重试。上传用幂等键，重试不会产生重复条目。

每条记录可以：修订转写（原始转写保留）、调整主题（改归属）、重试转写（失败时）、播放录音
（保留期内可回听，用来核对转写是否有误）。

### 6.2 回到服务端

服务端在当天有内容时生成草稿（默认 23:00，错过的会在之后补跑，窗口 60 天）。生成后还有一次
「无来源陈述检查」：找不到依据的句子会标出来并给出原因。

### 6.3 核验与发布

客户端「草稿」页打开某一天：

- 正文可编辑，标题/摘要可改；保存修改不会覆盖你以前的版本，三个版本槽（当前、上一版、初稿）都可以切回。
- 「来源核验」列出每条引用逐字对应的句子，并注明来自今天还是更早；正文改动后对不上的引用会标为「不再精确对应」。
- 有「无法追溯」的句子时，确认前必须显式勾选接受它们——这是刻意设计的停顿。
- 「重新生成」在存在手工修改时会先问你，确认后才会把当前版本移到「上一版」。
- 发布：选目标与可见性（草稿 / 公开）。公开前会再确认一次。发布后可「检查远程」看远端是否与本地一致。

「日历」页按月看哪天有输入、草稿到什么状态，点进去直接打开那天的草稿；「主题」页浏览、重命名、合并主题
（合并后原主题成为墓碑，历史文章的来源映射不变）。

## 7. 备份与恢复

### 7.1 备份

运维页点「立即备份」，或让它每天定时跑（默认 03:30，可用 `Maintenance:BackupEnabled` / `Maintenance:BackupLocalTime` 调整）。
备份包放在实例的 `backups/` 目录里，默认保留最近七份（`Backup:KeepCount`）。

包内含：SQLite 数据库快照、媒体（音频）、Markdown 输出、可读数据文件与一份清单。
**不含**：设备令牌及其派生的会话状态（恢复后所有设备都要重新配对）、DataProtection 密钥环、任何 Secret。

恢复前请先把旧实例整个 `dailymusings-state` 卷复制一份到别处——那是最后一道保险。

### 7.2 恢复（八步）

恢复是**暂存 + 重启生效**，不会当场替换正在运行的数据库：

1. 在运维页「恢复」区选择备份包并点「校验并暂存」。服务端会先校验（是不是本产品的备份、schema 版本、
   是否含设备令牌、路径是否越界），并把包内清单显示出来。
2. 重启实例：`docker compose -f deploy/compose.yaml restart app`（或 `up -d --force-recreate`）。
3. 启动时应用恢复：替换数据库、合并媒体与 Markdown，并把原数据库保留为 `pre-restore-<时间戳>.db`。
4. 重启后确认健康检查全绿，且没有遗留的 `Running` 任务。
5. 抽样看：随想正文能打开、三个版本槽完整、来源映射仍然对得上。
6. 抽样看：语音能播放（如果备份时音频还没被保留策略删掉），原始转写与修订稿都在。
7. 确认导出包与备份包里没有任何 Secret。
8. **所有设备都要重新配对**（备份里没有它们的令牌）——回「状态」页签发新的配对码即可。

这一套流程在阶段五做过一次完整的实机验证（全新空目录 + 新 Secrets + 自带卷，恢复同一份备份）。

### 7.3 可读导出

运维页「立即导出」会生成一个可阅读的包：每篇随想的 Markdown、输入/主题/来源映射的 JSON、以及尚未被
保留策略删除的音频，外加一份说明当前保留策略的清单。导出**不会**顺手删掉旧包——它是你自己的副本。

## 8. 升级

1. **先备份**（运维页「立即备份」）。
2. 取到新代码后重建并重启：

   ```bash
   docker compose -f deploy/compose.yaml up -d --build
   ```

3. 数据库迁移在启动时自动执行，向前迁移、不承诺自动降级。出问题时用旧镜像 + 第 7 节的备份恢复，
   旧数据库在 `pre-restore-*.db` 里也有留档。

## 9. 出问题先看哪里

| 现象 | 先看 |
| --- | --- |
| 实例整体不健康 | `/api/system/health` 的四个探针：迁移、数据库可写、媒体可写、任务执行器 |
| 模型/SMTP/博客不通 | 模型与邮件页或运维页的**测试连接**：它只做最小调用，不会把内容发出去 |
| 客户端连不上 | 客户端设置页「测试连接」；再确认地址、网络与端口；明文 HTTP 会一直有风险横幅 |
| 客户端说令牌失效 | 设备被撤销或轮换过 → 重新配对 |
| 录音上传了但没转写 | 今日页会显示转写状态与失败原因；「重试转写」可手动再来一次；转写失败不会丢输入 |
| 草稿没有生成 | 检查：当天有没有输入、转写是否失败（默认会暂缓生成）、生成接口是否启用、生成时刻是否已到 |
| 邮件没收到 | 运维页看通知收件地址与事件开关；「测试连接」测 SMTP（它只读问候语，不发信） |
| 自动公开没执行 | 已超过执行窗口（默认 120 分钟）时发布会被标记为「已过期」并且不会补跑；手动发布仍然可以 |
| 语义检索不可用 | 客户端/管理页会提示「重建中」；运维页可手动「重建索引」 |
| 想临时看内容相关的日志 | 运维页「日志与调试」可开启**有上限、会自到期**的调试模式；开启前必须确认「可能把私人内容写进日志」。默认日志只有请求/任务 ID、状态、耗时、重试次数与脱敏错误码，**不含转写正文、提示词、模型响应或密钥** |

排查任务队列：管理页暂时只提供「导出/备份/索引/调试」这些入口，任务状态可以通过
`GET /api/jobs?limit=100`（设备令牌或管理员 Cookie）查看，或直接查数据库的 `processing_job` 表。
失败的临时错误最多重试三次（指数退避），达到上限进入最终失败状态并按配置发邮件。

## 10. 数据与隐私

- **存在哪**：一个 `dailymusings-state` 卷里，数据库 + 音频 + 导出 + Markdown + 备份；密钥环另卷。
- **谁能看到**：单用户实例。管理页与客户端都需要凭据；设备令牌以哈希保存、可单独撤销。
- **模型接口**：只有你配置的接口会收到你的内容（转写在启用后才发送音频、生成才发送素材）；不配置就什么都不发。
  本项目不捆绑任何模型服务，也不做默认遥测。
- **日志**：默认不记录内容，只记录标识、状态、耗时、重试与脱敏错误码；调试模式是手动、限时、且需要确认风险。
- **邮件**：只带元数据（日期、标题、状态），不含草稿正文。
- **导出与备份**：导出含 Markdown/JSON/尚未清理的音频；备份含数据库快照、媒体、Markdown 与非秘密配置，
  不含设备令牌、密钥环与任何 Secret。
- **明文 HTTP 的风险**：密码、设备令牌、录音与文章都可能被同一网络中的他人截获。请优先 HTTPS、
  局域网或 VPN——界面上的风险提示只是提示，不提供任何保护。

## 11. 迁移到另一台机器 / 卸载

- **迁移**：在新机器上按第 3 节部署一个空实例 → 把旧机器的备份包拷过去 → 按第 7.2 节恢复 → 重新配对设备。
  也可以直接复制两个卷（`dailymusings-state` 与 `dailymusings-keys`），但那样密钥环一并搬走，
  管理员登录会话在新机器上仍然有效——请自行判断是否符合你的预期。
- **卸载**：`docker compose -f deploy/compose.yaml down -v` 会连数据卷一起删除。
  **先导出并确认备份包已经拷到别处**，再执行。
