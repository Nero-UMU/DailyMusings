## 2. 产品目标

“每日随想”面向会在日常生活中随时记录见闻、想法和思考的个人创作者。

用户通过 Android 客户端输入短语音或文字。服务端负责转写、主题识别、历史检索、每日随想生成、通知，并最终把成稿写成一份 Markdown 文件。当天只要存在至少一条有效输入，就生成一篇随想；没有输入则不执行生成任务。

核心原则：

- 捕捉瞬间想法，而非会议录音或备忘录管理。
- 默认生成私人草稿，由用户核验后才输出。
- 用户自行提供模型服务，项目不捆绑任何模型。
- 数据由用户自托管并可完整导出。
- AI 只能整理、重构和润色来源内容，不得故意补充不存在的事实。
- 模型无法提供绝对真实性保证，因此必须提供来源追溯和风险提示。
- 交付面尽量窄：当前只承诺产出一份 Markdown 文件，不做站点对接。

## 3. MVP 范围

### 3.1 必须包含

- 单用户 ASP.NET Core 服务端。
- Blazor 服务端管理页面。
- Android .NET MAUI 客户端。
- Linux Docker Compose 部署。
- 文字输入、短语音录制、离线队列和即时转写。
- **手机端只做三件事**（2026-09-24 第二轮定案，附录 A.18）：录制随想、看这段录音识别回来的文字、翻看本机留存的往期记录（录音 + 识别/手写文字）；外加设置页的连接与配对。草稿、主题、来源核验、版本切换、发布**都不在手机上**。
- **后台管理分八个分区**（同附录 A.18）：状态、设备、数据管理、模型管理、通知管理、发布设置、内容管理（含主题管理）、系统设置。
- 标签检索及可选的 Embedding 语义检索。
- 每日随想生成、历史主题引用、来源核验和三版本草稿。
- **主题由生成模型在写文章时选出或新建**；用户也可添加主题，但只有用户能删除。后台可查看与管理，手机端不展示。
- SMTP 邮件提醒。
- **产出 Markdown 文件**：把确认过的稿件写成一份 `.md`，落在用户指定的挂载目录里（附录 A.17）。
- 设备配对、数据导出、备份恢复、日志和失败重试。

### 3.2 明确不包含

- 多用户、团队或公开注册。
- **电脑端（Windows 桌面）客户端**（附录 A.17；`DailyMusings.Client` 只保留 Android 目标）。
- **WordPress 或任何博客站点的 API 对接**（附录 A.17）。
- **执行 `hexo generate`、`hexo deploy`、Git 提交或推送，或用户自定义命令**。
- **替用户修改 Hexo 站点结构或自动部署站点**：本项目只允许配置 front matter 模板和**数据目录**下的草稿/正式稿相对目录（附录 A.19、A.31）。
- 图片输入和已有音频导入。
- 会议录音和长音频工作流。
- 任意历史日期重新生成。
- Microsoft Store 或 Google Play 发布。
- 默认遥测。

## 4. 总体架构

```text
Android MAUI ──── HTTP/HTTPS API ── ASP.NET Core 服务端
                                        │
Blazor 管理页 ──────────────────────────┤
                                        ├── SQLite
                                        ├── 音频与导出文件目录
                                        ├── OpenAI 兼容模型接口
                                        ├── SMTP
                                        └── Markdown 输出目录（Hexo 读取）
```

### 4.1 职责划分

客户端负责：

- 录音、文字输入和本地离线队列。
- 时间线、日历、主题、草稿及任务状态展示。
- 修订转写、调整主题、编辑和重新生成允许处理的草稿。
- 触发 Markdown 导出及来源核验。
- 保存服务器引用和设备令牌，不保存模型或任何发布密钥。

服务端负责：

- 身份验证、设备配对和设备撤销。
- 音频接收、持久化、转写和重试。
- 主题识别、标签搜索、向量索引和历史检索。
- 每日调度、补跑、文章生成及事实来源检查。
- 草稿版本管理，以及把稿件写成 Markdown 文件。
- SMTP 通知、备份、恢复、数据导出和诊断日志。

管理网页负责：

- 管理员账号和密码。
- 模型、Embedding、SMTP、Markdown 输出目录及内容时区配置。
- 设备配对、设备撤销和系统状态查看。
- 任务失败处理、索引重建、备份恢复及日志查看。
- 不承担主要的日常创作体验。

  DailyMusings.Server/             # ASP.NET Core API、后台任务、宿主
  DailyMusings.Admin/              # Blazor 管理页面
  DailyMusings.Client/             # MAUI Android
  DailyMusings.Client.Core/        # 客户端状态、同步、离线队列

  DailyMusings.Domain.Tests/
  DailyMusings.Application.Tests/
  DailyMusings.Infrastructure.Tests/
  DailyMusings.Api.IntegrationTests/
  DailyMusings.Client.Tests/

依赖方向必须保持：Domain 不依赖其他项目；Application 只依赖 Domain；Infrastructure 实现 Application 定义的端口；宿主和 UI 负责组合依赖。

目标框架（2026-09-16 定案，2026-09-24 按附录 A.17 收窄）：服务端、Admin 及 Domain/Application/Infrastructure/Contracts 均为 `net10.0`；客户端**只有一个目标** `net10.0-android`，最低支持 Android 8.0（API 26，`SupportedOSPlatformVersion = 26`）。Windows 目标已随电脑端实现一并移除。Docker 基础镜像使用与所选 SDK 匹配的 ASP.NET Core 运行时镜像，并在 `deploy/` 中固定具体 tag，不使用 `latest`。

Compose 部署只有一份服务定义（仓库根的 `compose.yaml`），两种用法：

- **默认（使用者）**：用已发布的镜像（`ghcr.io/nero-umu/dailymusings`），只映射配置目录与数据目录两个持久目录，默认是这份 compose 同级的 `./data` 与 `./config`（都可用 `DM_DATA_DIR` / `DM_CONFIG_DIR` 指到别处）。这两个目录不需要预先创建、也不需要 chown：容器入口脚本在启动的第一瞬间把它们建好、把属主纠正到容器用户 uid 1654 并打印一行说明，随后立即 `setpriv` 降权；**服务进程本身不以 root 运行**，root 只存在于入口脚本改变属主的那几毫秒。默认端口是宿主机 `${DM_PORT:-18321}` 映射到容器内固定的 18321。健康检查写在镜像的 `HEALTHCHECK` 里而不是 compose 里——这样 `docker run` 的人也有它，而 compose 文件少一段。
- **从源码构建（维护者）**：`deploy/compose.yaml` 只是叠在它上面的覆盖文件（加 `build:` 与服务定义零重复），用 `docker compose -f compose.yaml -f deploy/compose.yaml up -d --build`。

**两个持久目录按「内容 / 状态」切分**（2026-09-29 定案，见附录 A.31），而不是按子目录名：

- **数据目录**（`DM_DATA_DIR`，容器内 `/var/lib/dailymusings`）**只放 Markdown**。后台「发布设置」里的那两个目录都以它为根：映射了 `/srv/dailymusings/data:/var/lib/dailymusings`、页面里填 `aaa/bbb/posts`，稿件就落在宿主上的 `/srv/dailymusings/data/aaa/bbb/posts`——填的就是宿主上看到的那条相对路径，中间不再有别的层级。因为它只装稿件，可以整份交给 Hexo，也可以整份同步走。
- **配置目录**（`DM_CONFIG_DIR`，容器内 `/var/lib/dailymusings-config`）放**其余全部状态**：SQLite（连同 `-wal` / `-shm`）、录音、可读导出、备份包、DataProtection 密钥环与管理页凭据、运行时覆盖文件。
- **两个目录必须分开，且都不允许落到匿名卷**：默认是两份有名字的宿主机目录（备份时看得见、`docker compose down` 不会碰它们），换成具名卷也必须是有名字的卷。配置目录装着能签发登录 Cookie 的密钥环（A.14），数据目录装的是要给人看、要同步走的东西——混在一起就等于把凭据一起送出去。
- **后台填的目录只有一个基准：数据目录。** 不允许绝对路径、不允许 `..`（`publish.markdown.path_not_relative` / `publish.markdown.path_escapes_root`），基准之外没有隐藏层级。

**APK 必须用一把固定的发布签名密钥**（2026-09-29 定案，见附录 A.30）。Android 规定「覆盖安装必须与已安装版本同一签名」，而 CI 的 runner 每次都是全新的：不显式给密钥时，.NET Android 会在 runner 上自动生成一把**调试**密钥（证书主题 `CN=Android Debug`），于是每次发布的签名都不一样，手机上永远装不上新版本——v1.0.3 / 1.0.4 / 1.0.5 就是这样，三份产物的证书指纹互不相同。规则：

- 密钥由维护者在本机生成一次（`tools/release/new-signing-key.ps1`），私钥只存在两处：本机备份与仓库的 **4 条 Secret**（`ANDROID_SIGNING_KEYSTORE_BASE64` / `ANDROID_SIGNING_STORE_PASSWORD` / `ANDROID_SIGNING_KEY_ALIAS` / `ANDROID_SIGNING_KEY_PASSWORD`）。**绝不提交进版本库**：仓库是公开的，泄露密钥等于任何人都能签出被手机接受的假更新。PKCS12 只有一个口令，所以 store 与 key 两条口令同值（脚本已处理）。
- 证书指纹写进仓库 **Variable** `ANDROID_SIGNING_CERT_SHA256`（小写、不含冒号）。`release.yml` 的 `apk` 作业**缺密钥就失败**，并且在打包后读回证书指纹与它比对——签名「没报错」不等于用的是那把密钥：构建找不到密钥时会静默退回调试密钥，而那正是这一版要杜绝的事。
- 换密钥等于换应用身份：所有已安装的手机只能卸载重装。因此这把密钥必须备份；丢了它，唯一的出路就是让每台手机卸载一次。
- 这一版之前装过旧版（调试签名或别的调试密钥）的手机，**需要卸载一次**再装新版本；此后每一版都能直接覆盖安装。

## 6. 核心领域模型

### 6.1 InputEntry

代表一条语音或文字输入。

关键字段：

- `Id`
- `SourceType`: `Voice` 或 `Text`
- `CreatedAtUtc`
- `CreatedOffsetMinutes`
- `ContentDate`: 按内容时区计算的自然日
- `AudioPath`、`AudioDuration`、`AudioDeletedAtUtc`
- `OriginalTranscript`
- `RevisedTranscript`
- `TranscriptionStatus`
- `AllowFutureRecall`
- `PrimaryTopicId`
- `SecondaryTopicIds`
- `DeletedAtUtc`

原始转写和用户修订稿必须分开保存。生成时优先使用修订稿，没有修订稿时使用原始转写。

音频保留策略见 §15.1；音频被清理后 `AudioPath` 置空，转写文本仍保留，输入记录本身不受影响。

用户在数据管理页手动删除一条输入时，该行连同它的来源关系被物理移除（§15.1、A.23）。`DeletedAtUtc` 只由保留策略写入，代表「内容已到期，但行必须留下」。因此「行还在」不等于「内容还在」，判断一条输入是否已退役要看 `DeletedAtUtc`，不要看它是否还能被查出来。

### 6.2 Topic

- 支持重命名、合并和调整输入归属。
- 一条输入最多有一个主要主题，可有多个次要主题。
- MVP 不要求自动拆分主题。
- 删除主题不得删除原始输入。
- `Topic.Id` 稳定且不可变，重命名只改展示名、不改 ID。
- 合并只改归属，不删除被合并主题行：保留为 tombstone 并记录 `MergedIntoId`、`MergedAtUtc`。
- `SourceReference` 指向输入而非主题，因此主题的合并、重命名与删除都不得改变历史文章的来源映射。

**2026-09-24 第二轮补充（附录 A.18）——主题由模型产生、由用户治理：**

- 主题**不再要求用户显式创建**。每日生成时，提示词把实例现有的主题清单交给模型，由模型**从中挑选 1–3 个**（原样回抄写法）；清单里确实没有合适的，模型才提出新主题，服务端按名称幂等落库并标记 `Origin = Model`。
- 主题因此挂在**文章（稿件版本）**上：一个版本可以有多个主题，其中第一个是主主题。输入上的主题归属（`InputEntry.PrimaryTopicId`）保留，它仍是检索退化的信号，但不再是主题这个词的主要含义。
- **用户与模型都可以创建主题，但只有用户可以删除主题**。删除只发生在后台，且**被文章当前使用的主题不允许删除**——用户必须先在内容管理里取消这些稿件与主题的关联。
- 隐藏判定的口径：守卫只看**被 `Reflection` 当前的 `WorkingVersionId` / `ConfirmedVersionId` 指向的版本**。被淘汰的历史版本不算「当前稿件在用」；删除一个主题会同时清掉历史版本上的主题标签行，但**正文与来源映射一概不动**。
- 手机端不展示、不管理主题。

### 6.3 Reflection

代表某一自然日的每日随想。

关键字段：

- `Id`
- `ContentDate`
- `Status`
- `GenerationReason`
- `LastStaleReason`（原 `IsStaleBecauseOfLateInput`，2026-09-16 定案降级为审计字段，不再作为状态依据）
- `InitialVersionId`
- `PreviousVersionId`
- `WorkingVersionId`
- `ConfirmedVersionId`
- `CreatedAtUtc`、`UpdatedAtUtc`

状态定义（2026-09-16 定案）：

```text
PendingInputs → Ready → Generating → ReviewRequired → Confirmed
                         │                 │
                         └── Failed       └── StaleByLateInput

Status ∈ { PendingInputs, Ready, Generating, ReviewRequired, Confirmed, Failed, StaleByLateInput }
```

`Failed` 指生成二阶段重试耗尽的**稿件态**，与 `ProcessingJob` 的任务态失败严格区分。`StaleByLateInput` 指当日已生成后又收到当日输入、等待补生成。唯一允许离开 `Confirmed` 的迁移是 `Confirmed → StaleByLateInput`。状态分组一律由服务端计算，客户端只负责展示。

### 6.4 ReflectionVersion

保存标题、摘要、正文、标签、分类建议、写作设置、模型信息、提示词版本和来源映射。

版本规则：

- 最初版本永久保留。
- 重新生成前，当前编辑版本通常转为上一版本；若它是对既有已确认稿的未发布替代稿，下一次重新生成会让这份已放弃的替代稿退出可见版本槽，上一位置继续保留已确认稿。
- 新结果成为当前编辑版本。
- 不得静默覆盖用户手工编辑。
- 默认只维护“最初、上一、当前”三个版本位置。

### 6.5 SourceReference

把文章段落或句子关联到一个或多个输入记录，字段定义（2026-09-16 定案）：

- `ReflectionVersionId`：文章版本 ID。
- `BlockIndex`：版本正文内的段落序号，0 起。
- `CharStart`、`CharEnd`：段内半开字符区间。
- `QuoteHash`：被引用片段规范化后的哈希，用于检测定位漂移。
- `InputId`：输入 ID，可多个。
- `Relevance`、`Reason`：相关度与引用原因。
- `IsHistorical`：是否为历史材料。

来源详情接口或可读导出展示来源时，若 `QuoteHash` 与当前文本不匹配，判为定位漂移：降级为整段提示而非精确高亮，并告知用户该版本已被编辑。当前内容管理主界面不承担逐条来源核验。

来源信息默认仅在应用内展示，不自动写入公开文章。

### 6.6 ProcessingJob

所有转写、索引、生成、检查、通知和发布操作都应建模为可持久化任务，而不是仅存在于进程内存中。

任务类型至少包括：转写、Embedding 索引与重建、生成、无来源陈述检查、通知、发布、备份，以及音频清理（`AudioCleanup`）。

关键字段：

- `JobType`
- `TargetId`
- `Status`
- `AttemptCount`
- `ScheduledAtUtc`
- `StartedAtUtc`
- `CompletedAtUtc`
- `IdempotencyKey`
- `ErrorCode`
- `ErrorSummary`

### 6.7 PublishTarget 与 Publication

发布目标只有一种类型：一个 **Markdown 目录**（相对实例的**数据目录**，A.31）。一个实例允许配置多个命名目标，因此同一篇稿件可以落到不同目录；每个目标独立保存导出状态与它写出的文件名（记录里沿用 `RemoteId` 这个字段名，值就是文件名）。

§11.1 的整条发布生命周期仍然成立，只是它的对象从「远端文章」变成「本地导出」：队列、幂等键、执行窗口、自动发布开关与可见性都保留，可见性对 Markdown 目标而言就是 front matter 里的 `draft` 字段（附录 A.17）。

**front matter 的两个时间（2026-09-30 定案，附录 A.37）**：`date` = 这一版**生成**的时刻，`updated` = 这一版**最后一次改动**的时刻；两者都是稿件自己的时刻，都按**内容时区**（§7）渲染成 `yyyy-MM-dd HH:mm:ss`。它们语义不同（重新生成会同时刷新两者，编辑只动 `updated`），因此是两个来源，不能互相代替。文件名里的日期仍然是**内容日期**——那是「这些材料属于哪一天」，与「这份稿子什么时候写出来的」是两件事。

## 7. 时间与生成规则

- 内容时区在服务端配置，默认 `Asia/Shanghai`。
- 所有时间以 UTC 持久化，并记录输入创建时的时区偏移。
- 自然日按内容时区的 `00:00–23:59` 划分。
- 默认 23:00 生成，时间可配置。
- 当天无输入时不得创建空文章。
- 服务器停机或客户端离线后，按每条输入的实际创建日期逐日补跑。
- 当天存在转写失败项时，默认暂缓生成并通知用户；用户可选择忽略失败项继续。
- 当日生成后又出现当日输入，草稿标记为过期并补生成。
- 不支持选择任意历史日期重新生成。
- **晚到输入的定义（2026-09-16 定案）**：服务端收到该输入的时刻晚于其 `ContentDate` 在内容时区的 `23:59:59`。`ContentDate` 始终由输入自身的 `CreatedAtUtc` 与 `CreatedOffsetMinutes` 决定，离线补传不改变内容日。
- 由此存在两条过期路径：①当日生成后又收到内容日为当天的输入 → 当日补生成；②次日才收到内容日属于昨天的输入 → 次日补生成。
- 唯一例外是由当日晚到输入导致的过期草稿；即使次日才处理，也只能使用该日及更早的材料。
- 已 `Confirmed` 的稿件若该日已有导出记录，待导出记录失效并需重新确认，系统不自动重新导出。
- 后来修改历史转写不得触发或允许重新生成原日期文章，但修改后的内容可参与未来主题检索。

## 8. AI 处理管线

### 8.1 模型配置

管理页分别配置：

1. 显式选择 API 类型的语音转写接口。
2. OpenAI 兼容的文章生成接口。
3. 可选的 OpenAI 兼容 Embedding 接口。

语音转写只要求用户提供 Base URL、写入式 API Key、API 类型和模型名；API 类型只允许
`openai_transcription`、`openai_chat_audio`、`dashscope_async`。**三个服务（生成 / 转写 / Embedding）在管理页上
一律有「启用」开关，也一律能清除管理页保存的 Key**（2026-09-30 修正：转写卡曾把这两项藏起来，并且保存时强制
`enabled=true`，后果是转写关不掉、密钥清不掉）。转写没有超时字段，其余两个有。
管理页不暴露内部 Secret 名；
Key 留空表示保持当前值，清除只针对管理页保存的值。部署侧仍可使用固定 Secret 文件或环境变量，客户端只能查看模型名与健康状态。

文章生成的新实例默认使用 DeepSeek：Base URL `https://api.deepseek.com`、模型 `deepseek-flash`、固定 Secret 文件名
`deepseek-api-key`。DeepSeek 不提供本项目需要的转写与 Embedding 接口，因此这两项仍是独立的 OpenAI 兼容端点。
「测试连接」必须使用用户在页面里当前输入、尚未保存的 Base URL、模型名与 API Key，向该能力的实际端点发送合成的最小输入；
只有模型真正响应成功才显示可用，无效 URL、模型名、缺少 Key、认证失败、超时、协议不兼容与网络错误都必须返回对应失败结果。
转写协议严格由 API 类型决定，不得读取 Base URL、厂商名或模型名前缀进行推断，也不得维护模型白名单：

- `openai_transcription`：`POST {base_url}/audio/transcriptions`，发送仅含音频文件与用户模型名的 multipart 请求。
- `openai_chat_audio`：`POST {base_url}/chat/completions`，请求只包含一个 `input_audio` 内容项；音频以 `data:<mime>;base64,<数据>` Data URL 发送，并携带 `stream: false` 和 `asr_options.enable_itn: false`。该契约可用于百炼 `qwen3-asr-flash`，响应从消息文本中读取。
- `dashscope_async`：`POST {base_url}/services/audio/asr/transcription` 提交任务，再从
  `GET {base_url}/tasks/{task_id}` 轮询直至成功或失败，最后读取返回的转写结果地址；任务 ID 和轮询过程不暴露给上层。

所有相对路径只拼接用户填写的 Base URL，并统一去除边界处重复 `/`。`dashscope_async` 要求公网可访问的 HTTP(S)
音频 URL；当前手机录音只保存在实例内部且没有公开上传能力，因此正常录音路径必须返回
`transcription.public_audio_url_required`，不得把本地文件路径作为 URL 提交。测试连接和真实转写共用同一协议适配模块。

### 8.2 转写流程

1. 客户端完成录音并写入离线队列。
2. 联网后上传，携带客户端生成的幂等 ID。
3. 服务端先持久化音频，再确认接收。
4. 创建转写任务并立即执行；**默认在上传请求里就把这次转写跑完**（2026-09-24 第二轮，附录 A.18）：
   音频与识别文本一起落库之后，同一次 HTTP 响应就把文本交回手机，手机不需要为了「看到自己刚说的话」再等一轮轮询。
   等待窗口由 `Transcription.InlineTimeoutSeconds` 控制（默认 90 秒，0 表示关闭同步等待、退回纯队列）。
   等待超时或模型失败时**上传仍然成功**：音频与条目都在，任务回到队列按退避重试，客户端可以稍后再问。
5. 成功后保存原始转写，识别主题并生成 Embedding。
6. 失败按退避策略重试三次，之后通知用户。

### 8.3 历史检索

- 只检索 `AllowFutureRecall = true` 的记录。
- 只允许检索文章内容日期当日及之前的记录。
- Embedding 可用时进行语义检索，否则退化为主题标签和全文搜索。
- 默认最多返回十条高相关材料，数量可配置。
- 历史事件必须以回忆或延续的方式表述，不得伪装成当天事件。
- 索引绑定 `EmbeddingConfigVersion`（模型名 + 维度 + Base URL 指纹）。更换 Embedding 模型（即配置指纹变化）后旧索引整体失效：`SemanticSearchAvailable` 置为 false，检索自动降级为主题标签与全文搜索，并在客户端提示“语义检索重建中”。
- 重建是可持久化任务、分批执行，期间降级检索始终可用，完成后原子切换。不保留多代索引；检索能力状态属外部能力状态，不计入基础健康检查。

### 8.4 生成与核验

生成请求应包含：

- 当天按时间排序的输入。
- 选中的历史材料及日期。
- **写作规范**（附录 A.24、A.28）：字数区间（默认最少 50、最多 300 字）、可选公差（默认 ±20 字，关掉即为严格区间）、人称（默认第一人称），以及用户自己维护的规范条目清单。
- 不得添加无来源事实的不可覆盖系统规则。
- 要求输出结构化正文及来源映射。

写作规范在**发布设置页**配置，随生成请求一起前置在当天素材之前，让模型先拿到成文要求再读素材。
规范条目是用户拥有的清单：默认给出行文风格、结构与段落、标题、开头与结尾、用词禁区五条，用户可以逐条改写、
删除、增删，也可以把清单清空；**只有从未配置过的实例才会拿到默认清单**，清空是一次明确的选择，不得在读取时
被重新种回默认值。字数区间、公差与人称是结构化字段，不是清单条目——它们决定篇幅与人称这种必须无歧义的信息。

篇幅按区间加公差交给模型（A.28）：**最少必须小于最多**；公差为 0 时把区间说死，大于 0 时把「可以到多少」一并
写进提示词（下限 `最少−公差`、上限 `最多+公差`，下限不小于 1），让素材多少决定最终落在哪儿。区间是意图，
公差是弹性：素材撑不满时不该为凑字数扩写，素材装不下时也不该为压字数删掉具体的事。

人称**只能**由写作规范表达，不得写进系统规则：系统规则是用户改不了的那一半，在那里写死一个「第一人称」
会悄悄压掉用户刚选的设置，配置看起来生效、实际不生效。

生成后执行第二阶段的无来源陈述检查，并保存检查时刻与存疑句。正式发布必须等待检查完成；用户在发布设置页明确点击发布后，
系统确认当前工作版本并可在接受已记录存疑句的前提下继续发布。模型请求的超时必须覆盖响应头与响应体读取全过程，不能因为服务商只返回响应头就让任务永久停在运行中。

不得在产品文案中声称模型能够“绝对不捏造”。应表述为“提供来源追溯和无来源陈述检查，帮助用户核验”。

## 9. 客户端体验

### 9.1 首页

- 醒目的开始/停止录音按钮。
- 直接文字输入入口。
- 今日输入数量。
- 上传、转写及生成状态。
- 待确认或已过期草稿提醒。

首版不要求 Android 小组件、快捷设置磁贴或全局快捷键。

### 9.2 离线队列

- 客户端必须先安全落盘再显示录音完成。
- 上传使用幂等键，重试不得产生重复输入。
- 服务端确认持久化后才能删除本地临时副本。
- 用户应能查看失败原因并手动重试。

### 9.3 主要页面

2026-09-24 第二轮把手机端收窄成三个页面（附录 A.18）。手机上**只**做这三件事：

- **今日随想**：一个占据屏幕中央的大圆圈（圈内写「记录随想」），点一下开始录音、再点一下停止；圆圈右上角的按钮切换成手动输入。圆圈下方是这一条记录的控制区——播放、可拖动的进度滑块、暂停、删除（二次确认）；录音识别回来的文字显示在同一区域。最下面是**上传按钮**：只有点了它才会上传（不做后台自动上传）。上传成功后，识别文本与录音一起留在本机。
- **日历**：一行一条记录（录音与手写同级），**每一行都必须标明时间**；点击打开一个窗口，里面是这条记录的播放控件（手写的没有）与完整文字。右上角筛选：从新到旧、从旧到新、今日、昨日、本周、本月。
- **设置**：服务器地址、测试连接、配对与解除配对、本机记录占用与清空、实例模型名。

同时明确**本机记录不再在上传成功后删除**：手机是「往期记录」的事实来源，上传只把副本送到服务器。删除只发生在用户明确点击删除时。

草稿、主题、来源核验、修订转写、版本切换与发布**不在手机端**，它们在后台管理里。

## 10. 身份与安全

### 10.1 管理员初始化

- 首次启动创建管理员账号 `admin`。
- 使用密码学安全随机数生成初始密码。
- 初始密码只在启动终端输出，不写入普通日志文件。
- 首次登录强制修改账号和密码。
- 服务器端只保存强密码哈希，不保存明文密码。

### 10.2 设备配对

- 管理页生成十分钟有效、仅可使用一次的配对码或二维码。
- 配对成功后签发独立设备令牌。
- 令牌应可轮换和单独撤销。
- 客户端使用平台安全存储保存令牌。
- **撤回与删除是两件事**：「撤回」是安全动作，立刻让令牌失效；「删除记录」是日常清理，只允许删**已撤回**的设备（删一台还在授权中的设备等于绕开撤回那条明确的路径）。删除时**内容必须留住**：输入行上「哪台设备录的」这一归属被清空，条目本身、录音、稿件与来源映射都不动——内容属于实例，不属于设备。配对码作为单次使用历史保留，只把 `redeemed_device_id` 清空。实现上两处引用都要在同一个事务里松手，否则会撞外键（2026-09-29 线上就是这样：用手机录过内容的设备一删就 500）。

### 10.3 HTTP 风险

产品允许 HTTP，但必须：

- 管理端登录页明确说明密码、令牌、录音和文章可能被截获。
- 管理员在通过 HTTP 登录时主动确认后才能继续。
- 登录后的管理页面和手机端不重复显示警告，避免提示淹没真正需要处理的状态。
- 文档优先推荐 HTTPS、局域网或 VPN。

警告不等于安全措施，不得在文档中暗示 HTTP 经过确认后便是安全的。

### 10.4 Secrets

**密钥只有一个入口：管理页。**（2026-09-29 修订，定案见附录 A.27；此前允许 Docker Secrets 文件与环境变量，已删除。）

- 模型密钥与 SMTP 密码由管理员在管理页填写，加密存放在配置目录（`keys/ui-secrets/`，与 DataProtection 密钥环同处）。
- 配置、环境变量、挂载文件都**不能**提供凭据；`ISecretStore` 只有一个实现，就是那一个加密存储。
- 该目录在实例根目录之外：因此不进配置表、不进可读导出、不进备份包，恢复旧备份也不会带回一把可用的密钥。
- 管理页永远不返回已保存的值，只报告「已保存 / 未配置」（`SecretSource.Ui` / `None`）。
- 密码清除写入一条空记录，它与「从未设置」必须可区分（否则清掉的凭据会被下一层来源复活——那一层现在不存在了，区分仍然保留，因为界面要能如实说明状态）。
- 普通数据导出及备份不得包含 Secrets。
- 设备令牌不属于上述 Secrets，但同样不进入备份与导出（见 §15.2）。
- 日志默认不得记录转写正文、提示词、模型响应或认证信息。

## 11. 导出为 Markdown

### 11.1 导出生命周期

「发布」在本产品里的含义是**把确认过的稿件导出成一份 Markdown 文件**。队列、幂等与审计这套机制保留，操作对象从远端文章换成本地文件。管理页只暴露一个正式发布目标；旧版多目标数据结构保留为兼容实现，不再作为界面功能。

- 生成成功后，当前工作版本立即以 `draft: true` 写入可配置的草稿目录（默认 `drafts`）。
- 默认只有 `Confirmed` 的稿件可被导出。**勾选了「允许自动公开发布」的目标例外**（附录 A.33）：到点直接导出**当天生成的工作稿**，不要求先有人确认，**导出成功即视为用户认可**并把这一天标为已确认（附录 A.36）。没勾选的目标保持原规则。
- 同一版本向同一目标导出恰好一次；再次导出是同一记录的下一轮（`ExportRound` 递增），不是第二条记录。
- 正式发布写入可配置的发布目录（默认 `posts`），front matter 中为 `draft: false`；Hexo 不会生成草稿目录中 `draft: true` 的文章。
- 同一天只能有一份正式发布稿。重新生成并发布新版本时，先确认旧文件仍与本实例记录的哈希一致，再删除旧文件并把旧发布记录标记为 `Superseded`；外部修改过的文件不自动删除，并阻止本次替换。
- 当天已有正式稿时，重新生成或确认新稿都不构成替换授权：旧正式稿和发布记录保持不动，自动发布也会跳过这个替代稿。只有用户点击「发布稿件」后，才执行上条所述的安全替换。
- 若替代稿到达配置的发布时间仍未发布，启用「新草稿待处理」邮件事件时只提醒一次，不自动发布或撤下旧稿；用户继续不处理也不会重复催促。下一次重新生成后，上一份未发布替代稿退出可见版本槽，以最新稿为准。
- 生成与导出时刻分别配置；默认 23:00 生成、次日 08:00 进入导出队列。
- **发布时刻按「它出现在生成时刻之后的那一次」解释**（附录 A.29）：发布时间晚于或等于生成时间就是**当天**，否则是**次日**。默认组合（23:00 生成、08:00 发布）因此仍是次日早晨；而「23:00 生成、23:16 发布」这种当晚发布的配置就是当天 23:16，不是 24 小时之后。三条路（调度入队、替代稿提醒、手动入队时的计划时刻）必须用同一处实现，不得各自重算。
- 管理页必须显示这两个时刻与服务端算出的**具体日期时间**，以及当前实际生效的规则：开了自动公开就说「到点会直接发布这一版」，没开就说「只处理已确认的稿件」。勾了开关却什么都不发生时，用户唯一的线索就是这一行。
- 夜间新增素材使待导出记录失效（`Superseded`）；补生成后才重新进入队列。
- 导出失败自动重试三次，之后通知用户。
- **执行窗口（2026-09-16 定案，2026-09-24 沿用）**：`Publish.WindowMinutes` 默认 120，自计划时刻起计。超窗未执行则该记录转 `Expired`，除按配置发邮件外不触发任何自动动作；`Expired` 只能由用户手动重试或重新确认后回到队列，服务重启不构成延期理由。
- **无人确认的自动发布**：默认关闭，开启与关闭都不再要求重新输入密码（附录 A.25），但必须在管理端操作并**展示风险提示**；只处理已确认稿件，并向正式稿目录写入 `draft: false`。设备令牌永远不能开关它——这条路由是管理员专属，「谁能到得了这里」才是保护。开关的改动由服务端记录操作者与时刻。
- **权限**：改输出目录、front matter 模板、**写作规范**、自动发布开关或通知收件地址必须用管理员身份。手动动作由服务端记录 `TriggeredBy`、`TriggeredAtUtc`。
- 记录文件名与内容哈希；本地后续修改不得静默覆盖已导出的文件。

### 11.2 Markdown 文件

- 产出带可配置 Front Matter 的 Markdown。
- 默认文件名为 `YYYY-MM-DD-slug.md`。
- 支持 `title`、`date`、`updated`、`tags`、`categories`、`draft` 和正文占位符。
- 文件写入用户指定的服务器挂载目录；目标目录必须是**数据目录**下的**相对路径**，绝对路径或试图跳出的路径一律拒绝。
- MVP 不执行 Hexo、Git 或其他外部命令。
- 不得静默覆盖已存在或被外部修改的文件：默认只覆盖「本实例写过、且内容仍是它写的那样」的文件，其余情况改为写入带版本号的新文件或直接拒绝。**唯一的例外是用户在「检查文件」看到差异之后明确选择「覆盖」**——那不是静默写入，而是用户看过差异后的决定，必须如实执行（§17.3 第 7 步）；而「本实例从未写过」的同名文件在任何情况下都不动，即使带着确认也一样。
- 再次导出默认创建带版本号的新文件（`YYYY-MM-DD-slug-2.md`），用户明确确认后才能替换。

**当前边界（附录 A.19、A.24）**：front matter 模板、草稿/正式稿相对目录与**写作规范**已可在发布设置中配置；
发布设置页的排列顺序是生成/发布动作 → 两个计划 → **博客生成规范** → Front matter 模板。整页的「保存发布设置」在页面右上角、
与「刷新状态」并排——它保存的是整页，所以不隶属任何一段设置（曾贴在「时区」那一行，被读成时区的设置动作）。目录始终限制在数据目录内（A.31）。
应用不运行 Hexo、Git 或部署命令，也不把站点仓库当成第二份内容数据库。

## 12. 邮件通知

使用通用 SMTP 配置，不为 QQ 邮箱、Gmail 等服务分别开发专用集成。

**2026-09-24 第二轮：配置必须能在后台完成（附录 A.18）。** 这一条是对 §10.4 的一次收窄解释，不是突破：

- 邮件配置**照 ani-rss 的样子只要求七项用户输入**：**SMTP 地址、SMTP 端口、发件人邮箱、密码、SSL、STARTTLS、收件人邮箱**，
  外加一个「启用」开关（一个刚部署的实例不能因为填了主机就开始发信）。**发件人邮箱同时就是 SMTP 用户名**；
  没有独立的用户名、发件人名称、超时或 Secret 名字段。**也不提供任何服务商预设**——主机与端口由用户自己填。
- **SSL 与 STARTTLS 是两个独立勾选框**，不是一个三选一：勾 SSL = 连上立刻 TLS 握手（465 的用法，
  别的软件里写「SSL：是，STARTTLS：否」）；勾 STARTTLS = 先明文打招呼再升级（587 的用法，
  别的软件里写「SSL：否，STARTTLS：是」）；两个都不勾 = 不加密，只适合本机中继。
  **两个都勾会被拒绝保存**（`smtp.security.conflicting`）：那种组合没有意义，只会在握手阶段以看不懂的方式失败。
  同理，**存在密码却不勾任何加密会被拒绝**（`smtp.security.credentials_in_clear`）——不能让明文连接把密码发出去。
- 密码可以直接填，值仍然不外流：它被加密存放在**配置目录下的凭据目录**里（部署里是 `<配置目录>/keys/ui-secrets`，在实例根目录之外），**不进配置表、不进导出、不进备份**；
  后台只能看到「有没有密码、来自哪里」，读不回明文。解析顺序是「后台填写的值 → Secret 文件（固定名 `smtp-password`）→ 环境变量」，
  所以用 Docker Secrets 的部署照旧可用。**老的部署配置键 `Smtp__Security` / `Smtp__UseStartTls` 仍然被尊重**并映射到这两个开关。
  「清除已保存的密码」写下的是一条**显式的空记录**而不是删除记录，因此它也盖住 Secret 文件里的那一份：
  否则操作者会看到「请清空密码」的提示却清不掉，而一个从示例目录抄来的遗留文件就会让本来能发信的实例发不出信。
- 提供**发送测试邮件**：真的发一封，并把失败原因（稳定错误码 + 说明）如实显示。只做问候语探测不足以证明「能发出去」——这个项目在部署实例上正是被这一点误导过。
- 收件地址与事件开关在同一处：没填收件地址、或三个事件开关全关，就什么都不会发；界面必须把这件事写清楚，而不是让用户猜为什么收不到信。

可独立启用的通知事件：

- 新草稿待处理（包括生成完成，以及已有正式稿的新版本到发布时间仍未发布）。
- 任务最终失败。
- 自动导出成功或失败。

**邮件可以带上稿件正文（2026-09-30 定案，附录 A.34）**：默认**不带**——邮件默认走明文，正文是这个产品最私密的东西，自动往收件箱塞一份比塞一句「请到实例里看」更糟。通知管理里提供「邮件里附上稿件正文」，打开后**新草稿待处理**与**导出成功 / 已上传草稿**这两类信会附上正文原文（Markdown，不含 front matter 元数据）；**失败与超时**的信永远不带，它们只需要原因与错误码。这是一个内容开关，与三个事件开关相互独立：事件决定「发不发」，它决定「发的时候带不带正文」。

邮件任务与业务任务解耦。邮件失败不能回滚稿件、触发重复生成或改变导出结果。

## 14. 后台任务与可靠性

- 任务必须持久化，服务重启后可恢复。
- 启动时把上一次进程留下的 `Running` 任务一律重排（此刻本实例不可能真有任务在跑），并且**目标自身的中间状态不得成为死路**：被中断的转写会把输入复位为待转写再重跑（音频还在，重跑安全）；被中断的导出则相反——文件可能已经写出来了而记录还不知道（进程死在写入与落库之间），重排后再写一次就会多出一份带版本号的文件，因此重排后按计划跳过，把「本地不知道磁盘上发生了什么」如实留给用户（见附录 A.15、A.17）。
- 同一输入的转写、同一日期的生成以及同一版本向同一目标导出都必须幂等。
- 临时错误采用指数退避，默认最多三次。
- 达到上限后进入最终失败状态并按配置发邮件。
- 用户修复配置后可以重试单项或批量补跑失败任务。
- SMTP 失败只影响通知任务。
- 自动导出超过合理执行窗口后不得静默补做，必须重新确认或手动重试（窗口长度见 §11.1，默认 120 分钟）。
- 转写、生成、来源检查与 Embedding 的超时必须覆盖 HTTP 响应头和响应体读取全过程；超时归类为可重试的外部故障，不能留下永久 `Running` 任务。

初期可使用数据库驱动的后台队列，不必引入外部消息中间件。确保多实例部署未被支持时，Compose 只运行一个任务执行实例。

## 15. 数据导出、备份与迁移

### 15.1 可阅读导出

至少包含：

- 每篇随想的 Markdown。
- 输入、主题、来源映射和元数据 JSON。
- 尚未被保留策略删除的音频文件。

**音频保留策略（2026-09-16 定案；计时起点见 2026-09-30 的附录 A.35）**：转写成功且该日的**保留计时起点**到达后，音频进入可清理状态；`Retention.AudioDays` 默认 30，可配置为“永久”或 0（立即删除）。**起点 = 首次确认与首次公开发布中较早的那个**——两个事件都意味着「这一天的文字已经定下来、录音不再需要留着核对」。到期物理删除音频文件，`InputEntry` 与转写文本保留，`AudioPath` 置空并记录 `AudioDeletedAtUtc`。清理是独立的可持久化任务（`JobType = AudioCleanup`），失败不影响业务；管理页与导出说明须明示当前策略。

**随想内容保留策略（2026-09-24 第二轮定案，附录 A.18；计时起点见 A.35）**：`Retention.ContentDays` 默认 **-1（永不删除）**，可配置为 0（计时起点到达后立即删除）或 N 天。计时起点与音频策略同一个（首次确认 / 首次公开发布，谁先算谁）。到期时删除的是**内容**——录音识别得到的文本与手动输入的文本都算在内：

- 音频文件按音频策略删除；
- 输入的 `OriginalTranscript` / `RevisedTranscript` 置空，并置 `DeletedAtUtc`（**软删除**）；
- 之所以不物理删除整行：`SourceReference` 指向输入行，物理删除会让历史文章的来源映射悬空（§6.5、§17.1 要求它可解析）。

清理同样是独立任务（`JobType = ContentCleanup`），默认每天 04:30，此外运维侧提供“立即清理一次”。**默认值是永不删除**：一个刚部署的实例不会自己动用户的内容。

**用户手动删除与保留策略不同（附录 A.23）**：数据管理页确认删除后物理移除输入行及音频，并在同一数据库事务中删除该输入对应的
`SourceReference`；主题关联与 Embedding 由外键级联清理。已生成的文章正文和版本仍保留，只是不再把已删除输入列为来源。
删除先落库、再删音频：必须避免的漂移是「活着的行指向已经没了的文件」，而反过来留下的孤儿音频不可见、可由清理任务回收。
保留策略仍按上一段保留墓碑；墓碑不在数据管理页展示，但运维可用 `includeDeleted=true` 显式取得（§10.3）。

### 15.2 完整备份

- 包含 SQLite 数据库、媒体、Markdown、索引元数据和非秘密配置。
- **不包含设备令牌及其派生的会话状态**（2026-09-16 定案）：恢复后所有设备必须重新配对。此举与 §10.4 凭据不外流原则一致，且重配对仅需管理页生成十分钟一次性码，成本很低。
- **不包含 DataProtection 密钥环**（2026-09-16 定案，见附录 A.14）。密钥环签发管理员登录 Cookie，属**凭据等价物**：放进实例根目录就等于让每份备份都带着伪造会话的能力，与上一条同理。它必须在实例根目录之外独立持久化——否则重建容器会静默登出管理员——但不得进入备份。
- 支持管理页一键备份。
- 支持每日定时输出到挂载目录。
- 默认保留最近七份。
- 必须提供在全新实例上的恢复验证流程，采用以下八步（2026-09-16 定案）：
  1. 全新空目录，只放入 `compose.yaml`（默认形态下连 `.env` 都不需要；要复现「绑定挂载到指定目录」的形态就设 `DM_DATA_DIR` / `DM_CONFIG_DIR`，见 §5 的部署约定）。**也不需要任何密钥文件**：凭据只能从管理页填（A.27），而这一步的校验不调用模型。
  2. `docker compose up -d`（从源码构建时是 `docker compose -f compose.yaml -f deploy/compose.yaml up -d --build`），确认自动迁移成功、管理员已初始化。
  3. 通过管理页恢复备份（SQLite + 媒体 + Markdown + 索引元数据 + 非秘密配置）。
  4. 校验基础健康检查全绿，且任务队列无遗留 `Running` 任务。
  5. 抽样校验：随想正文可打开、三版本位置完整、来源映射可解析（`QuoteHash` 匹配）。
  6. 抽样校验：语音输入可播放，且原始转写与修订稿均在。
  7. 校验：导出包与备份包中不含任何 Secret。
  8. 校验：原设备令牌不可用，且重新配对流程可正常完成。

### 15.3 数据库迁移

- 服务启动时自动执行向前迁移。
- 升级文档要求先备份。
- 不承诺自动降级；保留旧镜像和备份用于恢复。
- `0009_deleted_reflections` 为用户主动删除的内容日保存墓碑。删除稿件会清除其发布记录、全部版本和稿件主记录，调度器看到墓碑后不得重新生成同一天；已经写到数据目录的文件不由数据库删除动作移除，避免覆盖用户在外部做过的修改。

## 16. 可观测性

默认日志只记录：

- 请求或任务 ID。
- 状态变化、耗时和重试次数。
- 脱敏后的错误代码与摘要。

只有用户主动开启临时调试模式时才能记录内容相关信息，并必须提示可能包含私人数据。调试模式应自动到期。

服务提供健康检查，至少覆盖数据库可写、媒体目录可写、后台任务执行器状态；外部模型与 SMTP 使用独立的“测试连接”操作，不应让外部服务故障导致基础健康检查失败。Markdown 输出是本地目录，本就不属于外部服务，因此没有对应的“测试连接”（附录 A.17）。

## 17. 测试策略

### 17.1 单元测试

重点覆盖：

- UTC 与内容时区的自然日划分。
- 当日晚到输入引起的草稿过期和补生成资格。
- 禁止任意历史日期重新生成。
- 历史检索不得使用文章日期之后的内容。
- 三版本轮换不得覆盖手工编辑。
- 主题的合并、重命名与删除不得改变历史文章的来源映射。
- “晚到”判定只依赖输入的创建时间与偏移，与生成任务是否已执行无关。
- 删除音频与删除整条记录的不同语义。
- 自动发布的状态转换和执行窗口。
- 可见性与导出文件中 `draft` 字段的一致性，以及「已写出的文件仍是自己写的」这条判定的边界。

### 17.2 集成测试

- SQLite 和文件系统的一致性。
- 录音上传幂等性和断线重试。
- 模型接口成功、超时、限流和无效响应。
- Embedding 降级及索引重建。
- SMTP 失败不影响草稿。
- 同一版本重复导出不产生第二份文件，且绝不覆盖不是自己写的文件。
- Docker 重启后任务恢复。
- 备份在全新实例恢复。

外部服务必须使用可控的测试替身。

### 17.3 端到端验收

必须完成以下真实路径：

1. Android 断网录制多条语音并输入文字。
2. 联网后由用户明确点击上传，服务端转写并在生成稿件时识别主题。
3. 服务端按内容时区生成当天随想并关联历史来源。
4. 用户查看存疑语句、修改转写和草稿、执行允许的重新生成。
5. 邮箱收到待确认提醒。
6. 用户把稿件导出成 Markdown：先导出草稿（`draft: true`），再手动导出为公开（`draft: false`），两次落在同一份文件上。
7. 在导出目录里手改那份文件后，`check-remote` 报出差异，且用户的选择（保留两边 / 覆盖）被如实执行。
8. 创建完整备份，并在全新服务实例按 §15.2 的八步恢复验证流程恢复全部内容。

## 21. 界面文案约定

界面上的字是产品的一部分，不是文档的一部分。2026-09-29 的一轮排查（附录 A.32）发现两类反复出现的问题：**把设计理由写进界面**，以及**把对话里的具体例子抄进产品**（页面上出现过 `/home/atri/data` 这样带人名的示例路径，而 `**加粗**` 这种 Markdown 在 Razor 里根本不渲染，只会原样显示星号）。以下四条是硬约定：

1. **只说「填什么、不能填什么」**。字段提示的长度上限是一句话；「为什么这样设计」「代价是什么」写进 CHANGELOG 与附录，不写进界面。判断标准：这句话删掉之后，用户还能不能把这件事做对？能，就删。
2. **示例一律用中性占位**，不许出现具体的人名、机器名或从对话里抄来的路径（用 `/srv/dailymusings/data`、`aaa/bbb/posts` 这类）。
3. **不用 Markdown 语法写界面文案**。加粗写 `<strong>`，代码写 `<code>`；`**`、`- `、`#` 在 Razor/XAML 里都是原样显示的字符。
4. **面向用户的报错说中文**，并且说得能照着做（「配对码已过期。」比 `The pairing code has expired.` 好）。领域不变量（正常操作永远碰不到、给开发者看的断言，如 `Relevance must be within [0,1].`）保持英文——它是断言，不是文案。

自查方式：搜 `class="hint"` 与 `<p class="notice"` 里长度超过约 60 字的段落，逐条问第 1 条那个问题；搜界面文件里的 `**`；列一遍 `UseCaseException` / `DomainException` 的消息，把用户可达的那些确认成中文。

## 22. 界面视觉约定

管理页与手机端是**一套 Apple（iOS 深色）风格**（2026-09-30 定案，附录 A.38）。本节是约束；可逐条勾选的验收清单一并在 A.38。

1. **改皮肤不改骨架。** 换肤只动样式层：管理页的 `src/DailyMusings.Admin/wwwroot/admin.css`（唯一样式入口，由 `src/DailyMusings.Server/App.razor` 引用，改样式必须同时更新引用上的 `?v=` 串），以及手机端的 `Resources/Styles/Colors.xaml` 与 `Styles.xaml`。手机端页面里若有内联的字体重写（`FontFamily="OpenSansSemibold"` 这类），一并归到系统字体：它只是呈现属性，但留着会让同一种强调在列表里一会儿是 OpenSans、一会儿是系统字体。不改页面结构、不改 DOM 层级、不改 C# 逻辑、不改 API，也不引入前端框架或 UI 组件库。
2. **颜色与形状只从令牌层取。** 两个界面各有一处令牌层（管理页的 `:root`、手机端的 `Colors.xaml`），组件规则一律引用令牌，不写死颜色值。手机端的令牌**键名不可变**——它们已被 `Styles.xaml` 与三个页面引用，改名就是把换肤变成结构改动。
3. **层次靠层级色与分隔线，不靠投影。** 纯黑底上的投影会脏；深浅用层级色差与 1px 分隔线表达。
4. **只有深色一套。** 不写浅色分支，不做主题切换。
5. **四条不可破的既有约束**：
   - 危险操作（撤回授权、删除随想、还原备份）与普通操作在视觉上分得开（`.btn-danger` / `.risk`）——原先只记在 `admin.css` 头部注释里，本轮提升为正文约定；
   - 窄屏（`<900px`）侧栏折叠成顶部菜单，而不是把内容挤没（同上）；
   - 数据管理页的版式是用户指定的：单元格高度手动输入为 `x`、录音随想为 `1.5x`，一行必须包含 `[时间，类型，状态，内容]`，录音的播放功能区在内容下方（附录 A.18）；
   - 界面文案仍受 §21 约束。
6. **验收方式**：管理页按桌面宽屏（≥1200px）与窄屏（<900px）两种宽度各看一遍，手机端在 Android 模拟器上走一遍三个页面（沿用附录 A.20 记的回归方式），两者都以截图作为证据。

| A.36 | 自动发布成功即视为用户认可 | 勾选自动公开而用户没有干预时，**没有干预即视为认可**：公开发布成功后把这一天确认为「已确认」，页面不再停在「待核验」。**取代 A.33 中「不替用户写确认」那一半**——用户实测后明确要求这个语义 | §11.1 |
| A.37 | front matter 的两个时间 | `date` = 这一版生成的时刻，`updated` = 这一版最后改动的时刻，两者都按**内容时区**渲染。修正线上文件里 `date` 是内容日午夜、`updated` 是 UTC 的错（附录 A.37） | §11.2 |
| A.38 | 界面视觉：Apple（iOS 深色）风格 | 管理页与手机端只保留**一套 Apple 深色**皮肤；颜色与形状只从令牌层取；层次靠层级色与分隔线而非投影；改皮肤不改骨架；手机端令牌键名不可变 | §22 |

### A.1 音频保留策略

**问题**：§15.1 声明导出“尚未被保留策略删除的音频文件”，但全文没有任何地方定义该保留策略；§6.1 只有 `DeletedAtUtc`。导出范围、备份体积、隐私承诺，以及“转写成功后能否立即丢弃音频”都取决于此。

**备选与权衡**：

1. 转写成功后立即删除音频——隐私最强、体积最小，但用户事后无法复核转写是否有误。
2. 永久保留，仅在删除整条记录时清除——可回溯性最好，但备份体积与隐私风险最大。
3. 确认草稿后保留 30 天（可配置）——兼顾三者，代价是需要一套独立的清理任务与状态。

**定案理由**：选 3。本文的核心卖点是“来源可核验”；若转写成功即删音频，用户日后怀疑转写有误便无从复核，等于自断一半卖点；而永久保留又会同时恶化备份体积与隐私承诺。30 天覆盖“当天录、过几天核对”的实际节奏，且保留“永久”“立即删除”两个极值以满足不同偏好。

### A.2 自动发布执行窗口

**问题**：§14 要求“超过合理执行窗口后不得静默补发”，§17.1 要求测试该窗口，但全文未给数值。这是“不得静默公开”这一安全承诺的唯一执行依据，没有数值就无法实现也无法测试。

**备选与权衡**：

1. 60 分钟——更保守，但能容忍的故障窗口过短。
2. 120 分钟——覆盖容器重启与短暂故障，且不至于跨夜。
3. 当日有效（至 23:59）——最省心，但实质上放松了 §14 的约束。
4. 不设过期，重启后仍可自动发布——直接违背 §14，不采纳。

**定案理由**：选 2。默认导出点为次日 08:00，用户的白天在线时段足以处理两小时内的告警；窗口再长到跨夜，就等于把“不得静默补做”架空。同时明确**重启不构成延期理由**，否则反复重启即可无限延长窗口。

**2026-09-24 补充（A.17）**：这一条的对象从「自动公开到博客」变成了「自动写出文件」，数值与理由都未变。竞态里被保护的东西换了名字但没换性质：原来怕的是「没人看着就公开了」，现在怕的是「没人看着就把一份 `draft: false` 的文件写进了你的站点仓库」。

### A.3 稿件状态模型

**问题**：§6.3 状态机图把 `Failed` 与 `StaleByLateInput` 画成状态，字段列表却同时有 `Status` 与 `IsStaleBecauseOfLateInput`，二者关系未说明。这决定枚举取值、数据库约束，以及客户端“草稿”页的默认分组。

**备选与权衡**：

1. 七值 `Status` 枚举，布尔字段降级为审计用途——与状态机图一致，客户端可直接按状态分组。
2. `Status` 只保留主流程五值，失败与过期用两个标志位表达——状态更正交，但“已失败 + 已过期”这类组合需要 UI 层自行推导展示态，分组逻辑会散落到客户端。

**定案理由**：选 1。状态机图本就是状态语义；选 2 会让展示态推导逻辑进入客户端，与 §4.1“AI、调度与发布逻辑统归服务端”的分工相悖。另外 `Failed` 是**稿件态**，必须与 `ProcessingJob` 的**任务态失败**严格区分，避免两套失败语义互相污染。

### A.4 晚到输入的判定

**问题**：§7 提到“当日晚到输入”、§11.1 提到“夜间新增素材使待导出记录失效”，但未定义到达时间与内容日的关系，也未说明能否跨日到达。它直接决定补生成资格与导出队列的重入条件。

**备选与权衡**：

1. 以内容日 `23:59:59`（内容时区）为界——判定只依赖输入自身的创建时间与偏移。
2. 以当日生成时刻（默认 23:00）为界——更贴近“生成之后才算晚到”的字面表述，但生成因故障延到 23:40 执行时，“23:30 到达的输入”是否算晚到就没有唯一答案。

**定案理由**：选 1。它使“是否晚到”与“生成任务是否已经执行”完全解耦，因而确定、可离线补传、可单元测试。选 2 会把生成任务的执行时序引入判定，产生无法判定的边界情况。

### A.5 内容时区变更

**问题**：§7 规定内容时区可配置，§4.1 将其列为管理页配置项，但未说明变更是否回溯。

**备选与权衡**：

1. 不回溯，`ContentDate` 一经写入即不可变——历史数据稳定，但选错时区的实例会“前后不一致”。
2. 变更时全量重算 `ContentDate`——历史归属日会变，冲击“按日唯一”、补跑资格与已导出内容的日期归属。
3. 默认不回溯，另附一次性迁移工具。

**定案理由**：选 1。`ContentDate` 不可变是补生成规则能成立的地基：一旦可重算，“某日是否已生成”“某输入是否属于该日”都会失去稳定答案，与 §7 的不可变精神直接冲突。时区在实际中极少变更，且要纠正的是**新数据**的时区，历史数据本身并没有错；选 3 的工具属于假想需求，按 §20 不提前引入。

### A.6 来源定位格式

**问题**：§6.5 只要求“段落定位信息”，§8.4 要求存疑句子在客户端高亮。高亮、版本切换后的漂移检测，以及“来源核验”界面的实现都依赖一个确定格式。

**备选与权衡**：

1. 段落序号 + 字符区间 + 引用哈希——三层定位，可检测漂移。
2. 仅整段定位——实现最简，但存疑句子只能高亮到段落。
3. Markdown 块 ID 锚点——定位最稳，但正文会被标记污染，影响 Markdown 输出。

**定案理由**：选 1。`QuoteHash` 是这里唯一的漂移检测手段：用户手工编辑后段落文本已变，若仍按旧偏移精确高亮就会**指错地方**——在“帮助用户核验来源”的场景下，指错比不指更糟。哈希不匹配时降级为整段提示并告知版本已被编辑，是唯一诚实的处理方式。选 3 会侵入正文格式，与 §11.2 的 Markdown 输出要求冲突。

### A.7 发布权限边界

**问题**：§4.1 把“发布操作”列入客户端职责，§11.1 要求无人确认的**自动**公开需再次验证管理员身份；手动公开是否也需管理员二次验证，未说明。这决定设备令牌的权限模型与 API 鉴权策略。

**备选与权衡**：

1. 设备令牌可手动公开（客户端二次确认 + 服务端审计）；自动公开开关仅管理页可开。
2. 手动公开同样要求管理员密码——更保守，但日常在手机上发布会很繁琐。
3. 设备令牌只能上传草稿，所有公开动作都在管理页完成——剥夺了 §9.3 草稿页的发布能力。

**定案理由**：选 1。§11.1 的“再次验证管理员身份”在原文中明确限定于**无人确认的自动导出**；手动导出本身已经有人在确认，若再要求管理员密码，§9.3 的“草稿页导出”在手机上基本不可用。风险仍被看住：二次确认不可省略、导出动作留审计字段、自动导出的开关能力完全不给设备令牌。

**2026-09-24 补充（A.17）**：WordPress 移除后，「手动」与「自动」的差别只剩下一件事：**谁按下了导出**。因此这一条的结论原样成立，而且更容易说清楚——设备令牌可以手动导出一份文件，但只有管理员能打开「自动导出」这个开关，而自动导出的默认产物仍然是 `draft: true` 的草稿文件。

### A.8 检索失效与降级

**问题**：§8.3 说“更换 Embedding 模型后旧索引失效，重建完成前使用降级检索”，§16 要求健康检查不受外部依赖影响，但“语义检索当前是否可用”没有可查询的判定来源——否则每次检索都要临时探测模型。

**备选与权衡**：

1. 配置指纹 + 全库失效 + 全局降级开关——判定来源唯一，实现简单。
2. 按指纹保留多代索引并支持回退——可回滚，但存储与查询复杂度显著上升。

**定案理由**：选 1。`SemanticSearchAvailable` 必须是可查询状态，否则 §8.3 的降级检索与客户端“重建中”提示都无从实现。选 2 是为假想需求增加复杂度，与 §20 冲突。另需明确：重建状态属外部能力状态，**不**计入基础健康检查，否则 Embedding 服务不可用会连带让基础健康检查失败，违反 §16。

### A.9 主题引用稳定性

**问题**：§6.2 要求支持合并且“删除主题不得删除原始输入”，§6.5 的 `SourceReference` 关联的是输入而非主题。所以文档已隐含可解，真正待确认的只有一点：主题 ID 是否允许变化。

**备选与权衡**：

1. 主题 ID 稳定不可变，合并留 tombstone——成本是一行记录加一个 `MergedIntoId`。
2. 合并即删除被合并主题行——表更干净，但客户端缓存与历史引用会断裂，且旧 ID 可能被复用后语义串台。

**定案理由**：选 1。成本极低而收益明确；更重要的是，因 `SourceReference` 指向 `InputEntry`，历史文章的来源映射**天然不受**主题操作影响——这一条值得写成显式不变量测试固定下来，防止日后有人在合并逻辑里顺手改了引用。

### A.10 目标框架

**问题**：文档通篇未指定 .NET 版本；开发机已安装 SDK 为 10.0.302。阶段一的解决方案模板、`TargetFrameworks` 与 Docker 基础镜像选择都直接依赖它。

**备选与权衡**：

1. .NET 10——与开发机 SDK 一致，MAUI 模板与工作负载现成。
2. .NET 8 LTS——长期支持更稳，适合“多年不升级”的目标，但需另装 SDK，MAUI Android 工具链较旧。

**定案理由**：选 1。交付物是自托管的 Android APK（电脑端已于 2026-09-24 退出范围，见 A.17），不经商店审核，LTS 的“长期免升级”优势在此场景并非硬需求；与开发机一致可避免额外的工具链维护成本。另明确 Docker 基础镜像固定 tag、不使用 `latest`，以免镜像漂移导致“同一版本行为不同”。

### A.11 Android 最低版本

**问题**：同 A.10，需确定 `SupportedOSPlatformVersion`。

**备选与权衡**：

1. API 24（Android 7.0）——覆盖面更广，但旧版存储权限与后台限制差异多，兼容分支显著增加。
2. API 26（Android 8.0）——避开旧版存储权限差异，覆盖绝大多数在用设备。
3. API 29（Android 10）——测试矩阵最小，但会排除部分在用设备。

**定案理由**：选 2。运行时权限模型在 API 23 之后已统一，再取 26 可避开旧版存储权限的兼容分支；继续下探收益极小、分支成本陡增，而 29 的门槛对“个人自用”场景不必要地苛刻。

### A.12 恢复验证流程

**问题**：§15.2 要求“必须提供在全新实例上的恢复验证流程”，§19 要求“Docker Compose 环境可以从空目录部署”，但两处都没有步骤与判定标准，导致完成定义无法判定、用户文档也无从下笔。

**备选与权衡**：

1. 八步清单——覆盖迁移、任务队列残留、来源映射完整性、音频可播与 Secret 排除。
2. 精简为四项核心校验（服务能起、文章能看、音频能放、无 Secret 泄露）——更轻，但不校验任务队列残留与来源映射完整性。

**定案理由**：选 1。它的价值在于把 §15.2 与 §19 的两处要求接成一条可执行、可判定的清单，并直接充当 §17.3 端到端验收的第 8 步。选 2 会漏掉两类恢复失败模式：遗留 `Running` 任务导致的重复执行，以及来源映射无法解析导致的“文章看起来对、核验功能已坏”。

### A.13 备份排除设备令牌

**问题**：§15.2 原文写备份“包含 SQLite 数据库”，而设备令牌就存在于该库中，于是“恢复后原设备能否继续使用”没有答案。这是 A.12 清单第 8 步在编写时暴露出的真实歧义。

**备选与权衡**：

1. 备份不含设备令牌，恢复后重新配对——凭据不外流，攻击面最小。
2. 备份含设备令牌，恢复后原设备无需操作即可继续使用——灾难恢复体验最顺，但备份从此携带认证凭据。

**定案理由**：选 1。与 §10.4「普通数据导出及备份不得包含 Secrets」的原则保持一致，也让备份文件的泄露风险不因“恢复方便”而上升。重配对的成本很低——管理页生成十分钟一次性码、手机上扫一下，而恢复通常恰恰发生在手边就有设备的场景。

### A.14 DataProtection 密钥环的位置

**问题**：容器化部署时 ASP.NET Core 默认把密钥环放在运行时用户的主目录（容器内为 `/home/app/.aspnet/DataProtection-Keys`）。该路径位于容器的可写层，**重建容器即丢失**，于是每次重新部署都会让所有管理员会话失效。但把它放进实例根目录又会引出另一个问题：实例根目录就是备份集，密钥环因此会随备份外流。这个问题是在远程 Docker 环境做真实部署验收时，从启动日志的告警里发现的。

**备选与权衡**：

1. 不持久化，接受重建即登出——实现最简，备份天然干净；代价是每次重新部署都要重新登录，重建期间正在提交的表单也会失败。
2. 放进实例根目录——会话可存活，但备份从此携带可伪造管理员会话的材料，与 §10.4 和 A.13 的原则直接冲突。
3. 放在实例根目录之外的独立路径——会话存活，备份保持干净。物理形态随部署方式而定：当前 Compose 把它放在配置目录下的 `keys/`（该目录单独 bind mount，不进数据目录，因此也不进内容备份）。

**定案理由**：选 3。它同时满足两个约束：密钥环必须比容器活得久，但不得进入备份。这与 A.13 对设备令牌的推理是同一条——备份可以带走内容，不可以带走凭据。已用 `docker compose up -d --force-recreate` 在真实容器上验证：重建后同一 Cookie 仍被接受，密钥环文件位于实例根目录之外，且 `/var/lib/dailymusings` 内不含密钥环。

**正文落点**：§15.2。

### A.15 被中断任务的恢复语义

**问题**：§14 只写了「任务必须持久化，服务重启后可恢复」，没写**中断**（进程被杀、容器被替换、断电）留下的状态该怎么办。这一条是在阶段五补测试断言时暴露的：补上「重启后被中断的任务会被重排」这条断言后，测试第一次运行就红了——任务确实被重排了，但重排后的转写被领域规则拒绝（`input.transcription.bad_state`），因为输入条目还停在 `in_progress`，而 `BeginTranscription` 只接受 `pending`/`failed`。结果是：任务最终失败，输入永远拿不到转写，用户点「重试转写」也救不回来。缺陷不在恢复逻辑，而在「恢复之后目标的状态没人管」。

**备选与权衡**：

1. 启动时重排遗留 `Running` 任务，并把目标自身的中间状态按业务语义复位（转写复位后重跑；导出按计划跳过）——恢复是自动的，且不改领域规则。
2. 启动时把遗留 `Running` 任务直接标记为最终失败，交由用户手动重试——最保守，但把「机器被重启」说成了「你的这段语音转不出来」，而且用户往往并不知道要重试什么。
3. 什么都不做，让任务永远停在 `Running`——界面上一句「转写中」挂到天荒地老，等于静默丢数据。

**定案理由**：选 1，并按任务类型分别处理。判据是**重跑是否安全**：转写重跑安全——音频还在、目标条目唯一、写入的是同一个字段，所以把被中断的输入复位为待转写再跑一次，代价为零，收益是一条本来会永久丢失的转写。导出（当时是「发布」）重跑不安全——那时它指向上传到一个远端站点，请求可能已经进了对方的网络，重复发布是 §14 明令禁止的，所以重排后的发布任务在本地记录仍是 `InProgress` 时按计划跳过，把「本地不知道远端发生了什么」如实留给用户，由「检查远程」去核对。同一条原则也解释了为什么生成被中断后可以直接重跑：`Generating → Generating` 是生命周期里允许的自环，草稿没有「发出去了就收不回」的副作用。

**2026-09-24 补充（A.17）**：对象换成 Markdown 文件后，判据没有变，结论也没有变。文件确实可能已经写出来了而记录还不知道（进程死在写入与落库之间），此时重排再写一次就会多出一份带版本号的文件——对一份承诺「再次导出默认新建文件」的产品来说，那就是凭空多出一个副本。所以被中断的导出仍然按计划跳过，由用户自己决定是重新导出还是接受磁盘上的那一份。

**正文落点**：§14。回归断言在 `tests/DailyMusings.Api.IntegrationTests/JobRecoveryTests.cs`（真停真起：一个进程在转写中途被停止，数据库里留下 `Running`，新进程启动后同一条任务记录完成，尝试次数为 2）。

### A.16 Windows 交付形态：解压即用，不做安装包【已撤回】

> **本条目已被 A.17 撤回。** 电脑端客户端整体退出了项目方向，因此「交付形态」这个问题不再存在。以下内容保留，是因为它记录了当时踩过的坑与判断依据；它**不再是任何现行约束**，正文里对应的 §18 阶段五内容已划掉。

**问题**：§18 原文写「生成 Windows 安装包」，而「安装包」在 Windows 上默认指向 MSIX/Appx。交付前实测发现这条路对**自托管的个人工具**代价过高：自签名证书没有商用时间戳，`Add-AppxPackage` 要求证书先进入**本机**（而不是当前用户）的「受信任人」与「根」存储——因为 AppXSvc 以 SYSTEM 运行、只认本机存储——也就是**用户必须先用管理员权限导入一枚自己签的证书**才能装。更糟的是这条路必须真的装一次才会暴露问题：包里的清单引用了根本不存在的图片，而只做「能构建、能签名」的检查完全看不出来。

**备选与权衡**：

1. 交付 MSIX（自签名）+ 免安装 zip——形式上最"正式"，能从开始菜单启动；代价是每台机器都要一次管理员证书导入、每次客户端改动都要重新签名并复验两种形态，且签名链、时间戳、证书有效期都是长期负担。
2. 只交付**免安装 zip**（自包含，解压即用）——解压到任意目录双击即可运行；没有证书、没有安装步骤、没有卸载残留；代价是没有开始菜单入口、没有自动更新、包体较大（自包含 .NET 与 Windows App SDK）。
3. 只交付 MSIX，不做 zip——省一份包体，但把上面所有代价留给用户，且没有退路。

**当时的定案理由**：选 2。这个产品是**给自己用的自托管工具**，安装形态的价值是「打开就能记」，而不是「像商业软件一样被管理」。MSIX 的构建路径（`Platforms/Windows/Package.appxmanifest` 与签名参数）当时**保留在仓库里但不再作为交付物**。

**撤回时的实际处置**：不是「保留构建路径」，而是**整套 Windows 实现被删除**——`net10.0-windows` 目标、`Platforms/Windows/` 下的 WinUI 外壳与 `MediaCapture` 录音、`MediaPlayer` 播放、`Package.appxmanifest`、以及 README 与 `docs/发布校验值.md` 里那条 MSIX 留档，都已随 A.17 一并移除。**正文落点**：§3.2、§18 阶段五。

### A.17 方向调整：不做电脑端，交付只做 Hexo Markdown

**问题**：项目按 §18 走完了五个阶段，包括一个已验收的 Windows 客户端、一条 WordPress 发布路径，以及一条 Hexo Markdown 导出路径。此后方向被明确收窄，而这三件事在实现上是**互相支撑**的：Windows 客户端是「双端」这个前提的产物；WordPress 是「发布」这个概念原本的落点；而 WordPress 一旦移除，「公开 / 草稿」这个可见性概念就只剩 Markdown 一个消费者——它必须落到 front matter 的 `draft` 字段上，否则产品根本发布不出去。这三者若不一起定案，实现会被迫做隐式选择。

**备选与权衡**：

1. 保留全部实现，只在文档里降级——改动最小，但仓库里会留下一个不再交付、不再复验、却仍在构建与测试中的 Windows 目标，以及一条每个版本都要陪着跑的 WordPress 路径。§20 的「不为假设中的需求提前引入」直接反对这种状态：**未被复验的代码不是资产，是负债**。
2. 只删代码，文档照旧——更糟：文档会持续声称存在一个已经不存在的交付面。
3. 代码与文档一起收窄（本次选择）——删除 Windows 目标与 WordPress 全链路，把交付面明确成「产出一份 Markdown 文件」，可见性落到 `draft` 上。

**定案理由**：选 3。三条具体要求直接决定了删到什么程度：

- **不做电脑端**：`DailyMusings.Client` 只保留 `net10.0-android`；`Platforms/Windows/` 整个目录、`MauiProgram` 里的 `#elif WINDOWS` 分支、以及配套注释与文档全部删除。`PlatformNames` 保留为运行时平台名的归一化工具（Android 是唯一会出现的取值），因为它本来就是共享逻辑而不是平台实现。
- **交付只做 Hexo**：WordPress 退出范围。删除的不只是客户端实现，还有它在别处长出来的枝节：`PublishTargetType.WordPress`、`IRemotePublisher` / `WordPressSite` / `RemoteArticle`、`WordPressRestPublisher`、每目标的站点覆盖设置（`IWordPressSiteOverrideStore`、`UpdateWordPressSiteOverrideUseCase`、`/api/publish-targets/{id}/wordpress`、`WordPressSiteDto`）、`ExternalService.WordPress` 探测、管理页的站点设置区块、`wordpress-application-password` 这个 Secret、以及验收脚本里的真实 WordPress 环节。
- **先只要求一份 md**：`§11.2` 的产出一层保持原样（模板、文件名、安全写入、按版本号新建文件），这一轮把 Hexo 专属的 front-matter 与目录约定微调列为后续工作；该项后来由 A.19 补齐。

**代价与必须承认的后果**：

- **可见性现在必须真的落到 `draft` 字段上**，这从「WordPress 的草稿/公开」变成了「Hexo 会不会生成这篇文章」，因此它成了功能而不是装饰：`Published` 状态对应 `draft: false`，`DraftUploaded` 对应 `draft: true`。这不是新增需求，而是把原本只对 WordPress 有意义的语义接到了唯一剩下的目标上。
- **「检查远程差异」的含义变了**：远端就是磁盘上那个文件，`RemoteChanged` 变成「文件被人在编辑器里改过」。差异的三种处置里，**「拉取」恒定不可用**（把用户自己的文件抄回草稿会让导出目录变成第二份事实来源），它保留在契约里只为给出一个说明清楚的拒绝，而不是静默失败。
- **数据库要向前迁移一次**：`0006_markdown_only` 删除 WordPress 目标及其发布记录（`publication.publish_target_id` 没有级联，所以必须先删记录），把存活的 Markdown 目标从 `1` 重新编号为 `0`，并清掉 `publish.wordpress.%` 设置键。**这会真的丢弃 WordPress 目标的发布历史**，升级前应当先备份。稿件、版本、来源映射、输入与音频一概不动。
- **产物已重录，真机复验未做**：`docs/发布校验值.md` 里 1.0.0 的旧校验值是本轮改动之前构建的，已保留为历史留档；Android APK 已于 2026-09-24 按当前源码重建并记录新校验值（0 警告 0 错误），但**尚未在新产物上重跑真机验收**。

**正文落点**：§2、§3.1、§3.2、§4、§4.1、§5、§6.7、§10.4、§11、§13、§16、§17.2、§17.3、§18、§19、§20。回归方式：全量自动化测试（见 [`CHANGELOG.md`](../CHANGELOG.md) 的「当前进度」一节）加上 `tools/acceptance/` 里按新范围改写过的端到端脚本。

### A.18 第二轮调整：手机端收窄、主题由模型产生、后台八分区

**问题**：A.17 之后产品只剩「Android + 一份 Markdown」，但手机端仍然背着五页（今日/草稿/日历/主题/设置）与整套草稿治理，后台则是按开发阶段长的七个页面。实际使用中暴露三件事：

1. **手机上的能力与它的使用场景不匹配**。手机上真正会做的是「想起一句话 → 录下来 / 写下来 →（上传后）看看它被识别成了什么 → 以后翻得到」。草稿编辑、来源核验、版本切换、主题治理全都需要大屏与耐心，在手机上既难用又挤占了唯一的入口。
2. **主题原本要求用户先建、模型只做归类**，等于把「这一天的文章讲了什么」这件本该由模型在写作时回答的事，推给了用户在事前预判。而 §6.2 又要求删除主题不影响来源映射，于是「谁在用这个主题」这个问题从来没有被真正回答过。
3. **邮件配置不可用**：密码只能由 Docker Secrets 提供，管理页只能填名字；「测试连接」只读问候语、不认证也不发信。结果是运维照着别的软件（例如 ani-rss）的表单填完，却既发不出信也不知道为什么。

**备选与权衡**：

1. 保留手机端的全部页面，只把入口排序调整——改动最小，但手机端仍然是「一个缩小版的桌面管理页」，而 §20 明确反对为假设中的需求保留实现。
2. 手机端收窄成三页，主题改由模型产生、后台治理，邮件在后台可配可测——三类改动都直接对着上面三个问题。
3. 连后台一起收窄，把主题管理塞进某个现有页面——省一次导航重构，但「状态/设备/数据/模型/通知/发布/内容+主题/系统」这八件事彼此不重叠，混在一起只会让每次操作都要先在脑子里做一次翻译。

**定案理由**：选 2，并把后台按功能重做成八分区。

- **手机端只做三件事**：今日随想（大圆圈录音 + 一键切换手动输入 + 本条的播放/进度/暂停/删除 + 显式的「上传」按钮）、日历（一行一条、必标时间、点开看完整内容、可按新到旧/旧到新/今日/昨日/本周/本月筛选）、设置（连接与配对）。**上传是显式动作**，不做后台自动上传——用户按下它，才知道这一刻东西离开了手机。
- **本机记录不再在上传成功后删除**（这是对 §9.2「服务端确认持久化后才能删除本地临时副本」的补充说明）：§9.2 说的是「可以删」，而这一轮的需求是「往期记录在手机上也看得到」，所以副本保留下来并承担历史浏览。删除只发生在用户明确点击删除时。
- **主题由模型在生成时选出或新建**，服务端按名称幂等落库、`Origin = Model`；**只有用户可以删除**，被文章当前使用的主题不允许删除，后台要把「哪些文章在用」列出来并要求先迁移。判据只看 `WorkingVersionId` / `ConfirmedVersionId`：被淘汰的历史版本不算「当前稿件在用」，删除时会清掉历史版本上的标签行，但正文与来源映射不动——§6.5 的不变量仍然成立，因为来源映射指向的是输入。
- **邮件配置进后台**：密码可填、加密存放在配置目录下的凭据目录里（`<配置目录>/keys/ui-secrets`，在实例根目录之外，因此 §15.2 的备份仍然干净），解析顺序为「后台填写的值 → Secret 文件 → 环境变量」；「发送测试邮件」真的发一封并如实报错。这不是放开 §10.4，而是把「值不外流」落到实现上：值不进配置表、不进备份、不进导出、读不回明文。
- **识别文本随上传回传**：`POST /api/inputs/voice` 默认在等待窗口内把这次转写跑完并把文本放进同一个响应，超时或失败也不影响上传成功（音频与条目都已落盘，任务继续在队列里重试）。等待窗口 `Transcription.InlineTimeoutSeconds` 默认 90 秒，可关。
- **后台八分区**：状态 / 设备 / 数据管理 / 模型管理 / 通知管理 / 发布设置 / 内容管理（含主题管理）/ 系统设置。数据管理按用户给定的版式：手动输入的单元格高度为 x、录音随想为 1.5x，一行必须包含 [时间，类型，状态，内容]，录音的播放功能区放在内容下方。

**代价与必须承认的后果**：

- **手机端删掉了草稿/主题/来源核验/版本切换/发布**。这些能力在后台仍然齐全，但「在手机上确认今天的稿子」这件事不再可能——这是有意的收窄，不是遗漏。
- **新增一次数据库迁移 `0007_article_topics`**：新表 `reflection_version_topic` 与 `topic.origin`。**不回填历史版本的主题**：主题是对文章当下的判断，用输入去倒推等于往库里写一个没人做过的声明；旧版本就是「没有主题」。
- **主题删除会清掉历史版本上的标签行**。用户明确删掉一个主题时，历史版本不再挂这个标签；正文、版本与来源映射一概不动。这条取舍写在 `DeleteTopicUseCase` 的注释里。
- **生成失败可能留下一个 0 引用、`origin=model` 的主题**（主题解析发生在版本写入之前）。后台能看出「模型提了但没用上」，用户可以删掉它；要严格避免需要在同一事务里完成解析与写入，本轮没有做。
- **保留策略清理随想内容是软删除**：文本清空 + `DeletedAtUtc`，行留在库里，因为 `SourceReference` 指向它。默认 `-1`，即永不删除。**这里说的只是保留策略**；用户在数据管理页手动删除是物理删除，见 §15.1 与 A.23。
- **`diagnostics` 的日志缓冲是进程内的**：容器重建后日志从零开始；持久日志仍然只有容器 stdout。

**正文落点**：§3.1、§6.2、§8.2、§9.3、§12、§13、§15.1。回归方式：当轮全量自动化测试、`tools/deploy/verify-instance.ps1` 在真实部署实例上的 25 项自检，以及 MuMu 模拟器上的完整链路手工验收。当前测试基线以仓库 README 的「从源码构建与开发」一节为准。

### A.19 管理端与 Compose 重做

**问题**：A.18 把能力搬回后台，却仍把版本编辑、来源核验、文件差异、目标管理和发布动作挤在两个页面里；模型页的「测试连接」没有使用当前输入的配置，甚至可能在没有真正请求候选端点时显示可达。部署仍把状态拆成旧命名卷，稿件目录与 Hexo 模板也缺少一个清晰的配置入口。实际使用中还暴露了设备配对按钮因 Razor 属性表达式错误而永久禁用，以及来源检查在服务商已发响应头但不结束正文时无限等待的问题。

**定案**：按操作者的任务重划边界，而不是沿用旧页面布局。

- **发布设置**只保留两类动作及其配置：立即/定时生成、草稿输出目录；立即/定时正式发布、自动发布开关与执行窗口、正式稿目录；另提供 Hexo front matter 模板。生成成功写 `draft: true` 草稿，正式发布写 `draft: false`。
- **内容管理**只负责稿件库：按全部/未发布/已发布筛选，搜索、阅读、删除，并为每篇稿件分配一个或多个主题（第一个为主主题）。主题库允许用户添加和删除；模型只能添加；仍有当前稿件使用时拒绝删除。
- **稿件删除是领域动作**：清除数据库中的版本和发布记录，以内容日墓碑阻止调度器复生；磁盘上的 Markdown 可能已经由用户修改，因此保留不删。
- **模型设置**不出现 Secret 名输入框。新实例文章生成默认 DeepSeek；候选连接探测使用页面当前 Base URL、模型名与 API Key 发起一次最小的真实模型调用，只有实际模型成功响应才显示可用。
- **来源检查**继续作为发布前置条件，但不再把复杂核验工作流塞回内容管理。用户点击发布即构成对当前工作版本的明确确认；检查未完成时稳定返回 `reflection.confirm.source_check_pending`。模型 HTTP 超时覆盖响应头与响应体。
- **Compose**只映射用户明确指定的配置目录与数据目录。稿件全部位于数据目录，凭据与登录密钥位于配置目录；实例重置必须是单独、显式、可审计的脚本动作。

**代价与兼容**：旧的版本/来源/文件差异用例与 API 不为本轮强制删除，以免破坏历史数据与备份兼容，但不再出现在发布设置和内容管理的主流程中。旧命名卷只在部署脚本首次迁移时读取；新 Compose 不再挂载它们。删除墓碑新增迁移 `0009_deleted_reflections`，旧数据无需回填。

**正文落点**：§1、§3.1、§5、§6.2、§8.1、§8.4、§11、§14、§15.3、§18。回归方式：全量自动化测试（当前 553 项）、Docker Compose 重新构建与健康检查、管理端桌面/窄屏检查，以及 Android 配对回归。

### A.20 转写协议、每日唯一正式稿与风险提示收敛

**问题**：模型测试曾只探测通用端点，因此模型名或实际调用协议错误也会显示可达；转写实现把所有模型都当成 Whisper multipart 接口，导致配置 `paraformer-v2` 后真实录音稳定返回 404。另一方面，同一天重新生成并发布后旧稿仍保留为「已发布」，正式稿目录会出现多份同日文章。HTTP 风险提示还在登录后与手机多个页面重复出现，挤占了真正的操作提示。

**定案**：模型测试必须调用实际能力端点；Whisper 与 Qwen ASR 分别使用各自协议，拒绝需要公网音频 URL 的 Paraformer 文件转写配置。同一天的新正式稿取代旧稿，旧文件仅在哈希未变化时安全删除。明文 HTTP 风险集中在管理端登录页说明并要求确认，登录后与手机端不再重复展示。界面错误使用用户可执行的中文说明，不直接显示内部错误码。

**正文落点**：§8.1、§8.2、§9.3、§10.3、§11.1。回归方式：模型端点契约测试、录音上传集成测试、同日二次生成发布集成测试、管理端桌面/窄屏视觉检查与 Android 模拟器验收。

### A.21 已发布稿的显式替换与未发布提醒

**问题**：同一天已有正式稿后再生成新稿，生成和确认都不应被解释成“同意撤下旧稿”；否则定时器可能先于用户点击发布而替换内容。反过来，到了发布时间完全静默也会让新稿一直被遗忘。

**定案**：重新生成只产生新的未发布工作稿，旧正式稿继续保留；即使新稿已确认，定时器也不得自动替换。到发布时间后，使用“新草稿待处理”通知开关给当前版本发送一次未发布提醒，之后不重复催促。只有用户点击「发布稿件」才安全删除未被外部修改的旧文件并把旧记录标为 `Superseded`。若用户在未发布的情况下再次生成，上一份替代稿退出可见版本槽，最新稿成为工作稿。

跨日不会让替代稿失去操作入口：内容管理对“历史内容日 + 当前工作稿未发布 + 该日存在旧正式稿”的组合显示「继续发布」。动作需要二次确认，沿用当前版本的来源检查与人工发布流程，并仍以原内容日写入和替换文件；它不是补跑自动发布。

**正文落点**：§6.4、§11.1、§12。回归方式：领域版本轮换测试、真实 SQLite/Markdown/任务队列的定时提醒测试，以及管理端发布闭环集成测试。

### A.22 转写配置收敛为四参数

**问题**：上一版为了适配不同厂商，在语音设置中暴露了自动识别、语言、ITN、热词表、说话人区分等参数，并按模型名前缀选择协议。这让配置结果依赖隐藏规则，也无法可靠接入名称不同但协议相同的模型。

**定案**：用户只提供 Base URL、API Key、API 类型和模型名。API 类型只能是 `openai_transcription`、`openai_chat_audio`、`dashscope_async`，实现只按这个字段分派，模型名原样发送，所有接口路径只相对用户 Base URL 构造。DashScope 异步实现内部封装任务提交、轮询与结果读取；当前输入没有公网音频 URL 时在发送请求前明确失败。

**正文落点**：§8.1、§8.2。回归方式：协议请求契约测试、异步任务轮询测试、模型设置 API 往返测试及录音上传端到端测试。

### A.23 手动删除输入与保留策略彻底分开

**问题**：数据管理页的「删除」一直走领域软删除：置 `DeletedAtUtc`、清空音频，行留在库里当墓碑。这带来三处别扭。用户按下「删除」时看到的是「已删除」，库里却还留着一条只有内部才看得见的记录，后台还得专门为它做一个「包含已删除」开关；`InputEntry.Delete` 与保留策略的 `PurgeContent` 都写 `DeletedAtUtc`，两个语义相反的动作共用一个状态，注释只能靠「注意这与另一个方法不同」来解释自己；手机端与后台列表还得各自记得过滤墓碑，忘一处就会让用户删掉的东西重新出现。

**备选与权衡**：

1. 保持软删除，只在界面上隐藏。改动最小，但「删掉了」与「还在库里」永久不一致，导出与备份里也仍会带上用户以为已经删掉的内容。
2. 手动删除改为物理删除，保留策略继续留墓碑。两个动作各自只做一件事；代价是同一张表里「行还在」不再等于「内容还在」，读代码的人必须分清状态是哪条路径留下的。
3. 保留策略也改成物理删除。表最干净，但 `SourceReference` 指向输入行，物理删除会让历史文章的来源映射悬空——这正是 §6.5 与 §17.1 要保住的东西，不可行。

**定案理由**：选 2。手动删除表达的是「这条不要了」，保留策略表达的是「这段内容到期了」，两者对来源映射的要求正好相反，本来就不该共用一条路径。物理删除在一个事务里先删该输入的 `source_reference` 再删 `input_entry`，主题关联与 Embedding 由外键级联清理（`0001`/`0003` 里本来就是 `ON DELETE CASCADE`，且连接始终开着 `PRAGMA foreign_keys=ON`）；已生成的文章正文与版本一律不改写，只是不再把已删除输入列为来源。保留策略不动，墓碑照旧，`includeDeleted` 仍然让运维能显式看到它们。

**已知代价**：删除顺序是「先删行、后删音频」。这是刻意的——行是事实来源，音频是它指向的 blob，唯一值得防的漂移是「活着的行指向一个已经没了的文件」；反过来留下的孤儿 blob 不可见、不影响任何读取，可以由清理任务回收，且音频仓库本身按契约是尽力而为的。领域层从此不再有「删掉整条记录」的转换：`DeletedAtUtc` 只由保留策略设置，`PurgeContent` 是到达该状态的唯一入口。

**正文落点**：§6.1、§10.3、§15.1、§17.1。回归方式：`InputDeletionTests`（来源关系归零、文章仍在）、`ContentRetentionTests`（墓碑默认不可见、显式请求可见、总数与分页口径一致）、`InputLoopTests`（删除后 `GET /api/inputs/{id}` 为 404，手写记录也有文字修订入口）。

### A.24 写作规范交给用户维护

**问题**：生成请求里一直带着一组写作设置，但它从来没有出口。`WritingSettings` 只有三档枚举长度（提示词里写死成「三四百字」「六七百字」「一千字以上」）、一个固定为 `plain` 的语气字符串、一个布尔人称，而且没有任何 API 或界面能改它——每次生成都走默认值。用户要的是：自己定篇幅（默认 300 字）、自己选人称（默认第一人称）、自己维护一份行文规范，并且能删掉默认那份自己写。

**备选与权衡**：

1. 把三档枚举换成更多档（短 / 中 / 长 / 超长）。改动最小，但用户真正想说的是「300 字」，枚举永远只是近似，而且每加一档都要改代码。
2. 只做三个结构化字段（字数、人称、一段自由文本的风格要求）。够用，但用户明确要求「可以删除默认的自己写」；一整段自由文本无法逐条增删，也没法把「用词禁区」这类彼此独立的规则分开维护。
3. 结构化字段 + 一份用户拥有的规范清单（本次选择）。字段负责必须无歧义的信息（篇幅、人称），清单负责风格与体例，逐条可改可删可加。

**定案理由**：选 3。篇幅和人称是模型最容易遵守、也最容易搞错的两件事，用结构化字段表达；其余要求彼此独立、取舍因人而异，用清单交给用户。默认清单给五条——行文风格、结构与段落、标题、开头与结尾、用词禁区——针对的是中文机器写作的典型毛病（结尾升华、连接词填充、套话与被用滥的流行词），而不是某种文学风格。**默认值只在从未配置过时种下**：用户把清单清空是一次明确的选择，读回来时必须仍为空，否则界面上的删除按钮等于没有用。

**已知代价，以及两处必须一起改的地方**：

- 系统规则原来写着「写一篇**第一人称**的每日随想」，而人称现在是用户设置。若不改，系统规则会压掉用户的选择——配置存了却不生效，正是最难发现的那种错。因此人称只能由写作规范表达，系统规则不再提人称；这条不变量由提示词层的测试钉住。
- 版本里存的 settings JSON 换了形状。旧的 blob 会被反序列化成「没有字数、没有规则」的空壳，不能当成有效规范；读取时以「目标字数不是正数」判定为不可用并退回默认值。这条判据同时覆盖以后的下一次形状变更。
- 规范清单进提示词的位置从素材之后改到素材**之前**：这些是成文要求，模型先读到才能按它组织素材，而不是写完之后再套一层风格。

**正文落点**：§8.4、§11.1、§11.2。回归方式：领域校验测试、设置表往返测试（含「清空保持为空」与「读不懂退回默认」）、提示词测试（规范在素材之前、系统规则不提人称、空清单不补默认条目）、内容设置 API 往返测试，以及发布设置页的渲染断言。

### A.25 自动公开发布开关不再要求重新输入密码

**问题**：§11.1 原定「开启与关闭自动发布都要求管理员重新输入密码」。实际使用时这条要求的收益接近于零：能打开这个页面的人，已经是以本实例**唯一**管理员身份登录的会话（§4.1 不存在多用户），再输一遍刚刚用来登录的同一个密码，并没有引入第二个身份或第二条信道。代价却是真实的——它把一次勾选变成「输密码 → 保存」两步，于是用户倾向于让开关停在默认状态，而不是按需开关。

**备选与权衡**：

1. 保持现状（每次改动都要密码）。理论上的好处是「有人走开时，屏幕前的另一个人不能顺手打开」；但那个人在同一台已登录的浏览器上本来就能直接点「立即发布」并确认，也能改输出目录，单给自动发布加锁并不能控制住这个场景。
2. 改成前端二次确认弹窗，服务端不要密码。比密码轻，但在真正需要它的时候（用户自己一个人在用）只是多点一次，而且服务端不再有任何可验证的东西。
3. 去掉重新验证，保留管理员专属路由与审计记录（本次选择）。

**定案理由**：选 3。这个开关的保护来自两处，且都不依赖密码：**路由是管理员专属的**（设备令牌根本到不了这条路由，§11.1 与集成测试都钉着这一点），以及**改动被服务端记录为「谁在什么时候开的」**（`AutomaticPublishEnabledBy` / `AutomaticPublishEnabledAtUtc`，由服务端读账号写入，不采信请求体里的名字）。去掉的只是「把同一个身份再验证一遍」，权限边界与可追溯性都没有削弱。风险提示保留在界面上，并且写得更具体——它现在要独自承担告知责任（原来那句只讲「不会绕过内容核验」，没说清打开之后实例会自己写出 `draft: false` 的文件）。

**已知代价**：在一台已登录且无人看管的机器上，顺手勾选这个开关不再有额外阻力。这与同一台机器上可以顺手点「立即发布」是同一类风险；本轮的判断是，与其给其中一个动作加一道挡不住什么的闸门，不如把风险提示写到说清后果。日后若要真正控制这个场景，正确方向是会话超时或对管理端整体要求重新验证，而不是只锁这一个开关。

**正文落点**：§11.1。回归方式：集成测试确认「设备令牌被拒（403/401）」与「管理员只带 `enabled` 就能开与关，且记录操作者与时刻」；`SetAutomaticPublishRequest` 已去掉 `CurrentPassword`，`publish.automatic.password_rejected` 这个错误码随之删除。

### A.26 部署形态：一份 compose + 一个 APK

**问题**：A.19 之后，部署仍然只有一条路径——克隆仓库 → 复制 `deploy/.env` → 手工 `mkdir` 两个绝对目录并 `chown -R 1654:1654` → 复制 `deploy/secrets.example` 并填四个文件 → `docker compose --env-file deploy/.env -f deploy/compose.yaml up -d --build`。对写代码的人来说这没问题，但它把四件与「用起来」无关的事强加给新用户：要有源码、要有构建环境（拉 2GB 的 SDK 镜像现编译）、要理解 uid 1654 意味着什么、要凑齐四个密钥文件。实际后果有三条：

1. **漏建目录或漏 chown 会失败，而且失败得很不像权限问题**：`create_host_path: false` 让路径写错时直接拒绝启动；而 Secret 文件权限是 600、属主是宿主机用户时，容器里的 uid 1654 读不到——文件就在那里、名字也对，可每条模型调用都报 `transcription.secret_missing`（这条真踩过，见 [`CHANGELOG.md`](../CHANGELOG.md) 的缺陷记录）。
2. **`.env` 与四个 `secrets.file` 是硬性依赖**：前者用 `${VAR:?}` 让「不写 `.env`」变成硬错误，后者少一个容器就起不来——尽管密钥本来就可以在管理页里填（解析顺序是「管理页 → Secret 文件 → 环境变量」，且目录不存在只是返回 `null`，`FileSecretStore` 早就容得下空目录）。
3. **端口是两个变量，还能从页面改其中一个**：宿主机映射与容器内监听各一个，管理页又能改容器内的那个；改完映射就指向没人监听的端口——新手最容易把自己锁在门外的一步。

**备选与权衡**：

1. 维持现状，只把文档写得更细。改动为零，但「新用户」这条路依然是「照着七条命令，把每一件与产品无关的事都做对」。
2. compose 简化成「默认命名卷 + 无 `.env` + 无 Secret 文件」，但仍要求克隆源码本地构建。解决了 ②与 ③ 的一半，没解决「要有源码与构建环境」。
3. 发布多架构镜像 + 自足的单文件 compose + 入口脚本纠正属主后降权 + 容器部署独占端口 + 初始密码可由部署配置给出（本次选择）。

**定案理由**：选 3。判断标准是「一个新用户要做的动作里，有多少是产品本身要求他理解的」。要让服务起来，他真正需要决定的只有三件事：**放哪儿**（数据目录与配置目录）、**从哪个端口进**、**密码怎么给**。其余都应该有默认值或者干脆不发生。具体做法：

- 镜像发布到 `ghcr.io/nero-umu/dailymusings`（linux/amd64 与 linux/arm64，NAS 与树莓派要能装），Release 页同时附上签名 APK 与 SHA-256。
- `compose.yaml` 保持到「一眼看完」的长度：参数内联注释、与镜像 `ENV` 重复的变量一律不写（`ASPNETCORE_*`、`Storage__*` 都在镜像里）、健康检查搬进镜像的 `HEALTHCHECK`，只留端口、两个目录与三个真正需要用户决定的开关。默认落到 compose 同级的 `./data` 与 `./config`（看得见、好备份），具名卷作为替代写法写在注释里。
- 四个 `secrets.file` 换成**可选的目录挂载**，彻底消灭「少一个文件起不来」。
- 容器以 root 起步只为纠正两个挂载点的属主，随后 `setpriv` 降权到 uid 1654；只在属主不对时才递归 chown，所以第二次启动只是一次 `stat`。这条同时替新用户省掉了 `sudo mkdir` + `sudo chown -R`。
- 容器部署设 `DM_LOCK_LISTENING_PORT=1`：`runtime.json` 里的端口覆盖被忽略（否则锁一开就可能把上一次留下的覆盖重新捡起来），管理页那一节改成只读说明，端口只有 `DM_PORT` 一处。
- 初始管理员密码可以由部署配置给出；不给就完全保持原样（随机生成 + 只在启动终端打印一次）。给了也**不回显到容器输出**——Docker 会长期保存容器日志，配置里的密码不该在里面出现第二遍。

**已知代价**：

- **应用镜像的默认标签是 `latest`**（新手路径不写版本号）。§5 里「基础镜像固定具体 tag、不用 latest」那条约束没有变（Dockerfile 的 `FROM` 仍是固定 tag）；要固定版本的部署写 `DM_IMAGE=ghcr.io/nero-umu/dailymusings:1.0.0`，Release 会同时给出语义化版本与 `latest`。
- **入口脚本让容器的 PID 1 在头几毫秒是 root**。被降到 uid 1654 的是服务进程（全部业务代码、模型调用与文件写入都在那里），但「镜像以 root 起步」本身是安全边界上的一次移动，写在这里以便日后追责。
- **容器部署下管理页不能再改监听端口**。这是有意的取舍：容器内改端口只会把映射指向没人监听的端口，而 `DM_PORT` 已经能改宿主机那一侧。真要换容器内端口只能手改 `compose.yaml` 的三处（`ASPNETCORE_URLS`、端口映射、健康检查）。
- **`DM_ADMIN_PASSWORD` 让初始密码离开「只打印一次」的单一路径**，落在部署文件里。不回显到容器输出，但它在 `compose.yaml` / `.env` 里是可读的；不设它时行为与从前一致。首次登录仍然强制改账号名与密码（§10.1 未变）。
- **现有部署的迁移成本**：`deploy/.env` 的键名从 `DAILYMUSINGS_CONFIG_DIR` / `DAILYMUSINGS_DATA_DIR` / `DAILYMUSINGS_INTERNAL_PORT` 收敛为 `DM_CONFIG_DIR` / `DM_DATA_DIR` / `DM_PORT`；`tools/deploy/deploy.ps1` 仍会读一次旧键再回退到默认值，避免把已有实例指到空目录。
- **本轮有一部分没有在本机验证**：开发机上没有 Docker，所以 compose 的解析、镜像构建、入口脚本的降权、绑定挂载的属主纠正、多架构推送与 APK 构建，全部只在 CI 的 `compose-smoke` 与 `release` 作业里跑。在这些作业第一次真的跑通之前，「一份 compose 就能起」这句话只有代码与测试支撑，没有实测——按本项目的规矩，这一条必须如实说明，不能算已完成验证。

**正文落点**：§3.1、§5、§8.1、§10.1、§15.2、§15.3、§18。回归方式：`DeploymentBootstrapTests`（部署配置的初始密码被采用且不回显、不合规的值被明确报告并回退到随机生成）、`InstanceSettingsApiTests`（锁定时报告 `locked` 并拒绝写入、磁盘上残留的覆盖被忽略）、`RuntimeAndInstanceSettingsTests`（锁定使覆盖文件失效、非 `1` 的值不构成锁定）、`AdminSurfaceTests`（锁定时系统设置页渲染只读说明且不再有保存/清除按钮），以及 CI 的 compose smoke：用仓库根的 `compose.yaml` 起一次零配置实例，再按绑定挂载起第二次，并核对两个目录的属主已经是 1654。

### A.27 凭据只能从管理页填（删除 Docker Secrets 与环境变量两条路）

**问题**：到 A.26 为止，一把密钥有三个可能来源——管理页填的加密存储、挂到 `/run/secrets` 的文件、`DAILYMUSINGS_SECRET_<名字>` 环境变量，顺序如上。这三条路同时存在带来四个问题：

1. **承诺不成立**：§10.4 说「密钥不外流」，但另外两条路要求密钥以**明文**躺在宿主机上（还要 `chmod 644` 才能被容器读到），并且会出现在 `docker inspect` 的输出里。一个「安全」的说法被它自己的部署方式否掉了。
2. **排查代价高**：密钥「有没有、从哪来」变成三个来源的组合，页面得显示「来源」；而最常见的故障恰恰是文件权限（600 的文件、容器读不到，报的却是 `secret_missing`，看起来像没配）。
3. **状态难言之**：「清除已保存的密码」写下一条空记录，是为了压住下面那层文件——用户清掉的密码会被文件「复活」。多层来源让「清掉」这件事需要解释。
4. **部署面被迫变复杂**：compose 要留一行注释掉的 secrets 挂载、要有 `deploy/secrets.example/`、要解释四个固定文件名与权限；验收脚本也要靠 `sed`/`awk` 去打开那一行。

**备选与权衡**：

1. 保留三条路，只把文档里的措辞改严（「不推荐用文件」）。改动为零，但第 1 条的矛盾还在，且每条路都要继续维护与解释。
2. 只删环境变量，保留文件（Docker Secrets 是业界惯例）。惯例本身不解决明文落盘与 `docker inspect`。
3. **只留管理页一条路**（本次选择）：删掉文件与环境变量两个来源，`ISecretStore` 只剩加密存储一个实现，`Storage:SecretsPath`、`deploy/secrets.example/`、界面上的「密钥来源」一起消失。

**定案理由**：选 3，判断标准是「这个产品要不要为『部署自动化注入密钥』这个场景付出『密钥明文躺在服务器上』的代价」。这个产品的用户是**一个人**，他会登录管理页；而把密钥搬进部署配置的人本来就有能力在页面里粘贴一次。留一条明文的路，等于把「图省事」变成默认选项。删掉之后有三件事同时变简单：**密钥只有一个入口**（页面），**状态的表达只剩两种**（`ui` / `none`），**部署文件里彻底没有凭据**（compose 与 `.env` 都可以随便给人看）。这不是削弱 §10.4，而是把它从一句承诺变成代码里唯一可能的那条路径——`SecretSource` 枚举只剩 `Ui` 与 `None`，写不出来的东西就是不存在的东西。

**已知代价**：

- **不能用外部密钥管理系统注入**（Vault、K8s Secret、CI 变量）。要支持就得改回多来源；本项目的单实例、单人使用场景里，这个代价被明确接受。
- **凭据随配置目录存亡**：清空配置目录（`reset-instance.ps1`）或删掉密钥环之后，模型与 SMTP 的凭据要重新在页面上填一遍。这是刻意的——凭据不是内容，备份只带内容。
- **运维脚本要跟着改**：验收脚本原本靠往挂载目录里放文件来供密钥，现在改为登录管理页调用 `PATCH /api/system/model-endpoints/<service>`（写 `apiKey`）与 `PATCH /api/system/smtp-settings`（写 `password`）种进去，也就是**走操作员那条路**。
- **没有迁移**：这一版不读取旧的文件/环境变量来源，也不做「首次读到就搬进加密存储」的兼容。项目尚无使用者（用户明确确认），因此选择直接删干净。

**正文落点**：§3.2、§10.4、§15.2、§18。回归方式：`SecurityTests.A_secret_can_only_come_from_the_admin_pages_encrypted_store`（挂载文件与环境变量都必须**读不到**，而页面的加密存储照常工作）、`SecurityTests.A_secret_name_cannot_escape_the_credential_directory`（名字仍然不能带路径）、`SmtpUiPasswordTests`（清除之后没有任何东西可以被复活、环境变量不构成密码）、`InstanceDataTests.No_export_or_backup_carries_a_secret`（导出与备份都不含页面保存的凭据，也不提 `ui-secrets`）。

### A.28 篇幅改为区间加公差

**问题**：写作规范里篇幅一直是一个**目标值**（默认 300 字，提示词写「约 300 字，允许上下浮动两成」）。实际写作里每天的素材量差别很大：只有三句话的一天，模型被要求写满 300 字，只能靠形容词和升华凑；素材很密的一天又被 300 字截断。用户提出的诉求很具体：**最少与最多由自己设**（默认 50 与 300），并有**一个可选公差**，让模型按素材多少有一点弹性（默认 20 字）。

**备选与权衡**：

1. 保留单一目标值，把写死的「浮动两成」改成用户可调的百分比。解决了弹性，但「两成」这种相对量在 50 字的短篇上只有 10 个字、在 800 字的长篇上有 160 个，用户很难预期。
2. 三档枚举（短 / 中 / 长）。最容易实现，但把「篇幅」这种本来连续的判断压成三档，用户既说不出 200 字和 260 字的区别，也无法表达「素材多就写长些」。
3. **区间 + 可选公差**（本次选择）：最少与最多是硬边界，公差是允许越界的字数，0 = 严格。

**定案理由**：选 3。篇幅是**区间需求**而不是点需求——说「50 到 300 字」比说「300 字左右」更接近人的判断；公差则把「素材多少决定」这件事显式化，并且它天然回答「写不够怎么办」：公差大于 0 时提示词给出 `最少−公差` 与 `最多+公差` 两个数字，让模型知道可以短到哪、长到哪，而不是自己猜。默认 50 / 300 / 20 让开箱状态立刻可用；关掉公差就是把区间说死。校验放在领域里（`WritingSettings.Validate`）：两个数各自在 1..5000 内、**最少必须小于最多**、公差在 0..500 内。旧键 `writing.targetCharacters` 变成**只读回退**——读到它就当最多字数，所以已经存过 300 的实例开箱就是「最少 50、最多 300」，不会被打回默认。

**已知代价**：

- 区间与公差都是**提示词层面的约束**，产品不做字数硬裁：模型仍可能超出，超出后不自动重写，也不会因此失败。这与 A.24 的口径一致（规范是要求，不是后处理）。
- 提示词措辞变了（不再出现「约 N 字」）。任何依赖旧措辞的脚本或断言要跟着改；本轮已更新 `WritingSpecPromptTests`。
- 界面从「一个输入框」变成「两个数字 + 一个开关 + 一个数字」，多了一次判断成本。换来的是一句话能说清的界面：最少、最多、允不允许越界。

**正文落点**：§11.1、§11.2。回归方式：`WritingSettingsTests`（默认值、区间与公差的边界、`最少 ≥ 最多` 被拒、公差不会把下限压到 0 以下）、`WritingSpecSettingsTests`（往返 + 旧键回退成最多字数）、`WritingSpecPromptTests`（公差开启时给出 `最少−公差` / `最多+公差`，关闭时把范围说死）、`AdminSurfaceTests`（接口默认值与拒绝码、页面渲染「最少字数 / 最多字数 / 公差」）。

### A.29 发布时刻按「生成之后的那一次」解释

**问题**：2026-09-29 的线上实例暴露了一个把「自动发布」变成摆设的缺陷。用户在发布设置里把发布时刻设成 **23:16**（生成时刻是 23:00，即生成后 16 分钟），勾上自动发布，稿子也已确认，到点**什么都没发生**。根因有两层：

1. **时刻算法**：代码**无条件**按「内容日期 +1 天」计算发布时刻，于是「当晚 23:16 发布」被推到了 24 小时之后。默认组合（23:00 生成 / 次日 08:00 发布）恰好掩盖了这一点——它的确就该落在次日。
2. **零反馈**：页面只显示两个时间输入框，从不显示服务端算出的**具体日期时间**，也不说明「自动发布只处理已确认的稿件」。规则可以严，但用户看到的是沉默：一个勾选过的开关、一条已经确认的稿子、一个到点没有任何动静的夜晚。

**备选与权衡**：

1. 只改文案，把「每日自动发布时间」写成「次日 HH:mm」，算法不动。最省事，但「当晚发布」这种配置就永远表达不出来，而它恰恰是用户想要的。
2. 一律当天：默认的 08:00 会变成内容日当天的早上——生成（23:00）**之前**，站不住。
3. **按两个时刻的相对顺序解释**（本次选择）：发布时间晚于或等于生成时间 → 当天；否则 → 次日。

**定案理由**：选 3。「每日自动发布时间」在人看来就是**那一天的那个时刻**，唯一需要判断的是它在生成之前还是之后——用生成时刻做分界，既保住了默认的「次日早晨发布」，又让「生成完当晚就发」成为可表达的配置，而且一句话说得清。实现上把它收进 `ContentSettings.PublishSlotFor` 一处：调度入队、替代稿提醒、手动入队时的计划时刻三条路都用它，避免各自漂移（这三处原本都各自写着 `AddDays(1)`）。同时按 §11.1 的新要求，把算出的时刻与「只处理已确认稿件」的当前状态显示在发布设置页上——这一轮的教训是**沉默比严格更糟**。

**已知代价**：

- 把发布时间设成与生成时间相同（或更晚）意味着发布紧跟生成。若当天稿件始终没有确认，它会在执行窗口（默认 120 分钟）内等着，超窗转 `Expired` 并发通知（A.2 未变）。
- 跨日替代稿的提醒时刻跟着这条规则走，因此在「当晚发布」的配置下，历史内容日的提醒会比过去早一天。

**正文落点**：§11.1。回归方式：`PublishSlotTests`（早于生成 → 次日、晚于生成 → 当天、相等 → 当天三条边界）、`PublishingTests.A_publish_time_later_than_the_generation_time_publishes_the_same_evening`（照线上那组 23:00 / 23:16：23:05 不入队、23:17 入队且计划时刻是当天 23:16）、`PublishingTests.The_default_pair_still_publishes_the_next_morning`（默认组合仍落在次日 08:00）。

### A.30 APK 用一把固定的发布签名密钥

**问题**：2026-09-29 用户反馈「APK 升级时无法安装，手机提示已存在同样签名/签名不一致的应用」。查证（`apksigner verify --print-certs`）：

| 版本 | 签名证书 SHA-256 |
| --- | --- |
| v1.0.3 | `2c8c874490a5a3c9258d0c1012ea149000c484b6d680a7e28a2ff01b8add01fc` |
| v1.0.4 | `3d4370deee544997a21a7453b7e9caacf18db7a483ab03c4b7761cde3c333248` |
| v1.0.5 | `ecd15c9a36b7d5b84c55abd764792faaae5f11ded21bafd34f817c8f94adfda2` |

三份产物的证书主题都是 `CN=Android Debug, O=Android, C=US`——**每次都是不同的调试密钥**。根因：`release.yml` 只跑 `-t:SignAndroidPackage`，没有给任何密钥；GitHub 的 runner 每次都是全新的，.NET Android 于是在 `~/.android/debug.keystore` 自动生成一把调试密钥来签名。Android 规定「覆盖安装必须与已安装版本同一签名」，所以手机必然拒绝（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`），用户看到的提示就是这个。2026-09-29 之前手工构建并发布的版本同样是本机调试密钥，因此**每一版之间的升级都是断的**——只是之前没人跨版本升级过，缺陷一直没暴露。

**备选与权衡**：

1. 把密钥文件提交进版本库，CI 直接用。最省事，但仓库是公开的：私钥公开意味着任何人都能签出一份被用户手机接受的「更新」（同包名、同签名），这等于把「谁能给你推送新版本」交给了所有人。
2. 每次发布重新生成密钥，并要求用户卸载重装。把不可用当成常态，直接违背「下载 APK 装上就能用」这个交付承诺。
3. **密钥由维护者生成一次，私钥只存在 GitHub Secrets，CI 用仓库变量校验产物指纹**（本次选择）。

**定案理由**：选 3。签名密钥是这个应用**身份的一半**：它决定「谁能给已安装的实例发更新」。既然身份要长期稳定，密钥就必须长期稳定；既然仓库公开，它就不能进版本库。Secrets 是这两条的交点，代价是维护者要做一次手工设置（脚本把四值一条条打印出来，含 `gh` 命令）。同时补一道校验：**签名「没报错」不等于「用的是那把密钥」**——构建找不到密钥时会静默退回调试密钥，而那正是要杜绝的事，所以 `apk` 作业读回证书指纹与变量比对，不一致就让发布失败。缺密钥时也直接失败：与其再发出一份装不上的 APK，不如让发布停下来。

**已知代价**：

- **每台已安装旧版的手机需要卸载一次**（签名不能就地更换）。这是这次修复无法避免的一次性动作：旧版的私钥随 runner 一起消失了，无法用它再签一份新包。
- 维护者多了一次不可省的手工步骤，而且**密钥必须备份**：丢了它，所有已安装实例只能卸载重装；泄露了它，别人能签出被接受的假更新。两者都是「一次性、不可挽回」的错误。
- 本机（不走 CI）构建出来的 APK 仍是调试签名，装不上正式版；要用同一把密钥得显式传 `-p:AndroidSigningKeyStore` 等四个属性（脚本末尾会打印完整命令）。

**正文落点**：§5。回归方式：`release.yml` 的 `apk` 作业本身——缺密钥/缺变量即失败，且产物指纹与 `ANDROID_SIGNING_CERT_SHA256` 比对通过才会继续；本地验证方式是用生成的密钥构建一份 APK，`apksigner verify --print-certs` 得到的摘要应与脚本打印的指纹一字不差（2026-09-29 已实测：证书主题从 `CN=Android Debug` 变为 `CN=DailyMusings`，两份摘要一致）。

### A.31 磁盘布局按「内容 / 状态」切分

**问题**（2026-09-29，用户提出）：布局不合理，具体三条——①数据目录下应该只有 Markdown；②其他东西都进配置目录；③后台填的目录位置要**以映射目录为根**，例如映射了 `/srv/dailymusings/data:/var/lib/dailymusings`，想把稿件放在 `/srv/dailymusings/data/aaa/bbb/posts`，页面里就该填 `aaa/bbb/posts`，而不是只填 `posts`。

**旧布局的问题**（改之前）：

```text
<数据目录>/               # 容器内 /var/lib/dailymusings
  data/dailymusings.db    # 库
  media/                  # 录音
  exports/                # 可读导出
  backups/                # 备份包
  markdown/drafts|posts   # 稿件
<配置目录>/               # 容器内 /var/lib/dailymusings-config
  keys/                   # 密钥环 + 管理页凭据
  runtime.json
```

两个缺陷都不是「不好看」：

1. **要给人看的东西和实例内部状态混在一个目录里**。数据目录是「会整份同步走、会交给 Hexo」的那个——而它里面同时躺着数据库、录音、备份包和能签发登录 Cookie 的密钥环。用户按字面理解去做（把数据目录整个同步到别处），带走的就是全部状态。
2. **页面里填的路径，和宿主上看到的路径之间隔着一层只存在于代码里的 `markdown/`**。页面说「稿件发布目录：posts」，用户在宿主上找到的却是 `<数据目录>/markdown/posts`。没有任何办法从页面推断出文件到底会落在哪——这是「用户填什么就该在哪看到什么」的直接违背。

**备选与权衡**：

1. 布局不动，只在文档里说明「这个目录别乱同步」。风险不会因为写进文档而消失，而且第 2 条（多一层 `markdown/`）依然无解。
2. 拆成四个挂载点（media / backups / keys / markdown 各一个卷）。compose 从两个目录变成四个，用户仍要理解每个卷里是什么、哪个能同步；把一个「内容 vs 状态」的二分变成了四份作业。
3. **两个根按「内容 / 状态」切分**（本次选择）：数据目录只放 Markdown，且后台填的目录以它为根；SQLite、录音、导出、备份、密钥环、运行时覆盖全部进配置目录。

**定案理由**：选 3。它把「这份目录能不能给人看 / 能不能同步走」变成目录本身的性质，而不是需要记住的知识——数据目录可以整份交给 Hexo，配置目录可以整份进机密备份，两者都不需要再解释。第 3 条要求（填什么就在哪看到什么）随之为真：`aaa/bbb/posts` 直接拼在数据目录后面，中途不再有隐含层级。

**已知代价**：

- **破坏性变更，且不提供自动迁移**（用户 2026-09-29 明确同意）。升级后实例会在新位置建一份空库，旧内容不会自己出现；旧部署若要保留内容，需要在升级前把目录挪一次（`data/` `media/` `exports/` `backups/` 进配置目录，`markdown/` 下的子目录上移一层），README 与使用手册给了一次性命令。不写自动迁移是因为：跨两个挂载点搬库与媒体属于「错了就没有回头路」的操作，而这次迁移的形状完全取决于用户自己怎么摆目录——与其猜，不如给一条看得懂的命令。
- 备份包里的 Markdown 仍然是**从库里重新渲染**的（§15.2 的既有设计），不是照抄数据目录里那份。所以「数据目录可以随便同步」不会改变备份的内容，反过来，手动改过磁盘上的 Markdown 也不会进备份。
- 数据目录不再有任何子目录约定：`drafts` / `posts` 只是默认值，用户可以用任意深度（`aaa/bbb/posts`）。代价是实例不再能假设「Markdown 目录下只有稿件子目录」——所以它也不去遍历整棵 Markdown 根，备份与导出走库，而不是走磁盘遍历。

**正文落点**：§5（两个根的职责与相对路径规则）、§11.2（Markdown 目标的目录以数据目录为根）、§15.2（备份含什么）、README「部署参数」、`docs/使用手册.md` §3.3。回归方式：`A_nested_target_directory_is_created_directly_under_the_markdown_root`（填 `aaa/bbb/posts` 就落在 `<Markdown 根>/aaa/bbb/posts`，且整棵 Markdown 根下只有这一个文件）；目录契约由 `SecurityTests` 里遍历 `ManagedDirectories` 的测试覆盖；`InstancePaths` 的两个根在集成测试里由 `TestInstance.MarkdownRoot` / `DatabasePath` 统一解析，测试不再自行拼路径。

### A.32 界面文案约定

**问题**（2026-09-29，用户指出）：发布设置里出现了这样一段提示——

> 目录是\*\*相对于你映射给实例的数据目录\*\*的路径：映射了 /home/atri/data:/var/lib/dailymusings、这里填 aaa/bbb/posts，稿件就会写到宿主上的 /home/atri/data/aaa/bbb/posts。不能使用绝对路径或 ..。时间都是 Asia/Shanghai 时区的墙上时间；时区在系统设置中修改。

用户的问法是「为什么会出现下面这种话在最后的项目里」。这段是我在上一轮布局改动时写的，暴露了三件事，而且都不是笔误：

1. **把对话里的具体例子抄进了产品**：`/home/atri/data` 和 `atri` 来自需求里那句话，产品文案里出现某个人名，用户第一反应是「这是谁」。
2. **`**加粗**` 是 Markdown，Razor 不渲染**，页面上会原样显示两个星号（全文扫过 `.razor` / `.xaml`，只有这一处）。
3. **一句话塞了六件事**（规则＋映射示例＋填写示例＋落点示例＋禁止项＋时区），那是文档段落，不是字段提示。

顺着这条线索把全项目扫了一遍，同一个毛病还有三类：

- **界面里写设计理由**（7 处）：保留策略里「…是两个不同的承诺，所以是两个设置」、通知页「邮件功能由三件事共同决定：①…任何一条不满足…也不会报错，因为「不发」本来就是一个合法配置」、系统页「音频清理…（它比内容清理便宜，跑在前面）」与「完成后原子切换」、数据页「分页由服务端做…（分页接口不接受类型与状态参数）」、发布页「勾选即生效，保存后立即按新开关执行」。
- **中英混杂**：63 条英文消息会经由 `UseCaseException` / `DomainException` 弹到中文界面上。逐条分过之后，其中约 39 条是用户真能踩到的（改密码、配对码、保留天数、发布窗口、主题合并、版本切换、模板缺 `{body}`…），其余是**领域不变量**——正常操作永远碰不到，是给开发者看的断言。
- **客户端文案啰嗦**：地址说明一句里塞了三条操作指示；本地存储说明的「上传成功后也不会被删掉」是冗余重申。

**备选与权衡**：

1. 只改用户指出的那一条。成本最低，但同一个毛病在 7 个地方复制着，改一条等于承认其余 6 条合格。
2. 全改成英文或全改成中文。**不选**：界面语言是中文，领域断言是开发者的语言，两者混在一起才是问题，把断言也译成中文只会让调试更绕。
3. **按「界面只说做什么」重写，并把约定写成本文档的一节**（§21，本次选择）。

**定案理由**：选 3。这些文案的共同病因是我在**把界面当文档写**——规则、理由、示例都往里塞，示例还常常直接从对话里抄。只改文字治不了这个习惯，所以把它变成四条可执行、可自查的硬约定（§21），并且明确「理由写进 CHANGELOG 与附录」。区分「面向用户的报错」与「领域不变量」也是同一条思路：前者要让人照着做，后者是断言，翻译它反而是误导。

**已知代价**：界面短了，一部分上下文没了——例如「为什么录音和内容是两个保留设置」现在只写在 §15.2 与附录里，页面上不再有。这是刻意的取舍：页面负责让人把事做对，文档负责解释为什么；用户不需要在表单里读设计理由。另外 `DomainException` 的英文消息仍会出现在运行日志里，排查时要知道那是有意保留的。

**正文落点**：§21。本轮改动分布：`Publishing.razor`（4 处）、`SystemPage.razor`（4 处）、`NotificationsPage.razor`（1 处）、`DataPage.razor`（1 处）、`Client/Pages/SettingsPage.xaml`（3 处），加上 39 条报错文案与 12 处示例路径（代码注释、README、使用手册、快速部署、发布校验值）。回归方式：构建 + 全量测试（文案改动不该改变任何行为，若测试因此红了，说明它在断言文案而不是行为——那也是该修的信号）。

### A.33 勾选自动公开即授权自动发布

> **本条目的一半已被 A.36 取代**：下面「不替用户写确认（选项 3）」那一半，在用户实测后按他的要求改成了「**自动发布成功即视为用户认可**」。仍然有效的是另一半——**发布门槛按目标区分**（勾了的目标不要求先确认，没勾的保持原规则）。原文保留，以便看清当时的取舍。

**问题**（2026-09-30，用户提出）：用户勾了「允许自动公开发布」，到点却什么都没发生。查证后原因是产品规则本身：发布要求稿件处于 `已确认` 状态，而**确认是一个必须显式触发的动作**（`POST /api/reflections/{date}/confirm`，还要等来源核查结束、有疑问句时显式接受），可管理页与 App 里**都没有一个独立的「确认」按钮**——确认只在「手动发布」时作为副作用发生。于是想靠自动发布的用户卡在中间：23:00 自动生成，23:16 自动发布时稿件仍未确认，什么都不会发生，只收到一封「到点还没确认」的提醒。用户的要求很直接：**勾上就该到点发布当天生成了的稿件**。

**备选与权衡**：

1. 加一个「确认稿件」按钮，让用户自己去点。这能修好流程，但没有满足用户的要求——他要的是「勾上即自动」，而不是「勾上之后还得每天点一次」。
2. 勾上自动公开时到点**自动确认再发布**。状态最干净（已确认 + 已发布），但代价是：确认会**启动录音/内容的保留计时**（保留设 0 天时等于发出即删），还会让这一天不再被自动重新生成——这两件事用户都没要求，而它们都由一个勾选悄悄触发。
3. **勾上自动公开 = 授权自动发布当天的工作稿，但不写确认状态**（本次选择）。发布门槛按目标区分：勾了的目标不要求确认；没勾的目标保持原规则。

**定案理由**：选 3。它正好实现用户要的那句话，同时把「确认」留在它原本的含义上——**人核验过**。自动发布不替用户签名，所以页面会如实显示「已公开但未确认」，而保留计时与重新生成策略也不被一个勾选改变。区分「勾了 / 没勾」而不是全局放宽，是因为 §11.1 的「默认只生成私人草稿，由你核验后才发布」对**没打算自动公开**的用户仍然成立，他们不该被这次改动牵连。

**已知代价**：

- **勾了自动公开且从不确认的实例，保留策略不会启动**——这是 3 与 2 的直接取舍，用户在下一轮追问时选择了修正它，见 A.35。
- 被自动发布的稿件在页面上仍是「未确认」状态，所以「已确认」这个徽章不再等于「已发布」。两者都能在页面上看到（发布状态与稿件状态是两个角标）。
- 自动发布仍然**不会替换已经公开的文件**：重新生成后的新版本照旧需要人手动发布，自动动作只发提醒。这一条没有被本次改动放松。

**正文落点**：§11.1。实现：`RequestPublicationUseCase` 按 `manual` 与目标的 `AutomaticPublishEnabled` 选择版本（手动 = 已确认那一版；自动 + 勾选 = 当天工作稿；自动 + 未勾选 = 已确认那一版）；`SchedulePublicationsUseCase` 的候选从「已确认的日期」放宽为「有工作稿的日期」，并按目标逐条判断；`SupersedeStaleAsync` 的「还作数」判据也一并修正——否则刚排上的自动发布会立刻被作废。回归测试：`An_opted_in_target_publishes_the_day_that_was_only_generated`、`A_target_without_the_opt_in_still_waits_for_a_confirmed_draft`，以及原有的 `New_material_invalidates_a_pending_publication`（确认过的稿在新增素材后仍然失效）。

### A.34 邮件可以带稿件正文

**问题**（2026-09-30，用户提出）：希望「生成稿件」与「发布稿件」的提醒邮件里**带上稿件全文**，并能在通知管理里开关。

**为什么这是一个需要定案的改动**：§12 原先写得非常明确——「每封信只说发生了什么并指向实例，**任何一封都不带用户写的东西**；邮件默认走明文，草稿是这个产品最私密的东西，自动往收件箱塞一份比塞一句『请到实例里看』更糟」。这不是遗漏，是一条有理由的硬规则；用户的要求是**推翻它**。

**备选与权衡**：

1. 直接照做，默认就带正文。最省事，但等于把一个私密副本默认送进邮件服务商——对一个自称「本地优先、内容不外流」的产品，这是最不该默认打开的事。
2. 拒绝并坚持原规则。用户的场景是真实的（手机上直接读信，不必登录实例），拒绝等于把「方便」判给了设计洁癖。
3. **加一个内容开关，默认关闭**（本次选择）：通知管理里提供「邮件里附上稿件正文」，打开后才带；界面同时写明「邮件默认走明文，打开等于把稿件复制一份到邮箱」。

**定案理由**：选 3。它把「值不值得」交回给使用者，而默认值仍然是安全的那一侧；同时保留原规则里真正重要的部分——**失败与超时的信永远不带正文**（它们只需要原因与错误码），而带正文的只有「草稿就绪」与「导出成功 / 已上传草稿」两类。这个开关刻意**不是事件开关**：事件决定「发不发」，它决定「发的时候带不带正文」，两件事混在一个列表里会让人以为打开它才会收到信。

**已知代价**：打开之后，正文会留存在邮箱与邮件服务商那里，且不受实例的保留策略管辖（删了实例里的内容，邮箱里的副本还在）。这一点写在界面提示里，也写在这里。另外邮件仍是**纯文本**：正文以 Markdown 原文出现（不含 front matter），因此信里会看到 `#`、`**` 这类标记。

**正文落点**：§12。实现：`NotificationSettingKeys.IncludeContent`（`notification.includeContent`，可用 `Notification__IncludeContent=true` 预置）+ `NotificationSettings.IncludeContent` + `NotificationComposer` 的 `content` 参数与 `AppendContent`；正文由调用点提供（生成路径取 `version.Body`，发布路径按 `publication.ReflectionVersionId` 取版本）。回归测试：`The_content_switch_puts_the_article_text_in_the_mail`，以及 `A_notification_is_sent_once_and_carries_no_draft_text`（把正文交进队列、开关关闭时信里仍然没有它）。

### A.35 保留计时从首次确认或首次公开发布起算

**问题**（2026-09-30，用户在 A.33 之后追问「自动发布之后，录音等自动删除就开始计时吗」）：按 A.33 的口径，自动发布不写确认，而保留策略的守卫是「这一天被确认过」。两者相加的后果是——**只靠自动发布、从不确认的实例永远不会清理**：用户把录音保留设成 30 天，却什么都删不掉，而页面上没有任何迹象说明原因（清理任务成功运行、候选天数为 0）。这正是 A.33 里记下的代价，用户明确选择修正它。

**备选与权衡**：

1. 保持「只认确认」。安全，但等于让一个配置项静默失效；「保留策略不生效」和「策略生效但没有到期内容」在界面上长得一模一样。
2. 自动发布时顺带写确认。能计时，但把「人核验过」这个含义污染掉了，而且确认还会冻结这一天的自动重新生成（A.33 已论证）。
3. **计时起点 = 首次确认与首次公开发布中较早的那个**（本次选择）。两个事件都意味着「这一天的文字已经定下来、录音不再需要留着核对」，谁先发生就以谁起算。

**定案理由**：选 3。它说的是实话：发出去了，核对的必要性就下降了，30 天后即可清理；没有伪造「已确认」。只算 **`Published`**（公开发布）而不算「上传草稿」：草稿不是「发出去了」，核对价值没有下降。起点没有新增持久字段，而是从 `publication` 表里取最早一次成功公开发布的完成时刻——发布记录本来就是这件事的唯一事实来源，再加一个字段只会多一处可能不一致的副本。

**已知代价**：手动发布与自动发布**都会**开始计时（这是有意的：手发同样意味着发出去了）。备份恢复后，计时起点跟着发布记录一起回来（发布记录在备份里）。如果某一天的发布记录被删除（内容日被删除时随之清理），它的计时起点会退回确认时间——那时这一天已经没有文章了，保留问题也随之消失。

**正文落点**：§15.1。实现：`IReflectionRepository.ListRetentionCandidatesAsync`（用一条 SQL 取「确认时刻 / 首次公开发布时刻」中较早的那个，替换原来的 `ListConfirmedBeforeAsync`）+ `AudioCleanupPolicy.IsCleanable` / `ContentCleanupPolicy.IsCleanable` 的参数由 `confirmedAtUtc` 改名为 `countdownFromUtc`（语义变了，名字必须跟着变）。回归测试：`A_publication_starts_the_retention_countdown_without_a_confirmation`（没有确认、只有公开发布 → 起点是发布时刻；窗口没到则不是候选）。

### A.36 自动发布成功即视为用户认可

**问题**（2026-09-30，用户在服务器上实测 A.33 之后）：勾了自动公开、也确认文件确实写进了 `posts`，但管理页「今天的稿件」**依然显示「待核验」**。用户的话是：「这里应该要默认生成后，用户没有管代表用户认可了稿件内容」。这是对 A.33 里那半个决定的直接否定——我当时选的是「不替用户写确认」，理由是确认意味着人核验过；用户要的语义是相反的：**没人管就等于认可**。两者都成立，区别只在产品想表达哪一件事，而这是使用者的决定。

**备选与权衡**：

1. 只改界面：把「待核验」在自动发布后显示成别的字。**不选**：状态是事实，文案改不掉事实——保留计时、重新生成策略、统计里的「已确认 N 篇」读的都是它。
2. 保持「不写确认」，让用户自己去点一次。**不选**：那正是 A.33 要解决的问题（没有那个按钮），而且用户每天都要点一次，「自动」两个字就没有意义了。
3. **公开发布成功即写确认**（本次选择）：勾选自动公开的目标，在**成功公开发布**那一刻把当天的工作稿确认为正式稿。

**定案理由**：选 3。它把「勾选自动公开」解释成一次**预先给出的授权**：你说了「到点自己发」，那么发出去这件事本身就代表你认可了这一版——否则产品等于要求用户每天在自动发布之前先手工签一次名，而正文又确实已经公开了，状态与实际不一致才是真正的坏味道。刻意**不走** `ConfirmReflectionUseCase`：那条路要求来源核查跑完、并要求显式接受无依据的句子，那是留给人的确认闸门；「没人管就等于认可」是另一种授权来源，把两者塞进同一条路只会让两边都说不清。

**已知代价**：

- 确认会启动 §15.1 的保留计时（A.35 之后即使不确认也有第二来源，所以这条不再改变结果），并让这一天不再被自动重新生成。用户接受了这个语义。
- 「已确认」不再等于「人看过」：在勾了自动公开的实例里，它等于「已经公开发布过」或「人确认过」。这一点只能靠附录与代码注释说清，界面上的徽章分不出两者。
- 只对**公开发布成功**生效：上传草稿（目标没勾自动公开）不算认可，失败与超时也不算。

**正文落点**：§11.1。实现：`RunPublicationUseCase` 在一次成功运行收尾处判断「结果是 Published + 触发者是 Automatic + 工作稿就是被发布的版本 + 尚未确认」→ `reflection.Confirm(...)` 并落库。回归测试：`An_opted_in_target_publishes_the_day_that_was_only_generated`（同一条测试在 A.33 时断言「**不**应变成已确认」，本轮把断言反过来——它正好是这次语义翻转的证据）。

### A.37 front matter 的两个时间

**问题**（2026-09-30，用户在服务器上看生成的文件）：`posts/` 里那份 Markdown 的 front matter 是

```yaml
date: 2026-09-30 00:00:00
updated: 2026-09-30 06:45:28
```

两个都不对。`date` 是**内容日期的午夜**（把「这些材料属于哪一天」当成了「这份稿子什么时候写的」），`updated` 是**按 UTC 打印的**——那一刻本地其实是 14:45:28，差的正是内容时区那 8 小时。用户的要求：两个都应该是生成时间、都要用配置的时区，而且它们**是两个不同的概念，不能共用一个值**。

**备选与权衡**：

1. 只把 `updated` 换成内容时区，保留 `date` 为内容日午夜。**不选**：用户明确说 `date` 那行也是错的。
2. 两个字段共用一个「生成时间」。**不选**：用户明确点出不能共用——重新生成会同时刷新两者，而编辑只该动 `updated`；共用一个值就等于把「这一版什么时候生成的」和「这一版最后一次改动的时刻」这两件事合并掉，将来想分开就再也分不开。
3. **两个字段、两个来源、同一个时区**（本次选择）：`date` = `ReflectionVersion.CreatedAtUtc`，`updated` = `EditedAtUtc ?? CreatedAtUtc`，两者都用 `TimeZoneInfo.ConvertTime(..., 内容时区)` 之后按 `yyyy-MM-dd HH:mm:ss` 渲染。

**定案理由**：选 3。`date` 与 `updated` 的**语义本来就不同**，只是普通情形下相等；把它们分别接到正确的来源上，既满足了「都用生成时间」（这一版的生成时刻就是它自己的时间），也让「编辑后 updated 前进、date 不动」这种情形自然成立。时区换算放在**域模型的工厂方法**里，并且把时区做成**必填参数**——原来的签名有一个可选的缺省路径，`updated` 就是这么悄悄变成 UTC 的。

**已知代价**：

- 文件名里的日期仍然是**内容日期**（`2026-09-30-标题.md`），与 front matter 的 `date` 不再一致。这是有意的：文件名回答「这些材料属于哪一天」，front matter 回答「这份稿子什么时候写出来的」。
- 内容时区变更（系统设置里改时区）之后重新生成的文件，时间会按新时区渲染；旧文件不动，直到下一次写出。
- `MarkdownDocument` 的字段由 `UpdatedAtUtc` 变成 `GeneratedAt` + `UpdatedAt`，构造它的地方都要显式给出时区（编译期就会拦住漏掉的地方——这正是把参数做成必填的目的）。

**正文落点**：§11.2。实现：`MarkdownDocument.From(version, contentDate, timeZone, isDraft)`（必填时区）+ `MarkdownTemplate` 的 `date`/`updated` 取值 + 四个调用点（草稿导出、正式发布、差异比对渲染、可读导出）都传 `settings.CreateCalendar().TimeZone.TimeZoneInfo`。回归测试：`The_front_matter_times_are_the_drafts_own_times_in_the_configured_zone`（两个时间都等于按内容时区换算后的生成时刻，且**不等于**内容日午夜），以及 `PublishingTests` 里那条按种子版本的创建时刻计算的断言。

### A.38 界面视觉改为 Apple（iOS 深色）风格

**问题**：管理页与手机端此前的配色是两套各自长出来的方案——管理页是浅色（背景 `#F5F7FA`、卡片 `#FFFFFF`、主色 `#3B82F6`），手机端是深色（背景 `#101418`、主色 `#4C9AFF`）。用户要求两处都改成更像苹果的设计风格。要定的是三件事：改成什么、改到哪一层为止、「改好了」怎么判定。

**备选与权衡**：

1. **只调色值**，其余不动。**不够**：苹果观感的大半来自间距、圆角、分组列表的排布与深色下的层级关系，不是把蓝换成系统蓝就成立。
2. **两个界面都改成浅色 iOS**（分组列表、大白底）。**不选**：`Colors.xaml` 里明确记着手机端是**有意做成深色**的——「在暗处单手用几秒钟，要紧的是文字比背景亮多少，而不是装饰色」。改成浅色会与这条已记录的理由正面冲突。
3. **引入前端框架或 UI 组件库**（Tailwind / Bootstrap / 第三方 MAUI UI 包）一次到位。**不选**：管理页现有结构是「一套令牌 + 语义化类名，页面只组合类、不写内联布局」，这正是能整体换肤的前提；引入框架等于重写骨架，与「只换皮肤」相反，也把这次改动从视觉风险变成行为风险。
4. **只做一套深色，两处都用 Apple 深色；颜色与形状收进令牌层；页面结构不动**（本次选择）。

**定案理由**：选 4。两处本来就都有令牌层——`admin.css` 一个 `:root` 加 159 处 `var(--)`，`Colors.xaml` 本身就是 MAUI 的令牌层——所以「改令牌即换肤」在结构上已经成立，不需要动骨架。手机端因此走 iOS 深色（`#000` / `#1C1C1E` / `#2C2C2E` 的层级、系统蓝 `#0A84FF`、inset grouped list、大标题、底部 tab），既拿到苹果感，又不动「暗处单手用」那条理由。只保留深色一套，把工作量与「两套主题不一致」的风险一起砍掉；回退能力由本地 git 历史提供，所以不并行保留旧皮肤。
