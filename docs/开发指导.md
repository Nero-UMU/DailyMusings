# 每日随想：开发指导

## 1. 文档目的

本文档用于指导“每日随想”自托管应用的设计、开发、测试和交付。它是当前 MVP 的实现基线；新增功能不得突破本文范围，除非先更新产品约束。

> 2026-09-16 已就地合并一批实现澄清（原文留白项，共 14 条），涉及目标框架、主题 ID 稳定性、稿件状态枚举、晚到输入定义、来源定位格式、检索降级、发布权限与执行窗口、音频保留策略、备份排除项、密钥环位置与恢复验证流程。**§1–§20 正文是唯一的约束来源**；各条的背景、备选方案与定案理由见文末附录 A，供追溯“为何这样定”。正文与附录若有出入，以正文为准。

## 2. 产品目标

“每日随想”面向会在日常生活中随时记录见闻、想法和思考的个人创作者。

用户通过 Android 或 Windows 客户端输入短语音或文字。服务端负责转写、主题识别、历史检索、每日随想生成、通知和发布。当天只要存在至少一条有效输入，就生成一篇随想；没有输入则不执行生成任务。

核心原则：

- 捕捉瞬间想法，而非会议录音或备忘录管理。
- 默认生成私人草稿，由用户核验后发布。
- 用户自行提供模型服务，项目不捆绑任何模型。
- 数据由用户自托管并可完整导出。
- AI 只能整理、重构和润色来源内容，不得故意补充不存在的事实。
- 模型无法提供绝对真实性保证，因此必须提供来源追溯和风险提示。

## 3. MVP 范围

### 3.1 必须包含

- 单用户 ASP.NET Core 服务端。
- Blazor 服务端管理页面。
- Android 与 Windows .NET MAUI 客户端。
- Linux Docker Compose 部署。
- 文字输入、短语音录制、离线队列和即时转写。
- 标签检索及可选的 Embedding 语义检索。
- 每日随想生成、历史主题引用、来源核验和三版本草稿。
- SMTP 邮件提醒。
- WordPress 草稿、手动公开及可选自动公开。
- 将 Hexo Markdown 写入用户指定的挂载目录。
- 设备配对、数据导出、备份恢复、日志和失败重试。

### 3.2 明确不包含

- 多用户、团队或公开注册。
- 图片输入和已有音频导入。
- 会议录音和长音频工作流。
- 任意历史日期重新生成。
- Git 自动提交或推送。
- 执行 `hexo generate`、`hexo deploy` 或用户自定义命令。
- Microsoft Store 或 Google Play 发布。
- 默认遥测。

```text
              ├── HTTP/HTTPS API ── ASP.NET Core 服务端
Windows MAUI ─┘                         │
                                       ├── SQLite
Blazor 管理页 ──────────────────────────┤
                                       ├── 音频与导出文件目录
                                       ├── OpenAI 兼容模型接口
                                       ├── SMTP
                                       └── WordPress REST API
```

### 4.1 职责划分

客户端负责：

- 录音、文字输入和本地离线队列。
- 时间线、日历、主题、草稿及任务状态展示。
- 修订转写、调整主题、编辑和重新生成允许处理的草稿。
- 发布操作及来源核验。
- 保存服务器引用和设备令牌，不保存模型或发布密钥。

服务端负责：

- 身份验证、设备配对和设备撤销。
- 音频接收、持久化、转写和重试。
- 主题识别、标签搜索、向量索引和历史检索。
- 每日调度、补跑、文章生成及事实来源检查。
- 草稿版本管理、Markdown 输出和 WordPress 发布。
- SMTP 通知、备份、恢复、数据导出和诊断日志。

管理网页负责：

- 管理员账号和密码。
- 模型、Embedding、SMTP、WordPress、Markdown 目标及内容时区配置。
- 设备配对、设备撤销和系统状态查看。
- 任务失败处理、索引重建、备份恢复及日志查看。
- 不承担主要的日常创作体验。

## 6. 核心领域模型

### 6.1 InputEntry

代表一条语音或文字输入。

关键字段：

- `Id`
- `SourceType`: `Voice` 或 `Text`
- `CreatedAtUtc`
- `CreatedOffsetMinutes`
- `ContentDate`: 按内容时区计算的自然日
- `AudioPath`、`AudioDuration`、`AudioDeletedAtUtc`
- `OriginalTranscript`
- `RevisedTranscript`
- `TranscriptionStatus`
- `AllowFutureRecall`
- `PrimaryTopicId`
- `SecondaryTopicIds`
- `DeletedAtUtc`

原始转写和用户修订稿必须分开保存。生成时优先使用修订稿，没有修订稿时使用原始转写。

音频保留策略见 §15.1；音频被清理后 `AudioPath` 置空，转写文本仍保留，输入记录本身不受影响。

### 6.2 Topic

- 支持重命名、合并和调整输入归属。
- 一条输入最多有一个主要主题，可有多个次要主题。
- MVP 不要求自动拆分主题。
- 删除主题不得删除原始输入。
- `Topic.Id` 稳定且不可变，重命名只改展示名、不改 ID。
- 合并只改归属，不删除被合并主题行：保留为 tombstone 并记录 `MergedIntoId`、`MergedAtUtc`。
- `SourceReference` 指向输入而非主题，因此主题的合并、重命名与删除都不得改变历史文章的来源映射。

### 6.3 Reflection

代表某一自然日的每日随想。

关键字段：

- `Id`
- `ContentDate`
- `Status`
- `GenerationReason`
- `LastStaleReason`（原 `IsStaleBecauseOfLateInput`，2026-09-16 定案降级为审计字段，不再作为状态依据）
- `InitialVersionId`
- `PreviousVersionId`
- `WorkingVersionId`
- `ConfirmedVersionId`
- `CreatedAtUtc`、`UpdatedAtUtc`

状态定义（2026-09-16 定案）：

```text
PendingInputs → Ready → Generating → ReviewRequired → Confirmed
                         │                 │
                         └── Failed       └── StaleByLateInput

Status ∈ { PendingInputs, Ready, Generating, ReviewRequired, Confirmed, Failed, StaleByLateInput }
```

`Failed` 指生成二阶段重试耗尽的**稿件态**，与 `ProcessingJob` 的任务态失败严格区分。`StaleByLateInput` 指当日已生成后又收到当日输入、等待补生成。唯一允许离开 `Confirmed` 的迁移是 `Confirmed → StaleByLateInput`。状态分组一律由服务端计算，客户端只负责展示。

### 6.4 ReflectionVersion

保存标题、摘要、正文、标签、分类建议、写作设置、模型信息、提示词版本和来源映射。

版本规则：

- 最初版本永久保留。
- 重新生成前，当前编辑版本转为上一版本。
- 新结果成为当前编辑版本。
- 不得静默覆盖用户手工编辑。
- 默认只维护“最初、上一、当前”三个版本位置。

### 6.5 SourceReference

把文章段落或句子关联到一个或多个输入记录，字段定义（2026-09-16 定案）：

- `ReflectionVersionId`：文章版本 ID。
- `BlockIndex`：版本正文内的段落序号，0 起。
- `CharStart`、`CharEnd`：段内半开字符区间。
- `QuoteHash`：被引用片段规范化后的哈希，用于检测定位漂移。
- `InputId`：输入 ID，可多个。
- `Relevance`、`Reason`：相关度与引用原因。
- `IsHistorical`：是否为历史材料。

客户端高亮时若 `QuoteHash` 与当前文本不匹配，判为定位漂移：降级为整段提示而非精确高亮，并告知用户该版本已被编辑。

来源信息默认仅在应用内展示，不自动写入公开文章。

### 6.6 ProcessingJob

所有转写、索引、生成、检查、通知和发布操作都应建模为可持久化任务，而不是仅存在于进程内存中。

任务类型至少包括：转写、Embedding 索引与重建、生成、无来源陈述检查、通知、发布、备份，以及音频清理（`AudioCleanup`）。

关键字段：

- `JobType`
- `TargetId`
- `Status`
- `AttemptCount`
- `ScheduledAtUtc`
- `StartedAtUtc`
- `CompletedAtUtc`
- `IdempotencyKey`
- `ErrorCode`
- `ErrorSummary`

### 6.7 PublishTarget 与 Publication

发布目标包括 WordPress 和 Markdown 两种类型。一个实例允许配置多个命名目标。一篇文章可以发布到多个目标，每个目标独立保存发布状态和远程文章 ID。

## 7. 时间与生成规则

- 内容时区在服务端配置，默认 `Asia/Shanghai`。
- 所有时间以 UTC 持久化，并记录输入创建时的时区偏移。
- 自然日按内容时区的 `00:00–23:59` 划分。
- 默认 23:00 生成，时间可配置。
- 当天无输入时不得创建空文章。
- 服务器停机或客户端离线后，按每条输入的实际创建日期逐日补跑。
- 当天存在转写失败项时，默认暂缓生成并通知用户；用户可选择忽略失败项继续。
- 当日生成后又出现当日输入，草稿标记为过期并补生成。
- 不支持选择任意历史日期重新生成。
- **晚到输入的定义（2026-09-16 定案）**：服务端收到该输入的时刻晚于其 `ContentDate` 在内容时区的 `23:59:59`。`ContentDate` 始终由输入自身的 `CreatedAtUtc` 与 `CreatedOffsetMinutes` 决定，离线补传不改变内容日。
- 由此存在两条过期路径：①当日生成后又收到内容日为当天的输入 → 当日补生成；②次日才收到内容日属于昨天的输入 → 次日补生成。
- 唯一例外是由当日晚到输入导致的过期草稿；即使次日才处理，也只能使用该日及更早的材料。
- 已 `Confirmed` 的稿件若该日已有发布记录，待发布版本失效并需重新确认，系统不自动重新发布。
- 后来修改历史转写不得触发或允许重新生成原日期文章，但修改后的内容可参与未来主题检索。

## 8. AI 处理管线

### 8.1 模型配置

管理页分别配置：

1. OpenAI 兼容的语音转写接口。
2. OpenAI 兼容的文章生成接口。
3. 可选的 OpenAI 兼容 Embedding 接口。

每项至少包含 Base URL、模型名、Secret 引用、超时和启用状态。客户端只能查看模型名与健康状态。

### 8.2 转写流程

1. 客户端完成录音并写入离线队列。
2. 联网后上传，携带客户端生成的幂等 ID。
3. 服务端先持久化音频，再确认接收。
4. 创建转写任务并立即执行。
5. 成功后保存原始转写，识别主题并生成 Embedding。
6. 失败按退避策略重试三次，之后通知用户。

### 8.3 历史检索

- 只检索 `AllowFutureRecall = true` 的记录。
- 只允许检索文章内容日期当日及之前的记录。
- Embedding 可用时进行语义检索，否则退化为主题标签和全文搜索。
- 默认最多返回十条高相关材料，数量可配置。
- 历史事件必须以回忆或延续的方式表述，不得伪装成当天事件。
- 索引绑定 `EmbeddingConfigVersion`（模型名 + 维度 + Base URL 指纹）。更换 Embedding 模型（即配置指纹变化）后旧索引整体失效：`SemanticSearchAvailable` 置为 false，检索自动降级为主题标签与全文搜索，并在客户端提示“语义检索重建中”。
- 重建是可持久化任务、分批执行，期间降级检索始终可用，完成后原子切换。不保留多代索引；检索能力状态属外部能力状态，不计入基础健康检查。

### 8.4 生成与核验

生成请求应包含：

- 当天按时间排序的输入。
- 选中的历史材料及日期。
- 篇幅、语气、第一人称等写作设置。
- 用户自定义写作要求。
- 不得添加无来源事实的不可覆盖系统规则。
- 要求输出结构化正文及来源映射。

生成后执行第二阶段的无来源陈述检查。存疑句子在客户端高亮并显示原因，但用户确认后仍可发布。

不得在产品文案中声称模型能够“绝对不捏造”。应表述为“提供来源追溯和无来源陈述检查，帮助用户核验”。

## 9. 客户端体验

### 9.1 首页

- 醒目的开始/停止录音按钮。
- 直接文字输入入口。
- 今日输入数量。
- 上传、转写及生成状态。
- 待确认或已过期草稿提醒。

首版不要求 Windows 托盘、全局快捷键、Android 小组件或快捷设置磁贴。

### 9.2 离线队列

- 客户端必须先安全落盘再显示录音完成。
- 上传使用幂等键，重试不得产生重复输入。
- 服务端确认持久化后才能删除本地临时副本。
- 用户应能查看失败原因并手动重试。

### 9.3 主要页面

- 今日：首页和当天时间线。
- 日历：按日期查看输入与随想状态。
- 主题：浏览、重命名、合并和调整归属。
- 草稿：编辑、来源核验、版本切换和发布。
- 设置：服务器连接、通知偏好和设备信息。

## 10. 身份与安全

### 10.1 管理员初始化

- 首次启动创建管理员账号 `admin`。
- 使用密码学安全随机数生成初始密码。
- 初始密码只在启动终端输出，不写入普通日志文件。
- 首次登录强制修改账号和密码。
- 服务器端只保存强密码哈希，不保存明文密码。

### 10.2 设备配对

- 管理页生成十分钟有效、仅可使用一次的配对码或二维码。
- 配对成功后签发独立设备令牌。
- 令牌应可轮换和单独撤销。
- 客户端使用平台安全存储保存令牌。

### 10.3 HTTP 风险

产品允许公网 HTTP，但必须：

- 首次连接时明确说明密码、令牌、录音和文章可能被截获。
- 要求用户主动确认后才能继续。
- 设置页持续显示不安全连接状态。
- 文档优先推荐 HTTPS、局域网或 VPN。

警告不等于安全措施，不得在文档中暗示 HTTP 经过确认后便是安全的。

### 10.4 Secrets

- 模型密钥、SMTP 密码和 WordPress Application Password 使用 Docker Secrets。
- 主配置文件仅保存 Secret 名称或路径引用。
- 普通数据导出及备份不得包含 Secrets。
- 设备令牌不属于上述 Secrets，但同样不进入备份与导出（见 §15.2）。
- 日志默认不得记录转写正文、提示词、模型响应或认证信息。

## 11. 发布

### 11.1 WordPress

- 使用标准 REST API 和 Application Password。
- 支持多个命名目标。
- 支持上传为 WordPress 草稿和立即公开。
- 默认自动行为是上传为私人草稿。
- 无人确认的自动公开必须按目标单独开启，并再次验证管理员身份、展示风险提示。
- 生成与发布时间分别配置；默认 23:00 生成、次日 08:00 发布。
- 夜间新增素材使待发布版本失效；补生成后才重新进入发布队列。
- 发布失败自动重试三次，之后通知用户，不得在长时间后静默公开。
- **执行窗口（2026-09-16 定案）**：`Publish.WindowMinutes` 默认 120，自计划发布时刻起计。超窗未执行则该发布记录转 `Expired`，除按配置发邮件外不触发任何自动动作；`Expired` 只能由用户手动重试或重新确认后回到队列，服务重启不构成延期理由。
- **权限（2026-09-16 定案）**：设备令牌可发起上传草稿、导出 Markdown 与手动公开；手动公开须在客户端显式二次确认（展示目标站点与文章标题），并由服务端记录 `TriggeredBy`、`TriggeredAtUtc` 审计字段。自动公开开关只能在管理页由管理员开启，开启时需重新输入密码并展示风险提示；设备令牌永远不能开启或关闭自动公开。
- 保存远程文章 ID；后续本地修改不得自动更新远程内容。
- 用户可主动检查远程差异，并选择拉取、覆盖或保留两边。

### 11.2 Hexo Markdown

- 生成带可配置 Front Matter 的 Markdown。
- 默认文件名为 `YYYY-MM-DD-slug.md`。
- 支持 `title`、`date`、`updated`、`tags`、`categories`、`draft` 和正文占位符。
- 文件写入用户指定的服务器挂载目录，例如 Hexo 的草稿目录。
- MVP 不执行 Hexo、Git 或其他外部命令。
- 不得静默覆盖已存在或被外部修改的文件。
- 再次导出默认创建带版本号的新文件，用户明确确认后才能替换。

## 12. 邮件通知

使用通用 SMTP 配置，不为 QQ 邮箱、Gmail 等服务分别开发专用集成。

可独立启用的通知事件：

- 新草稿待确认。
- 任务最终失败。
- 自动发布成功或失败。

邮件任务与业务任务解耦。邮件失败不能回滚文章、触发重复生成或改变发布结果。

## 13. 建议 API 边界


## 14. 后台任务与可靠性

- 任务必须持久化，服务重启后可恢复。
- 启动时把上一次进程留下的 `Running` 任务一律重排（此刻本实例不可能真有任务在跑），并且**目标自身的中间状态不得成为死路**：被中断的转写会把输入复位为待转写再重跑（音频还在，重跑安全）；被中断的发布则相反——它可能已经进了对方的网络，重排后按计划跳过，由用户主动核对远端（见附录 A.15）。
- 同一输入的转写、同一日期的生成以及同一版本向同一目标发布都必须幂等。
- 临时错误采用指数退避，默认最多三次。
- 达到上限后进入最终失败状态并按配置发邮件。
- 用户修复配置后可以重试单项或批量补跑失败任务。
- SMTP 失败只影响通知任务。
- 自动发布超过合理执行窗口后不得静默补发，必须重新确认或手动重试（窗口长度见 §11.1，默认 120 分钟）。

初期可使用数据库驱动的后台队列，不必引入外部消息中间件。确保多实例部署未被支持时，Compose 只运行一个任务执行实例。

## 15. 数据导出、备份与迁移

### 15.1 可阅读导出

至少包含：

- 每篇随想的 Markdown。
- 输入、主题、来源映射和元数据 JSON。
- 尚未被保留策略删除的音频文件。

**音频保留策略（2026-09-16 定案）**：转写成功且用户首次确认该日草稿后，音频进入可清理状态；`Retention.AudioDays` 默认 30，可配置为“永久”或 0（立即删除）。到期物理删除音频文件，`InputEntry` 与转写文本保留，`AudioPath` 置空并记录 `AudioDeletedAtUtc`。清理是独立的可持久化任务（`JobType = AudioCleanup`），失败不影响业务；管理页与导出说明须明示当前策略。

### 15.2 完整备份

- 包含 SQLite 数据库、媒体、Markdown、索引元数据和非秘密配置。
- **不包含设备令牌及其派生的会话状态**（2026-09-16 定案）：恢复后所有设备必须重新配对。此举与 §10.4 凭据不外流原则一致，且重配对仅需管理页生成十分钟一次性码，成本很低。
- **不包含 DataProtection 密钥环**（2026-09-16 定案，见附录 A.14）。密钥环签发管理员登录 Cookie，属**凭据等价物**：放进实例卷就等于让每份备份都带着伪造会话的能力，与上一条同理。它必须在实例根目录之外独立持久化——否则重建容器会静默登出管理员——但不得进入备份。
- 支持管理页一键备份。
- 支持每日定时输出到挂载目录。
- 默认保留最近七份。
- 必须提供在全新实例上的恢复验证流程，采用以下八步（2026-09-16 定案）：
  1. 全新空目录，仅放入 Compose 文件与新生成的 Secrets。
  2. `docker compose up -d`，确认自动迁移成功、管理员已初始化。
  3. 通过管理页恢复备份（SQLite + 媒体 + Markdown + 索引元数据 + 非秘密配置）。
  4. 校验基础健康检查全绿，且任务队列无遗留 `Running` 任务。
  5. 抽样校验：随想正文可打开、三版本位置完整、来源映射可解析（`QuoteHash` 匹配）。
  6. 抽样校验：语音输入可播放，且原始转写与修订稿均在。
  7. 校验：导出包与备份包中不含任何 Secret。
  8. 校验：原设备令牌不可用，且重新配对流程可正常完成。

### 15.3 数据库迁移

- 服务启动时自动执行向前迁移。
- 升级文档要求先备份。
- 不承诺自动降级；保留旧镜像和备份用于恢复。

## 16. 可观测性

默认日志只记录：

- 请求或任务 ID。
- 状态变化、耗时和重试次数。
- 脱敏后的错误代码与摘要。

只有用户主动开启临时调试模式时才能记录内容相关信息，并必须提示可能包含私人数据。调试模式应自动到期。

服务提供健康检查，至少覆盖数据库可写、媒体目录可写、后台任务执行器状态；外部模型、SMTP 和 WordPress 使用独立的“测试连接”操作，不应让外部服务故障导致基础健康检查失败。

## 17. 测试策略

### 17.1 单元测试

重点覆盖：

- UTC 与内容时区的自然日划分。
- 当日晚到输入引起的草稿过期和补生成资格。
- 禁止任意历史日期重新生成。
- 历史检索不得使用文章日期之后的内容。
- 三版本轮换不得覆盖手工编辑。
- 主题的合并、重命名与删除不得改变历史文章的来源映射。
- “晚到”判定只依赖输入的创建时间与偏移，与生成任务是否已执行无关。
- 删除音频与删除整条记录的不同语义。
- 自动发布的状态转换和执行窗口。

### 17.2 集成测试

- SQLite 和文件系统的一致性。
- 录音上传幂等性和断线重试。
- 模型接口成功、超时、限流和无效响应。
- Embedding 降级及索引重建。
- SMTP 失败不影响草稿。
- WordPress 重试不产生重复文章。
- Docker 重启后任务恢复。
- 备份在全新实例恢复。

外部服务必须使用可控的测试替身；另外保留一套可选的真实 WordPress 测试环境验收。

### 17.3 端到端验收

必须完成以下真实路径：

1. Android 断网录制多条语音并输入文字。
2. 联网后自动上传、转写和识别主题。
3. 服务端按内容时区生成当天随想并关联历史来源。
4. 用户查看存疑语句、修改转写和草稿、执行允许的重新生成。
5. 邮箱收到待确认提醒。
6. 用户将文章上传为 WordPress 草稿或输出 Hexo Markdown。
7. Windows 客户端查看、录制、编辑并发布同一服务端数据。
8. 创建完整备份，并在全新服务实例按 §15.2 的八步恢复验证流程恢复全部内容。

## 19. 完成定义

一个功能只有同时满足以下条件才算完成：

- 领域规则和失败路径已实现。
- 数据写入具有幂等性或明确的恢复策略。
- 不会泄露 Secret 或私人内容到默认日志。
- 核心逻辑有自动化测试。
- 涉及 UI 的功能已在真实 Android 设备验证；跨平台功能还需在 Windows 验证。
- Docker Compose 环境可以从空目录部署。
- 相关配置、备份和故障恢复方式已经写入用户文档。

## 20. 实施约束

- 优先交付 Android 端到端闭环，再完成 Windows 适配。
- 不为假设中的多人或大规模部署提前引入复杂基础设施。
- 不在客户端实现应由服务端统一执行的 AI、调度或发布逻辑。
- 不执行用户提供的任意 Shell 命令。
- 不因模型、SMTP 或 WordPress 暂时失败而丢失输入。
- 不允许后台任务通过重复执行产生重复文章、重复输入或重复发布。
- 新需求若属于 MVP 排除项，应先修改本文档并重新确认范围。

### A.1 音频保留策略

**问题**：§15.1 声明导出“尚未被保留策略删除的音频文件”，但全文没有任何地方定义该保留策略；§6.1 只有 `DeletedAtUtc`。导出范围、备份体积、隐私承诺，以及“转写成功后能否立即丢弃音频”都取决于此。

**备选与权衡**：

1. 转写成功后立即删除音频——隐私最强、体积最小，但用户事后无法复核转写是否有误。
2. 永久保留，仅在删除整条记录时清除——可回溯性最好，但备份体积与隐私风险最大。
3. 确认草稿后保留 30 天（可配置）——兼顾三者，代价是需要一套独立的清理任务与状态。

**定案理由**：选 3。本文的核心卖点是“来源可核验”；若转写成功即删音频，用户日后怀疑转写有误便无从复核，等于自断一半卖点；而永久保留又会同时恶化备份体积与隐私承诺。30 天覆盖“当天录、过几天核对”的实际节奏，且保留“永久”“立即删除”两个极值以满足不同偏好。

### A.2 自动发布执行窗口

**问题**：§14 要求“超过合理执行窗口后不得静默补发”，§17.1 要求测试该窗口，但全文未给数值。这是“不得静默公开”这一安全承诺的唯一执行依据，没有数值就无法实现也无法测试。

**备选与权衡**：

1. 60 分钟——更保守，但能容忍的故障窗口过短。
2. 120 分钟——覆盖容器重启与短暂故障，且不至于跨夜。
3. 当日有效（至 23:59）——最省心，但实质上放松了 §14 的约束。
4. 不设过期，重启后仍可自动发布——直接违背 §14，不采纳。

**定案理由**：选 2。默认发布点为次日 08:00，用户的白天在线时段足以处理两小时内的告警；窗口再长到跨夜，就等于把“不得静默公开”架空。同时明确**重启不构成延期理由**，否则反复重启即可无限延长窗口。

### A.3 稿件状态模型

**问题**：§6.3 状态机图把 `Failed` 与 `StaleByLateInput` 画成状态，字段列表却同时有 `Status` 与 `IsStaleBecauseOfLateInput`，二者关系未说明。这决定枚举取值、数据库约束，以及客户端“草稿”页的默认分组。

**备选与权衡**：

1. 七值 `Status` 枚举，布尔字段降级为审计用途——与状态机图一致，客户端可直接按状态分组。
2. `Status` 只保留主流程五值，失败与过期用两个标志位表达——状态更正交，但“已失败 + 已过期”这类组合需要 UI 层自行推导展示态，分组逻辑会散落到客户端。

**定案理由**：选 1。状态机图本就是状态语义；选 2 会让展示态推导逻辑进入客户端，与 §4.1“AI、调度与发布逻辑统归服务端”的分工相悖。另外 `Failed` 是**稿件态**，必须与 `ProcessingJob` 的**任务态失败**严格区分，避免两套失败语义互相污染。

### A.4 晚到输入的判定

**问题**：§7 提到“当日晚到输入”、§11.1 提到“夜间新增素材使待发布版本失效”，但未定义到达时间与内容日的关系，也未说明能否跨日到达。它直接决定补生成资格与发布队列的重入条件。

**备选与权衡**：

1. 以内容日 `23:59:59`（内容时区）为界——判定只依赖输入自身的创建时间与偏移。
2. 以当日生成时刻（默认 23:00）为界——更贴近“生成之后才算晚到”的字面表述，但生成因故障延到 23:40 执行时，“23:30 到达的输入”是否算晚到就没有唯一答案。

**定案理由**：选 1。它使“是否晚到”与“生成任务是否已经执行”完全解耦，因而确定、可离线补传、可单元测试。选 2 会把生成任务的执行时序引入判定，产生无法判定的边界情况。

### A.5 内容时区变更

**问题**：§7 规定内容时区可配置，§4.1 将其列为管理页配置项，但未说明变更是否回溯。

**备选与权衡**：

1. 不回溯，`ContentDate` 一经写入即不可变——历史数据稳定，但选错时区的实例会“前后不一致”。
2. 变更时全量重算 `ContentDate`——历史归属日会变，冲击“按日唯一”、补跑资格与已发布内容的日期归属。
3. 默认不回溯，另附一次性迁移工具。

**定案理由**：选 1。`ContentDate` 不可变是补生成规则能成立的地基：一旦可重算，“某日是否已生成”“某输入是否属于该日”都会失去稳定答案，与 §7 的不可变精神直接冲突。时区在实际中极少变更，且要纠正的是**新数据**的时区，历史数据本身并没有错；选 3 的工具属于假想需求，按 §20 不提前引入。

### A.6 来源定位格式

**问题**：§6.5 只要求“段落定位信息”，§8.4 要求存疑句子在客户端高亮。高亮、版本切换后的漂移检测，以及“来源核验”界面的实现都依赖一个确定格式。

**备选与权衡**：

1. 段落序号 + 字符区间 + 引用哈希——三层定位，可检测漂移。
2. 仅整段定位——实现最简，但存疑句子只能高亮到段落。
3. Markdown 块 ID 锚点——定位最稳，但正文会被标记污染，影响 Markdown 输出。

**定案理由**：选 1。`QuoteHash` 是这里唯一的漂移检测手段：用户手工编辑后段落文本已变，若仍按旧偏移精确高亮就会**指错地方**——在“帮助用户核验来源”的场景下，指错比不指更糟。哈希不匹配时降级为整段提示并告知版本已被编辑，是唯一诚实的处理方式。选 3 会侵入正文格式，与 §11.2 的 Markdown 输出要求冲突。

### A.7 发布权限边界

**问题**：§4.1 把“发布操作”列入客户端职责，§11.1 要求无人确认的**自动**公开需再次验证管理员身份；手动公开是否也需管理员二次验证，未说明。这决定设备令牌的权限模型与 API 鉴权策略。

**备选与权衡**：

1. 设备令牌可手动公开（客户端二次确认 + 服务端审计）；自动公开开关仅管理页可开。
2. 手动公开同样要求管理员密码——更保守，但日常在手机上发布会很繁琐。
3. 设备令牌只能上传草稿，所有公开动作都在管理页完成——剥夺了 §9.3 草稿页的发布能力。

**定案理由**：选 1。§11.1 的“再次验证管理员身份”在原文中明确限定于**无人确认的自动公开**；手动公开本身已经有人在确认，若再要求管理员密码，§9.3 的“草稿页发布”在手机上基本不可用。风险仍被看住：二次确认不可省略、公开动作留审计字段、自动公开的开关能力完全不给设备令牌。

### A.8 检索失效与降级

**问题**：§8.3 说“更换 Embedding 模型后旧索引失效，重建完成前使用降级检索”，§16 要求健康检查不受外部依赖影响，但“语义检索当前是否可用”没有可查询的判定来源——否则每次检索都要临时探测模型。

**备选与权衡**：

1. 配置指纹 + 全库失效 + 全局降级开关——判定来源唯一，实现简单。
2. 按指纹保留多代索引并支持回退——可回滚，但存储与查询复杂度显著上升。

**定案理由**：选 1。`SemanticSearchAvailable` 必须是可查询状态，否则 §8.3 的降级检索与客户端“重建中”提示都无从实现。选 2 是为假想需求增加复杂度，与 §20 冲突。另需明确：重建状态属外部能力状态，**不**计入基础健康检查，否则 Embedding 服务不可用会连带让基础健康检查失败，违反 §16。

### A.9 主题引用稳定性

**问题**：§6.2 要求支持合并且“删除主题不得删除原始输入”，§6.5 的 `SourceReference` 关联的是输入而非主题。所以文档已隐含可解，真正待确认的只有一点：主题 ID 是否允许变化。

**备选与权衡**：

1. 主题 ID 稳定不可变，合并留 tombstone——成本是一行记录加一个 `MergedIntoId`。
2. 合并即删除被合并主题行——表更干净，但客户端缓存与历史引用会断裂，且旧 ID 可能被复用后语义串台。

**定案理由**：选 1。成本极低而收益明确；更重要的是，因 `SourceReference` 指向 `InputEntry`，历史文章的来源映射**天然不受**主题操作影响——这一条值得写成显式不变量测试固定下来，防止日后有人在合并逻辑里顺手改了引用。

### A.10 目标框架

**问题**：文档通篇未指定 .NET 版本；开发机已安装 SDK 为 10.0.302。阶段一的解决方案模板、`TargetFrameworks` 与 Docker 基础镜像选择都直接依赖它。

**备选与权衡**：

1. .NET 10——与开发机 SDK 一致，MAUI 模板与工作负载现成。
2. .NET 8 LTS——长期支持更稳，适合“多年不升级”的目标，但需另装 SDK，MAUI Android 工具链较旧。

**定案理由**：选 1。交付物是自托管 Windows 安装包与 Android APK，不经商店审核，LTS 的“长期免升级”优势在此场景并非硬需求；与开发机一致可避免额外的工具链维护成本。另明确 Docker 基础镜像固定 tag、不使用 `latest`，以免镜像漂移导致“同一版本行为不同”。

### A.11 Android 最低版本

**问题**：同 A.10，需确定 `SupportedOSPlatformVersion`。

**备选与权衡**：

1. API 24（Android 7.0）——覆盖面更广，但旧版存储权限与后台限制差异多，兼容分支显著增加。
2. API 26（Android 8.0）——避开旧版存储权限差异，覆盖绝大多数在用设备。
3. API 29（Android 10）——测试矩阵最小，但会排除部分在用设备。

**定案理由**：选 2。运行时权限模型在 API 23 之后已统一，再取 26 可避开旧版存储权限的兼容分支；继续下探收益极小、分支成本陡增，而 29 的门槛对“个人自用”场景不必要地苛刻。

### A.12 恢复验证流程

**问题**：§15.2 要求“必须提供在全新实例上的恢复验证流程”，§19 要求“Docker Compose 环境可以从空目录部署”，但两处都没有步骤与判定标准，导致完成定义无法判定、用户文档也无从下笔。

**备选与权衡**：

1. 八步清单——覆盖迁移、任务队列残留、来源映射完整性、音频可播与 Secret 排除。
2. 精简为四项核心校验（服务能起、文章能看、音频能放、无 Secret 泄露）——更轻，但不校验任务队列残留与来源映射完整性。

**定案理由**：选 1。它的价值在于把 §15.2 与 §19 的两处要求接成一条可执行、可判定的清单，并直接充当 §17.3 端到端验收的第 8 步。选 2 会漏掉两类恢复失败模式：遗留 `Running` 任务导致的重复执行，以及来源映射无法解析导致的“文章看起来对、核验功能已坏”。

### A.13 备份排除设备令牌

**问题**：§15.2 原文写备份“包含 SQLite 数据库”，而设备令牌就存在于该库中，于是“恢复后原设备能否继续使用”没有答案。这是 A.12 清单第 8 步在编写时暴露出的真实歧义。

**备选与权衡**：

1. 备份不含设备令牌，恢复后重新配对——凭据不外流，攻击面最小。
2. 备份含设备令牌，恢复后原设备无需操作即可继续使用——灾难恢复体验最顺，但备份从此携带认证凭据。

**定案理由**：选 1。与 §10.4「普通数据导出及备份不得包含 Secrets」的原则保持一致，也让备份文件的泄露风险不因“恢复方便”而上升。重配对的成本很低——管理页生成十分钟一次性码、手机上扫一下，而恢复通常恰恰发生在手边就有设备的场景。

### A.14 DataProtection 密钥环的位置

**问题**：容器化部署时 ASP.NET Core 默认把密钥环放在运行时用户的主目录（容器内为 `/home/app/.aspnet/DataProtection-Keys`）。该路径位于容器的可写层，**重建容器即丢失**，于是每次重新部署都会让所有管理员会话失效。但把它放进实例根目录又会引出另一个问题：实例根目录就是备份集，密钥环因此会随备份外流。这个问题是在远程 Docker 环境做真实部署验收时，从启动日志的告警里发现的。

**备选与权衡**：

1. 不持久化，接受重建即登出——实现最简，备份天然干净；代价是每次重新部署都要重新登录，重建期间正在提交的表单也会失败。
2. 放进实例根目录——会话可存活，但备份从此携带可伪造管理员会话的材料，与 §10.4 和 A.13 的原则直接冲突。
3. 放在实例根目录之外的独立路径与独立卷——会话存活，备份保持干净。

**定案理由**：选 3。它同时满足两个约束：密钥环必须比容器活得久，但不得进入备份。这与 A.13 对设备令牌的推理是同一条——备份可以带走内容，不可以带走凭据。已用 `docker compose up -d --force-recreate` 在真实容器上验证：重建后同一 Cookie 仍被接受，密钥环文件位于独立卷，且 `/var/lib/dailymusings` 内不含密钥环。

**正文落点**：§15.2。

### A.15 被中断任务的恢复语义

**问题**：§14 只写了「任务必须持久化，服务重启后可恢复」，没写**中断**（进程被杀、容器被替换、断电）留下的状态该怎么办。这一条是在阶段五补测试断言时暴露的：补上「重启后被中断的任务会被重排」这条断言后，测试第一次运行就红了——任务确实被重排了，但重排后的转写被领域规则拒绝（`input.transcription.bad_state`），因为输入条目还停在 `in_progress`，而 `BeginTranscription` 只接受 `pending`/`failed`。结果是：任务最终失败，输入永远拿不到转写，用户点「重试转写」也救不回来。缺陷不在恢复逻辑，而在「恢复之后目标的状态没人管」。

**备选与权衡**：

1. 启动时重排遗留 `Running` 任务，并把目标自身的中间状态按业务语义复位（转写复位后重跑；发布按计划跳过）——恢复是自动的，且不改领域规则。
2. 启动时把遗留 `Running` 任务直接标记为最终失败，交由用户手动重试——最保守，但把「机器被重启」说成了「你的这段语音转不出来」，而且用户往往并不知道要重试什么。
3. 什么都不做，让任务永远停在 `Running`——界面上一句「转写中」挂到天荒地老，等于静默丢数据。

**定案理由**：选 1，并按任务类型分别处理。判据是**重跑是否安全**：转写重跑安全——音频还在、目标条目唯一、写入的是同一个字段，所以把被中断的输入复位为待转写再跑一次，代价为零，收益是一条本来会永久丢失的转写。发布重跑不安全——请求可能已经进了对方的网络，重复发布是 §14 明令禁止的，所以重排后的发布任务在本地记录仍是 `InProgress` 时按计划跳过，把「本地不知道远端发生了什么」如实留给用户，由 §11.1 的「检查远程」去核对。同一条原则也解释了为什么生成被中断后可以直接重跑：`Generating → Generating` 是生命周期里允许的自环，草稿没有「发出去了就收不回」的副作用。

**正文落点**：§14。回归断言在 `tests/DailyMusings.Api.IntegrationTests/JobRecoveryTests.cs`（真停真起：一个进程在转写中途被停止，数据库里留下 `Running`，新进程启动后同一条任务记录完成，尝试次数为 2）。
