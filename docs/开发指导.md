## 2. 产品目标

“每日随想”面向会在日常生活中随时记录见闻、想法和思考的个人创作者。

用户通过 Android 客户端输入短语音或文字。服务端负责转写、主题识别、历史检索、每日随想生成、通知，并最终把成稿写成一份 Markdown 文件。当天只要存在至少一条有效输入，就生成一篇随想；没有输入则不执行生成任务。

核心原则：

- 捕捉瞬间想法，而非会议录音或备忘录管理。
- 默认生成私人草稿，由用户核验后才输出。
- 用户自行提供模型服务，项目不捆绑任何模型。
- 数据由用户自托管并可完整导出。
- AI 只能整理、重构和润色来源内容，不得故意补充不存在的事实。
- 模型无法提供绝对真实性保证，因此必须提供来源追溯和风险提示。
- 交付面尽量窄：当前只承诺产出一份 Markdown 文件，不做站点对接。

## 3. MVP 范围

### 3.1 必须包含

- 单用户 ASP.NET Core 服务端。
- Blazor 服务端管理页面。
- Android .NET MAUI 客户端。
- Linux Docker Compose 部署。
- 文字输入、短语音录制、离线队列和即时转写。
- 标签检索及可选的 Embedding 语义检索。
- 每日随想生成、历史主题引用、来源核验和三版本草稿。
- SMTP 邮件提醒。
- **产出 Markdown 文件**：把确认过的稿件写成一份 `.md`，落在用户指定的挂载目录里（附录 A.17）。
- 设备配对、数据导出、备份恢复、日志和失败重试。

### 3.2 明确不包含

- 多用户、团队或公开注册。
- **电脑端（Windows 桌面）客户端**（附录 A.17；`DailyMusings.Client` 只保留 Android 目标）。
- **WordPress 或任何博客站点的 API 对接**（附录 A.17）。
- **执行 `hexo generate`、`hexo deploy`、Git 提交或推送，或用户自定义命令**。
- **Hexo 专属的 front-matter 字段与目录约定微调**：当前只要求产出一份可读的 Markdown 文件，适配 Hexo 的细节属于后续工作（附录 A.17）。
- 图片输入和已有音频导入。
- 会议录音和长音频工作流。
- 任意历史日期重新生成。
- Microsoft Store 或 Google Play 发布。
- 默认遥测。

## 4. 总体架构

```text
Android MAUI ──── HTTP/HTTPS API ── ASP.NET Core 服务端
                                        │
Blazor 管理页 ──────────────────────────┤
                                        ├── SQLite
                                        ├── 音频与导出文件目录
                                        ├── OpenAI 兼容模型接口
                                        ├── SMTP
                                        └── Markdown 输出目录（Hexo 读取）
```

### 4.1 职责划分

客户端负责：

- 录音、文字输入和本地离线队列。
- 时间线、日历、主题、草稿及任务状态展示。
- 修订转写、调整主题、编辑和重新生成允许处理的草稿。
- 触发 Markdown 导出及来源核验。
- 保存服务器引用和设备令牌，不保存模型或任何发布密钥。

服务端负责：

- 身份验证、设备配对和设备撤销。
- 音频接收、持久化、转写和重试。
- 主题识别、标签搜索、向量索引和历史检索。
- 每日调度、补跑、文章生成及事实来源检查。
- 草稿版本管理，以及把稿件写成 Markdown 文件。
- SMTP 通知、备份、恢复、数据导出和诊断日志。

管理网页负责：

- 管理员账号和密码。
- 模型、Embedding、SMTP、Markdown 输出目录及内容时区配置。
- 设备配对、设备撤销和系统状态查看。
- 任务失败处理、索引重建、备份恢复及日志查看。
- 不承担主要的日常创作体验。

## 6. 核心领域模型

### 6.1 InputEntry

代表一条语音或文字输入。

关键字段：

- `Id`
- `SourceType`: `Voice` 或 `Text`
- `CreatedAtUtc`
- `CreatedOffsetMinutes`
- `ContentDate`: 按内容时区计算的自然日
- `AudioPath`、`AudioDuration`、`AudioDeletedAtUtc`
- `OriginalTranscript`
- `RevisedTranscript`
- `TranscriptionStatus`
- `AllowFutureRecall`
- `PrimaryTopicId`
- `SecondaryTopicIds`
- `DeletedAtUtc`

原始转写和用户修订稿必须分开保存。生成时优先使用修订稿，没有修订稿时使用原始转写。

音频保留策略见 §15.1；音频被清理后 `AudioPath` 置空，转写文本仍保留，输入记录本身不受影响。

### 6.2 Topic

- 支持重命名、合并和调整输入归属。
- 一条输入最多有一个主要主题，可有多个次要主题。
- MVP 不要求自动拆分主题。
- 删除主题不得删除原始输入。
- `Topic.Id` 稳定且不可变，重命名只改展示名、不改 ID。
- 合并只改归属，不删除被合并主题行：保留为 tombstone 并记录 `MergedIntoId`、`MergedAtUtc`。
- `SourceReference` 指向输入而非主题，因此主题的合并、重命名与删除都不得改变历史文章的来源映射。

### 6.3 Reflection

代表某一自然日的每日随想。

关键字段：

- `Id`
- `ContentDate`
- `Status`
- `GenerationReason`
- `LastStaleReason`（原 `IsStaleBecauseOfLateInput`，2026-09-16 定案降级为审计字段，不再作为状态依据）
- `InitialVersionId`
- `PreviousVersionId`
- `WorkingVersionId`
- `ConfirmedVersionId`
- `CreatedAtUtc`、`UpdatedAtUtc`

状态定义（2026-09-16 定案）：

```text
PendingInputs → Ready → Generating → ReviewRequired → Confirmed
                         │                 │
                         └── Failed       └── StaleByLateInput

Status ∈ { PendingInputs, Ready, Generating, ReviewRequired, Confirmed, Failed, StaleByLateInput }
```

`Failed` 指生成二阶段重试耗尽的**稿件态**，与 `ProcessingJob` 的任务态失败严格区分。`StaleByLateInput` 指当日已生成后又收到当日输入、等待补生成。唯一允许离开 `Confirmed` 的迁移是 `Confirmed → StaleByLateInput`。状态分组一律由服务端计算，客户端只负责展示。

### 6.4 ReflectionVersion

保存标题、摘要、正文、标签、分类建议、写作设置、模型信息、提示词版本和来源映射。

版本规则：

- 最初版本永久保留。
- 重新生成前，当前编辑版本转为上一版本。
- 新结果成为当前编辑版本。
- 不得静默覆盖用户手工编辑。
- 默认只维护“最初、上一、当前”三个版本位置。

### 6.5 SourceReference

把文章段落或句子关联到一个或多个输入记录，字段定义（2026-09-16 定案）：

- `ReflectionVersionId`：文章版本 ID。
- `BlockIndex`：版本正文内的段落序号，0 起。
- `CharStart`、`CharEnd`：段内半开字符区间。
- `QuoteHash`：被引用片段规范化后的哈希，用于检测定位漂移。
- `InputId`：输入 ID，可多个。
- `Relevance`、`Reason`：相关度与引用原因。
- `IsHistorical`：是否为历史材料。

客户端高亮时若 `QuoteHash` 与当前文本不匹配，判为定位漂移：降级为整段提示而非精确高亮，并告知用户该版本已被编辑。

来源信息默认仅在应用内展示，不自动写入公开文章。

### 6.6 ProcessingJob

所有转写、索引、生成、检查、通知和发布操作都应建模为可持久化任务，而不是仅存在于进程内存中。

任务类型至少包括：转写、Embedding 索引与重建、生成、无来源陈述检查、通知、发布、备份，以及音频清理（`AudioCleanup`）。

关键字段：

- `JobType`
- `TargetId`
- `Status`
- `AttemptCount`
- `ScheduledAtUtc`
- `StartedAtUtc`
- `CompletedAtUtc`
- `IdempotencyKey`
- `ErrorCode`
- `ErrorSummary`

### 6.7 PublishTarget 与 Publication

发布目标只有一种类型：一个 **Markdown 目录**（相对实例的 markdown 根目录）。一个实例允许配置多个命名目标，因此同一篇稿件可以落到不同目录；每个目标独立保存导出状态与它写出的文件名（记录里沿用 `RemoteId` 这个字段名，值就是文件名）。

§11.1 的整条发布生命周期仍然成立，只是它的对象从「远端文章」变成「本地导出」：队列、幂等键、执行窗口、自动发布开关与可见性都保留，可见性对 Markdown 目标而言就是 front matter 里的 `draft` 字段（附录 A.17）。

## 7. 时间与生成规则

- 内容时区在服务端配置，默认 `Asia/Shanghai`。
- 所有时间以 UTC 持久化，并记录输入创建时的时区偏移。
- 自然日按内容时区的 `00:00–23:59` 划分。
- 默认 23:00 生成，时间可配置。
- 当天无输入时不得创建空文章。
- 服务器停机或客户端离线后，按每条输入的实际创建日期逐日补跑。
- 当天存在转写失败项时，默认暂缓生成并通知用户；用户可选择忽略失败项继续。
- 当日生成后又出现当日输入，草稿标记为过期并补生成。
- 不支持选择任意历史日期重新生成。
- **晚到输入的定义（2026-09-16 定案）**：服务端收到该输入的时刻晚于其 `ContentDate` 在内容时区的 `23:59:59`。`ContentDate` 始终由输入自身的 `CreatedAtUtc` 与 `CreatedOffsetMinutes` 决定，离线补传不改变内容日。
- 由此存在两条过期路径：①当日生成后又收到内容日为当天的输入 → 当日补生成；②次日才收到内容日属于昨天的输入 → 次日补生成。
- 唯一例外是由当日晚到输入导致的过期草稿；即使次日才处理，也只能使用该日及更早的材料。
- 已 `Confirmed` 的稿件若该日已有导出记录，待导出记录失效并需重新确认，系统不自动重新导出。
- 后来修改历史转写不得触发或允许重新生成原日期文章，但修改后的内容可参与未来主题检索。

## 8. AI 处理管线

### 8.1 模型配置

管理页分别配置：

1. OpenAI 兼容的语音转写接口。
2. OpenAI 兼容的文章生成接口。
3. 可选的 OpenAI 兼容 Embedding 接口。

每项至少包含 Base URL、模型名、Secret 引用、超时和启用状态。客户端只能查看模型名与健康状态。

### 8.2 转写流程

1. 客户端完成录音并写入离线队列。
2. 联网后上传，携带客户端生成的幂等 ID。
3. 服务端先持久化音频，再确认接收。
4. 创建转写任务并立即执行。
5. 成功后保存原始转写，识别主题并生成 Embedding。
6. 失败按退避策略重试三次，之后通知用户。

### 8.3 历史检索

- 只检索 `AllowFutureRecall = true` 的记录。
- 只允许检索文章内容日期当日及之前的记录。
- Embedding 可用时进行语义检索，否则退化为主题标签和全文搜索。
- 默认最多返回十条高相关材料，数量可配置。
- 历史事件必须以回忆或延续的方式表述，不得伪装成当天事件。
- 索引绑定 `EmbeddingConfigVersion`（模型名 + 维度 + Base URL 指纹）。更换 Embedding 模型（即配置指纹变化）后旧索引整体失效：`SemanticSearchAvailable` 置为 false，检索自动降级为主题标签与全文搜索，并在客户端提示“语义检索重建中”。
- 重建是可持久化任务、分批执行，期间降级检索始终可用，完成后原子切换。不保留多代索引；检索能力状态属外部能力状态，不计入基础健康检查。

### 8.4 生成与核验

生成请求应包含：

- 当天按时间排序的输入。
- 选中的历史材料及日期。
- 篇幅、语气、第一人称等写作设置。
- 用户自定义写作要求。
- 不得添加无来源事实的不可覆盖系统规则。
- 要求输出结构化正文及来源映射。

生成后执行第二阶段的无来源陈述检查。存疑句子在客户端高亮并显示原因，但用户确认后仍可导出。

不得在产品文案中声称模型能够“绝对不捏造”。应表述为“提供来源追溯和无来源陈述检查，帮助用户核验”。

## 9. 客户端体验

### 9.1 首页

- 醒目的开始/停止录音按钮。
- 直接文字输入入口。
- 今日输入数量。
- 上传、转写及生成状态。
- 待确认或已过期草稿提醒。

首版不要求 Android 小组件、快捷设置磁贴或全局快捷键。

### 9.2 离线队列

- 客户端必须先安全落盘再显示录音完成。
- 上传使用幂等键，重试不得产生重复输入。
- 服务端确认持久化后才能删除本地临时副本。
- 用户应能查看失败原因并手动重试。

### 9.3 主要页面

- 今日：首页和当天时间线。
- 日历：按日期查看输入与随想状态。
- 主题：浏览、重命名、合并和调整归属。
- 草稿：编辑、来源核验、版本切换和导出。
- 设置：服务器连接、通知偏好和设备信息。

## 10. 身份与安全

### 10.1 管理员初始化

- 首次启动创建管理员账号 `admin`。
- 使用密码学安全随机数生成初始密码。
- 初始密码只在启动终端输出，不写入普通日志文件。
- 首次登录强制修改账号和密码。
- 服务器端只保存强密码哈希，不保存明文密码。

### 10.2 设备配对

- 管理页生成十分钟有效、仅可使用一次的配对码或二维码。
- 配对成功后签发独立设备令牌。
- 令牌应可轮换和单独撤销。
- 客户端使用平台安全存储保存令牌。

### 10.3 HTTP 风险

产品允许公网 HTTP，但必须：

- 首次连接时明确说明密码、令牌、录音和文章可能被截获。
- 要求用户主动确认后才能继续。
- 设置页持续显示不安全连接状态。
- 文档优先推荐 HTTPS、局域网或 VPN。

警告不等于安全措施，不得在文档中暗示 HTTP 经过确认后便是安全的。

### 10.4 Secrets

- 模型密钥与 SMTP 密码使用 Docker Secrets。
- 主配置文件仅保存 Secret 名称或路径引用。
- 普通数据导出及备份不得包含 Secrets。
- 设备令牌不属于上述 Secrets，但同样不进入备份与导出（见 §15.2）。
- 日志默认不得记录转写正文、提示词、模型响应或认证信息。

## 11. 导出为 Markdown

### 11.1 导出生命周期

「发布」在本产品里的含义是**把确认过的稿件导出成一份 Markdown 文件**。队列、幂等与审计这套机制保留，操作对象从远端文章换成本地文件。

- 一个实例允许配置多个命名目标，每个目标是一个目录。
- 只有 `Confirmed` 的稿件可被导出。
- 同一版本向同一目标导出恰好一次；再次导出是同一记录的下一轮（`ExportRound` 递增），不是第二条记录。
- 用户可选择**草稿**或**公开**：对 Markdown 目标而言，这就是 front matter 里 `draft: true` / `draft: false` —— Hexo 不会生成 `draft: true` 的文章，所以这个字段是「公开」在文件上的唯一落点。
- 生成与导出时刻分别配置；默认 23:00 生成、次日 08:00 进入导出队列。
- 夜间新增素材使待导出记录失效（`Superseded`）；补生成后才重新进入队列。
- 导出失败自动重试三次，之后通知用户。
- **执行窗口（2026-09-16 定案，2026-09-24 沿用）**：`Publish.WindowMinutes` 默认 120，自计划时刻起计。超窗未执行则该记录转 `Expired`，除按配置发邮件外不触发任何自动动作；`Expired` 只能由用户手动重试或重新确认后回到队列，服务重启不构成延期理由。
- **无人确认的自动导出（2026-09-16 定案，2026-09-24 收窄）**：按目标单独开启，开启与关闭都要求管理员重新输入密码并展示风险提示；设备令牌永远不能开关它。默认行为是**只写草稿文件**（`draft: true`），开启自动导出后才会按目标当下的可见性选择自动写文件。
- **权限**：设备令牌可发起导出与查看记录；改目标、开自动导出、改通知收件地址必须用管理员身份。手动动作由服务端记录 `TriggeredBy`、`TriggeredAtUtc`。
- 记录文件名与内容哈希；本地后续修改不得静默覆盖已导出的文件。

### 11.2 Markdown 文件

- 产出带可配置 Front Matter 的 Markdown。
- 默认文件名为 `YYYY-MM-DD-slug.md`。
- 支持 `title`、`date`、`updated`、`tags`、`categories`、`draft` 和正文占位符。
- 文件写入用户指定的服务器挂载目录；目标目录必须是 markdown 根目录下的**相对路径**，绝对路径或试图跳出的路径一律拒绝。
- MVP 不执行 Hexo、Git 或其他外部命令。
- 不得静默覆盖已存在或被外部修改的文件：默认只覆盖「本实例写过、且内容仍是它写的那样」的文件，其余情况改为写入带版本号的新文件或直接拒绝。**唯一的例外是用户在「检查远程」看到差异之后明确选择「覆盖」**——那不是静默写入，而是用户看过差异后的决定，必须如实执行（§17.3 第 7 步）；而「本实例从未写过」的同名文件在任何情况下都不动，即使带着确认也一样。
- 再次导出默认创建带版本号的新文件（`YYYY-MM-DD-slug-2.md`），用户明确确认后才能替换。

**当前边界（附录 A.17）**：以上是「产出一份 md 文件」这一层的要求。让它更贴合某个具体 Hexo 站点的约定（例如 front matter 字段集合、`source/_drafts` 与 `source/_posts` 的分流、文件名风格）属于后续的格式微调，不在当前范围内。

## 12. 邮件通知

使用通用 SMTP 配置，不为 QQ 邮箱、Gmail 等服务分别开发专用集成。

可独立启用的通知事件：

- 新草稿待确认。
- 任务最终失败。
- 自动导出成功或失败。

邮件任务与业务任务解耦。邮件失败不能回滚稿件、触发重复生成或改变导出结果。

## 14. 后台任务与可靠性

- 任务必须持久化，服务重启后可恢复。
- 启动时把上一次进程留下的 `Running` 任务一律重排（此刻本实例不可能真有任务在跑），并且**目标自身的中间状态不得成为死路**：被中断的转写会把输入复位为待转写再重跑（音频还在，重跑安全）；被中断的导出则相反——文件可能已经写出来了而记录还不知道（进程死在写入与落库之间），重排后再写一次就会多出一份带版本号的文件，因此重排后按计划跳过，把「本地不知道磁盘上发生了什么」如实留给用户（见附录 A.15、A.17）。
- 同一输入的转写、同一日期的生成以及同一版本向同一目标导出都必须幂等。
- 临时错误采用指数退避，默认最多三次。
- 达到上限后进入最终失败状态并按配置发邮件。
- 用户修复配置后可以重试单项或批量补跑失败任务。
- SMTP 失败只影响通知任务。
- 自动导出超过合理执行窗口后不得静默补做，必须重新确认或手动重试（窗口长度见 §11.1，默认 120 分钟）。

初期可使用数据库驱动的后台队列，不必引入外部消息中间件。确保多实例部署未被支持时，Compose 只运行一个任务执行实例。

## 15. 数据导出、备份与迁移

### 15.1 可阅读导出

至少包含：

- 每篇随想的 Markdown。
- 输入、主题、来源映射和元数据 JSON。
- 尚未被保留策略删除的音频文件。

**音频保留策略（2026-09-16 定案）**：转写成功且用户首次确认该日草稿后，音频进入可清理状态；`Retention.AudioDays` 默认 30，可配置为“永久”或 0（立即删除）。到期物理删除音频文件，`InputEntry` 与转写文本保留，`AudioPath` 置空并记录 `AudioDeletedAtUtc`。清理是独立的可持久化任务（`JobType = AudioCleanup`），失败不影响业务；管理页与导出说明须明示当前策略。

### 15.2 完整备份

- 包含 SQLite 数据库、媒体、Markdown、索引元数据和非秘密配置。
- **不包含设备令牌及其派生的会话状态**（2026-09-16 定案）：恢复后所有设备必须重新配对。此举与 §10.4 凭据不外流原则一致，且重配对仅需管理页生成十分钟一次性码，成本很低。
- **不包含 DataProtection 密钥环**（2026-09-16 定案，见附录 A.14）。密钥环签发管理员登录 Cookie，属**凭据等价物**：放进实例卷就等于让每份备份都带着伪造会话的能力，与上一条同理。它必须在实例根目录之外独立持久化——否则重建容器会静默登出管理员——但不得进入备份。
- 支持管理页一键备份。
- 支持每日定时输出到挂载目录。
- 默认保留最近七份。
- 必须提供在全新实例上的恢复验证流程，采用以下八步（2026-09-16 定案）：
  1. 全新空目录，仅放入 Compose 文件与新生成的 Secrets。
  2. `docker compose up -d`，确认自动迁移成功、管理员已初始化。
  3. 通过管理页恢复备份（SQLite + 媒体 + Markdown + 索引元数据 + 非秘密配置）。
  4. 校验基础健康检查全绿，且任务队列无遗留 `Running` 任务。
  5. 抽样校验：随想正文可打开、三版本位置完整、来源映射可解析（`QuoteHash` 匹配）。
  6. 抽样校验：语音输入可播放，且原始转写与修订稿均在。
  7. 校验：导出包与备份包中不含任何 Secret。
  8. 校验：原设备令牌不可用，且重新配对流程可正常完成。

### 15.3 数据库迁移

- 服务启动时自动执行向前迁移。
- 升级文档要求先备份。
- 不承诺自动降级；保留旧镜像和备份用于恢复。

## 16. 可观测性

默认日志只记录：

- 请求或任务 ID。
- 状态变化、耗时和重试次数。
- 脱敏后的错误代码与摘要。

只有用户主动开启临时调试模式时才能记录内容相关信息，并必须提示可能包含私人数据。调试模式应自动到期。

服务提供健康检查，至少覆盖数据库可写、媒体目录可写、后台任务执行器状态；外部模型与 SMTP 使用独立的“测试连接”操作，不应让外部服务故障导致基础健康检查失败。Markdown 输出是本地目录，本就不属于外部服务，因此没有对应的“测试连接”（附录 A.17）。

## 17. 测试策略

### 17.1 单元测试

重点覆盖：

- UTC 与内容时区的自然日划分。
- 当日晚到输入引起的草稿过期和补生成资格。
- 禁止任意历史日期重新生成。
- 历史检索不得使用文章日期之后的内容。
- 三版本轮换不得覆盖手工编辑。
- 主题的合并、重命名与删除不得改变历史文章的来源映射。
- “晚到”判定只依赖输入的创建时间与偏移，与生成任务是否已执行无关。
- 删除音频与删除整条记录的不同语义。
- 自动发布的状态转换和执行窗口。
- 可见性与导出文件中 `draft` 字段的一致性，以及「已写出的文件仍是自己写的」这条判定的边界。

### 17.2 集成测试

- SQLite 和文件系统的一致性。
- 录音上传幂等性和断线重试。
- 模型接口成功、超时、限流和无效响应。
- Embedding 降级及索引重建。
- SMTP 失败不影响草稿。
- 同一版本重复导出不产生第二份文件，且绝不覆盖不是自己写的文件。
- Docker 重启后任务恢复。
- 备份在全新实例恢复。

外部服务必须使用可控的测试替身。

### 17.3 端到端验收

必须完成以下真实路径：

1. Android 断网录制多条语音并输入文字。
2. 联网后自动上传、转写和识别主题。
3. 服务端按内容时区生成当天随想并关联历史来源。
4. 用户查看存疑语句、修改转写和草稿、执行允许的重新生成。
5. 邮箱收到待确认提醒。
6. 用户把稿件导出成 Markdown：先导出草稿（`draft: true`），再手动导出为公开（`draft: false`），两次落在同一份文件上。
7. 在导出目录里手改那份文件后，`check-remote` 报出差异，且用户的选择（保留两边 / 覆盖）被如实执行。
8. 创建完整备份，并在全新服务实例按 §15.2 的八步恢复验证流程恢复全部内容。

### A.1 音频保留策略

**问题**：§15.1 声明导出“尚未被保留策略删除的音频文件”，但全文没有任何地方定义该保留策略；§6.1 只有 `DeletedAtUtc`。导出范围、备份体积、隐私承诺，以及“转写成功后能否立即丢弃音频”都取决于此。

**备选与权衡**：

1. 转写成功后立即删除音频——隐私最强、体积最小，但用户事后无法复核转写是否有误。
2. 永久保留，仅在删除整条记录时清除——可回溯性最好，但备份体积与隐私风险最大。
3. 确认草稿后保留 30 天（可配置）——兼顾三者，代价是需要一套独立的清理任务与状态。

**定案理由**：选 3。本文的核心卖点是“来源可核验”；若转写成功即删音频，用户日后怀疑转写有误便无从复核，等于自断一半卖点；而永久保留又会同时恶化备份体积与隐私承诺。30 天覆盖“当天录、过几天核对”的实际节奏，且保留“永久”“立即删除”两个极值以满足不同偏好。

### A.2 自动发布执行窗口

**问题**：§14 要求“超过合理执行窗口后不得静默补发”，§17.1 要求测试该窗口，但全文未给数值。这是“不得静默公开”这一安全承诺的唯一执行依据，没有数值就无法实现也无法测试。

**备选与权衡**：

1. 60 分钟——更保守，但能容忍的故障窗口过短。
2. 120 分钟——覆盖容器重启与短暂故障，且不至于跨夜。
3. 当日有效（至 23:59）——最省心，但实质上放松了 §14 的约束。
4. 不设过期，重启后仍可自动发布——直接违背 §14，不采纳。

**定案理由**：选 2。默认导出点为次日 08:00，用户的白天在线时段足以处理两小时内的告警；窗口再长到跨夜，就等于把“不得静默补做”架空。同时明确**重启不构成延期理由**，否则反复重启即可无限延长窗口。

**2026-09-24 补充（A.17）**：这一条的对象从「自动公开到博客」变成了「自动写出文件」，数值与理由都未变。竞态里被保护的东西换了名字但没换性质：原来怕的是「没人看着就公开了」，现在怕的是「没人看着就把一份 `draft: false` 的文件写进了你的站点仓库」。

### A.3 稿件状态模型

**问题**：§6.3 状态机图把 `Failed` 与 `StaleByLateInput` 画成状态，字段列表却同时有 `Status` 与 `IsStaleBecauseOfLateInput`，二者关系未说明。这决定枚举取值、数据库约束，以及客户端“草稿”页的默认分组。

**备选与权衡**：

1. 七值 `Status` 枚举，布尔字段降级为审计用途——与状态机图一致，客户端可直接按状态分组。
2. `Status` 只保留主流程五值，失败与过期用两个标志位表达——状态更正交，但“已失败 + 已过期”这类组合需要 UI 层自行推导展示态，分组逻辑会散落到客户端。

**定案理由**：选 1。状态机图本就是状态语义；选 2 会让展示态推导逻辑进入客户端，与 §4.1“AI、调度与发布逻辑统归服务端”的分工相悖。另外 `Failed` 是**稿件态**，必须与 `ProcessingJob` 的**任务态失败**严格区分，避免两套失败语义互相污染。

### A.4 晚到输入的判定

**问题**：§7 提到“当日晚到输入”、§11.1 提到“夜间新增素材使待导出记录失效”，但未定义到达时间与内容日的关系，也未说明能否跨日到达。它直接决定补生成资格与导出队列的重入条件。

**备选与权衡**：

1. 以内容日 `23:59:59`（内容时区）为界——判定只依赖输入自身的创建时间与偏移。
2. 以当日生成时刻（默认 23:00）为界——更贴近“生成之后才算晚到”的字面表述，但生成因故障延到 23:40 执行时，“23:30 到达的输入”是否算晚到就没有唯一答案。

**定案理由**：选 1。它使“是否晚到”与“生成任务是否已经执行”完全解耦，因而确定、可离线补传、可单元测试。选 2 会把生成任务的执行时序引入判定，产生无法判定的边界情况。

### A.5 内容时区变更

**问题**：§7 规定内容时区可配置，§4.1 将其列为管理页配置项，但未说明变更是否回溯。

**备选与权衡**：

1. 不回溯，`ContentDate` 一经写入即不可变——历史数据稳定，但选错时区的实例会“前后不一致”。
2. 变更时全量重算 `ContentDate`——历史归属日会变，冲击“按日唯一”、补跑资格与已导出内容的日期归属。
3. 默认不回溯，另附一次性迁移工具。

**定案理由**：选 1。`ContentDate` 不可变是补生成规则能成立的地基：一旦可重算，“某日是否已生成”“某输入是否属于该日”都会失去稳定答案，与 §7 的不可变精神直接冲突。时区在实际中极少变更，且要纠正的是**新数据**的时区，历史数据本身并没有错；选 3 的工具属于假想需求，按 §20 不提前引入。

### A.6 来源定位格式

**问题**：§6.5 只要求“段落定位信息”，§8.4 要求存疑句子在客户端高亮。高亮、版本切换后的漂移检测，以及“来源核验”界面的实现都依赖一个确定格式。

**备选与权衡**：

1. 段落序号 + 字符区间 + 引用哈希——三层定位，可检测漂移。
2. 仅整段定位——实现最简，但存疑句子只能高亮到段落。
3. Markdown 块 ID 锚点——定位最稳，但正文会被标记污染，影响 Markdown 输出。

**定案理由**：选 1。`QuoteHash` 是这里唯一的漂移检测手段：用户手工编辑后段落文本已变，若仍按旧偏移精确高亮就会**指错地方**——在“帮助用户核验来源”的场景下，指错比不指更糟。哈希不匹配时降级为整段提示并告知版本已被编辑，是唯一诚实的处理方式。选 3 会侵入正文格式，与 §11.2 的 Markdown 输出要求冲突。

### A.7 发布权限边界

**问题**：§4.1 把“发布操作”列入客户端职责，§11.1 要求无人确认的**自动**公开需再次验证管理员身份；手动公开是否也需管理员二次验证，未说明。这决定设备令牌的权限模型与 API 鉴权策略。

**备选与权衡**：

1. 设备令牌可手动公开（客户端二次确认 + 服务端审计）；自动公开开关仅管理页可开。
2. 手动公开同样要求管理员密码——更保守，但日常在手机上发布会很繁琐。
3. 设备令牌只能上传草稿，所有公开动作都在管理页完成——剥夺了 §9.3 草稿页的发布能力。

**定案理由**：选 1。§11.1 的“再次验证管理员身份”在原文中明确限定于**无人确认的自动导出**；手动导出本身已经有人在确认，若再要求管理员密码，§9.3 的“草稿页导出”在手机上基本不可用。风险仍被看住：二次确认不可省略、导出动作留审计字段、自动导出的开关能力完全不给设备令牌。

**2026-09-24 补充（A.17）**：WordPress 移除后，「手动」与「自动」的差别只剩下一件事：**谁按下了导出**。因此这一条的结论原样成立，而且更容易说清楚——设备令牌可以手动导出一份文件，但只有管理员能打开「自动导出」这个开关，而自动导出的默认产物仍然是 `draft: true` 的草稿文件。

### A.8 检索失效与降级

**问题**：§8.3 说“更换 Embedding 模型后旧索引失效，重建完成前使用降级检索”，§16 要求健康检查不受外部依赖影响，但“语义检索当前是否可用”没有可查询的判定来源——否则每次检索都要临时探测模型。

**备选与权衡**：

1. 配置指纹 + 全库失效 + 全局降级开关——判定来源唯一，实现简单。
2. 按指纹保留多代索引并支持回退——可回滚，但存储与查询复杂度显著上升。

**定案理由**：选 1。`SemanticSearchAvailable` 必须是可查询状态，否则 §8.3 的降级检索与客户端“重建中”提示都无从实现。选 2 是为假想需求增加复杂度，与 §20 冲突。另需明确：重建状态属外部能力状态，**不**计入基础健康检查，否则 Embedding 服务不可用会连带让基础健康检查失败，违反 §16。

### A.9 主题引用稳定性

**问题**：§6.2 要求支持合并且“删除主题不得删除原始输入”，§6.5 的 `SourceReference` 关联的是输入而非主题。所以文档已隐含可解，真正待确认的只有一点：主题 ID 是否允许变化。

**备选与权衡**：

1. 主题 ID 稳定不可变，合并留 tombstone——成本是一行记录加一个 `MergedIntoId`。
2. 合并即删除被合并主题行——表更干净，但客户端缓存与历史引用会断裂，且旧 ID 可能被复用后语义串台。

**定案理由**：选 1。成本极低而收益明确；更重要的是，因 `SourceReference` 指向 `InputEntry`，历史文章的来源映射**天然不受**主题操作影响——这一条值得写成显式不变量测试固定下来，防止日后有人在合并逻辑里顺手改了引用。

### A.10 目标框架

**问题**：文档通篇未指定 .NET 版本；开发机已安装 SDK 为 10.0.302。阶段一的解决方案模板、`TargetFrameworks` 与 Docker 基础镜像选择都直接依赖它。

**备选与权衡**：

1. .NET 10——与开发机 SDK 一致，MAUI 模板与工作负载现成。
2. .NET 8 LTS——长期支持更稳，适合“多年不升级”的目标，但需另装 SDK，MAUI Android 工具链较旧。

**定案理由**：选 1。交付物是自托管的 Android APK（电脑端已于 2026-09-24 退出范围，见 A.17），不经商店审核，LTS 的“长期免升级”优势在此场景并非硬需求；与开发机一致可避免额外的工具链维护成本。另明确 Docker 基础镜像固定 tag、不使用 `latest`，以免镜像漂移导致“同一版本行为不同”。

### A.11 Android 最低版本

**问题**：同 A.10，需确定 `SupportedOSPlatformVersion`。

**备选与权衡**：

1. API 24（Android 7.0）——覆盖面更广，但旧版存储权限与后台限制差异多，兼容分支显著增加。
2. API 26（Android 8.0）——避开旧版存储权限差异，覆盖绝大多数在用设备。
3. API 29（Android 10）——测试矩阵最小，但会排除部分在用设备。

**定案理由**：选 2。运行时权限模型在 API 23 之后已统一，再取 26 可避开旧版存储权限的兼容分支；继续下探收益极小、分支成本陡增，而 29 的门槛对“个人自用”场景不必要地苛刻。

### A.12 恢复验证流程

**问题**：§15.2 要求“必须提供在全新实例上的恢复验证流程”，§19 要求“Docker Compose 环境可以从空目录部署”，但两处都没有步骤与判定标准，导致完成定义无法判定、用户文档也无从下笔。

**备选与权衡**：

1. 八步清单——覆盖迁移、任务队列残留、来源映射完整性、音频可播与 Secret 排除。
2. 精简为四项核心校验（服务能起、文章能看、音频能放、无 Secret 泄露）——更轻，但不校验任务队列残留与来源映射完整性。

**定案理由**：选 1。它的价值在于把 §15.2 与 §19 的两处要求接成一条可执行、可判定的清单，并直接充当 §17.3 端到端验收的第 8 步。选 2 会漏掉两类恢复失败模式：遗留 `Running` 任务导致的重复执行，以及来源映射无法解析导致的“文章看起来对、核验功能已坏”。

### A.13 备份排除设备令牌

**问题**：§15.2 原文写备份“包含 SQLite 数据库”，而设备令牌就存在于该库中，于是“恢复后原设备能否继续使用”没有答案。这是 A.12 清单第 8 步在编写时暴露出的真实歧义。

**备选与权衡**：

1. 备份不含设备令牌，恢复后重新配对——凭据不外流，攻击面最小。
2. 备份含设备令牌，恢复后原设备无需操作即可继续使用——灾难恢复体验最顺，但备份从此携带认证凭据。

**定案理由**：选 1。与 §10.4「普通数据导出及备份不得包含 Secrets」的原则保持一致，也让备份文件的泄露风险不因“恢复方便”而上升。重配对的成本很低——管理页生成十分钟一次性码、手机上扫一下，而恢复通常恰恰发生在手边就有设备的场景。

### A.14 DataProtection 密钥环的位置

**问题**：容器化部署时 ASP.NET Core 默认把密钥环放在运行时用户的主目录（容器内为 `/home/app/.aspnet/DataProtection-Keys`）。该路径位于容器的可写层，**重建容器即丢失**，于是每次重新部署都会让所有管理员会话失效。但把它放进实例根目录又会引出另一个问题：实例根目录就是备份集，密钥环因此会随备份外流。这个问题是在远程 Docker 环境做真实部署验收时，从启动日志的告警里发现的。

**备选与权衡**：

1. 不持久化，接受重建即登出——实现最简，备份天然干净；代价是每次重新部署都要重新登录，重建期间正在提交的表单也会失败。
2. 放进实例根目录——会话可存活，但备份从此携带可伪造管理员会话的材料，与 §10.4 和 A.13 的原则直接冲突。
3. 放在实例根目录之外的独立路径与独立卷——会话存活，备份保持干净。

**定案理由**：选 3。它同时满足两个约束：密钥环必须比容器活得久，但不得进入备份。这与 A.13 对设备令牌的推理是同一条——备份可以带走内容，不可以带走凭据。已用 `docker compose up -d --force-recreate` 在真实容器上验证：重建后同一 Cookie 仍被接受，密钥环文件位于独立卷，且 `/var/lib/dailymusings` 内不含密钥环。

**正文落点**：§15.2。

### A.15 被中断任务的恢复语义

**问题**：§14 只写了「任务必须持久化，服务重启后可恢复」，没写**中断**（进程被杀、容器被替换、断电）留下的状态该怎么办。这一条是在阶段五补测试断言时暴露的：补上「重启后被中断的任务会被重排」这条断言后，测试第一次运行就红了——任务确实被重排了，但重排后的转写被领域规则拒绝（`input.transcription.bad_state`），因为输入条目还停在 `in_progress`，而 `BeginTranscription` 只接受 `pending`/`failed`。结果是：任务最终失败，输入永远拿不到转写，用户点「重试转写」也救不回来。缺陷不在恢复逻辑，而在「恢复之后目标的状态没人管」。

**备选与权衡**：

1. 启动时重排遗留 `Running` 任务，并把目标自身的中间状态按业务语义复位（转写复位后重跑；导出按计划跳过）——恢复是自动的，且不改领域规则。
2. 启动时把遗留 `Running` 任务直接标记为最终失败，交由用户手动重试——最保守，但把「机器被重启」说成了「你的这段语音转不出来」，而且用户往往并不知道要重试什么。
3. 什么都不做，让任务永远停在 `Running`——界面上一句「转写中」挂到天荒地老，等于静默丢数据。

**定案理由**：选 1，并按任务类型分别处理。判据是**重跑是否安全**：转写重跑安全——音频还在、目标条目唯一、写入的是同一个字段，所以把被中断的输入复位为待转写再跑一次，代价为零，收益是一条本来会永久丢失的转写。导出（当时是「发布」）重跑不安全——那时它指向上传到一个远端站点，请求可能已经进了对方的网络，重复发布是 §14 明令禁止的，所以重排后的发布任务在本地记录仍是 `InProgress` 时按计划跳过，把「本地不知道远端发生了什么」如实留给用户，由「检查远程」去核对。同一条原则也解释了为什么生成被中断后可以直接重跑：`Generating → Generating` 是生命周期里允许的自环，草稿没有「发出去了就收不回」的副作用。

**2026-09-24 补充（A.17）**：对象换成 Markdown 文件后，判据没有变，结论也没有变。文件确实可能已经写出来了而记录还不知道（进程死在写入与落库之间），此时重排再写一次就会多出一份带版本号的文件——对一份承诺「再次导出默认新建文件」的产品来说，那就是凭空多出一个副本。所以被中断的导出仍然按计划跳过，由用户自己决定是重新导出还是接受磁盘上的那一份。

**正文落点**：§14。回归断言在 `tests/DailyMusings.Api.IntegrationTests/JobRecoveryTests.cs`（真停真起：一个进程在转写中途被停止，数据库里留下 `Running`，新进程启动后同一条任务记录完成，尝试次数为 2）。

### A.16 Windows 交付形态：解压即用，不做安装包【已撤回】

> **本条目已被 A.17 撤回。** 电脑端客户端整体退出了项目方向，因此「交付形态」这个问题不再存在。以下内容保留，是因为它记录了当时踩过的坑与判断依据；它**不再是任何现行约束**，正文里对应的 §18 阶段五内容已划掉。

**问题**：§18 原文写「生成 Windows 安装包」，而「安装包」在 Windows 上默认指向 MSIX/Appx。交付前实测发现这条路对**自托管的个人工具**代价过高：自签名证书没有商用时间戳，`Add-AppxPackage` 要求证书先进入**本机**（而不是当前用户）的「受信任人」与「根」存储——因为 AppXSvc 以 SYSTEM 运行、只认本机存储——也就是**用户必须先用管理员权限导入一枚自己签的证书**才能装。更糟的是这条路必须真的装一次才会暴露问题：包里的清单引用了根本不存在的图片，而只做「能构建、能签名」的检查完全看不出来。

**备选与权衡**：

1. 交付 MSIX（自签名）+ 免安装 zip——形式上最"正式"，能从开始菜单启动；代价是每台机器都要一次管理员证书导入、每次客户端改动都要重新签名并复验两种形态，且签名链、时间戳、证书有效期都是长期负担。
2. 只交付**免安装 zip**（自包含，解压即用）——解压到任意目录双击即可运行；没有证书、没有安装步骤、没有卸载残留；代价是没有开始菜单入口、没有自动更新、包体较大（自包含 .NET 与 Windows App SDK）。
3. 只交付 MSIX，不做 zip——省一份包体，但把上面所有代价留给用户，且没有退路。

**当时的定案理由**：选 2。这个产品是**给自己用的自托管工具**，安装形态的价值是「打开就能记」，而不是「像商业软件一样被管理」。MSIX 的构建路径（`Platforms/Windows/Package.appxmanifest` 与签名参数）当时**保留在仓库里但不再作为交付物**。

**撤回时的实际处置**：不是「保留构建路径」，而是**整套 Windows 实现被删除**——`net10.0-windows` 目标、`Platforms/Windows/` 下的 WinUI 外壳与 `MediaCapture` 录音、`MediaPlayer` 播放、`Package.appxmanifest`、以及 README 与 `docs/发布校验值.md` 里那条 MSIX 留档，都已随 A.17 一并移除。**正文落点**：§3.2、§18 阶段五。

### A.17 方向调整：不做电脑端，交付只做 Hexo Markdown

**问题**：项目按 §18 走完了五个阶段，包括一个已验收的 Windows 客户端、一条 WordPress 发布路径，以及一条 Hexo Markdown 导出路径。此后方向被明确收窄，而这三件事在实现上是**互相支撑**的：Windows 客户端是「双端」这个前提的产物；WordPress 是「发布」这个概念原本的落点；而 WordPress 一旦移除，「公开 / 草稿」这个可见性概念就只剩 Markdown 一个消费者——它必须落到 front matter 的 `draft` 字段上，否则产品根本发布不出去。这三者若不一起定案，实现会被迫做隐式选择。

**备选与权衡**：

1. 保留全部实现，只在文档里降级——改动最小，但仓库里会留下一个不再交付、不再复验、却仍在构建与测试中的 Windows 目标，以及一条每个版本都要陪着跑的 WordPress 路径。§20 的「不为假设中的需求提前引入」直接反对这种状态：**未被复验的代码不是资产，是负债**。
2. 只删代码，文档照旧——更糟：文档会持续声称存在一个已经不存在的交付面。
3. 代码与文档一起收窄（本次选择）——删除 Windows 目标与 WordPress 全链路，把交付面明确成「产出一份 Markdown 文件」，可见性落到 `draft` 上。

**定案理由**：选 3。三条具体要求直接决定了删到什么程度：

- **不做电脑端**：`DailyMusings.Client` 只保留 `net10.0-android`；`Platforms/Windows/` 整个目录、`MauiProgram` 里的 `#elif WINDOWS` 分支、以及配套注释与文档全部删除。`PlatformNames` 保留为运行时平台名的归一化工具（Android 是唯一会出现的取值），因为它本来就是共享逻辑而不是平台实现。
- **交付只做 Hexo**：WordPress 退出范围。删除的不只是客户端实现，还有它在别处长出来的枝节：`PublishTargetType.WordPress`、`IRemotePublisher` / `WordPressSite` / `RemoteArticle`、`WordPressRestPublisher`、每目标的站点覆盖设置（`IWordPressSiteOverrideStore`、`UpdateWordPressSiteOverrideUseCase`、`/api/publish-targets/{id}/wordpress`、`WordPressSiteDto`）、`ExternalService.WordPress` 探测、管理页的站点设置区块、`wordpress-application-password` 这个 Secret、以及验收脚本里的真实 WordPress 环节。
- **先只要求一份 md**：`§11.2` 的产出一层保持原样（模板、文件名、安全写入、按版本号新建文件），Hexo 专属的 front-matter 与目录约定微调被明确列为**后续工作**，不进当前完成定义。

**代价与必须承认的后果**：

- **可见性现在必须真的落到 `draft` 字段上**，这从「WordPress 的草稿/公开」变成了「Hexo 会不会生成这篇文章」，因此它成了功能而不是装饰：`Published` 状态对应 `draft: false`，`DraftUploaded` 对应 `draft: true`。这不是新增需求，而是把原本只对 WordPress 有意义的语义接到了唯一剩下的目标上。
- **「检查远程差异」的含义变了**：远端就是磁盘上那个文件，`RemoteChanged` 变成「文件被人在编辑器里改过」。差异的三种处置里，**「拉取」恒定不可用**（把用户自己的文件抄回草稿会让导出目录变成第二份事实来源），它保留在契约里只为给出一个说明清楚的拒绝，而不是静默失败。
- **数据库要向前迁移一次**：`0006_markdown_only` 删除 WordPress 目标及其发布记录（`publication.publish_target_id` 没有级联，所以必须先删记录），把存活的 Markdown 目标从 `1` 重新编号为 `0`，并清掉 `publish.wordpress.%` 设置键。**这会真的丢弃 WordPress 目标的发布历史**，升级前应当先备份。稿件、版本、来源映射、输入与音频一概不动。
- **产物已重录，真机复验未做**：`docs/发布校验值.md` 里 1.0.0 的旧校验值是本轮改动之前构建的，已保留为历史留档；Android APK 已于 2026-09-24 按当前源码重建并记录新校验值（0 警告 0 错误），但**尚未在新产物上重跑真机验收**。

**正文落点**：§2、§3.1、§3.2、§4、§4.1、§5、§6.7、§10.4、§11、§13、§16、§17.2、§17.3、§18、§19、§20。回归方式：全量自动化测试（见仓库 README 的「当前进度」小节）加上 `tools/acceptance/` 里按新范围改写过的端到端脚本。
