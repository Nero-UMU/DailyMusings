# 发布校验值

本文记录构建产物的 SHA-256，供下载后核对（§18 阶段五要求「生成 Android APK 和发布校验值」）。

**交付形态（2026-09-29 起）**：对外是**一份 compose 文件 + 一个 APK**（附录 A.26）。APK 与多架构服务端镜像都由 CI 在打 tag 时构建：

- 镜像：`ghcr.io/nero-umu/dailymusings`（`linux/amd64`、`linux/arm64`），同时给出语义化版本与 `latest`。
- APK：附在 [Releases](https://github.com/Nero-UMU/DailyMusings/releases) 里，**同页给出该次构建的 SHA-256**（`*.apk.sha256`），因此校验值以 Release 页为准，不再手工维护在下表——下表保留的是本轮之前手工构建并验证过的产物。

流程定义见 [`.github/workflows/release.yml`](../.github/workflows/release.yml)：`image` 作业构建推送镜像，`apk` 作业构建签名 APK，`compose-smoke` 作业**用仓库根那份 `compose.yaml` 真的起一次实例**（零配置一次、绑定挂载一次），`release` 作业把 APK 与校验值附到 Release。

**客户端形态（2026-09-24 起）**：只有 **Android APK**。电脑端客户端整体退出了项目方向（[`docs/开发指导.md`](开发指导.md) 附录 A.17），因此不再有 Windows 免安装包，也不再有任何 MSIX 相关产物与构建路径。

## APK 签名（升级安装的前提）

Android 规定「**覆盖安装必须与已安装版本同一签名**」。做不到这一点时，手机上会看到「应用未安装 / 与现有应用签名不一致」这类提示，而**不是**一个可以忽略的警告。

**1.0.6 之前的所有 APK 都是调试签名，而且每版签名都不同**——`release.yml` 当时没给密钥，全新 runner 上由 .NET Android 自动生成了一把调试密钥（证书主题 `CN=Android Debug`）。实测三个版本的证书指纹：

| 版本 | 签名证书 SHA-256 |
| --- | --- |
| v1.0.3 | `2c8c874490a5a3c9258d0c1012ea149000c484b6d680a7e28a2ff01b8add01fc` |
| v1.0.4 | `3d4370deee544997a21a7453b7e9caacf18db7a483ab03c4b7761cde3c333248` |
| v1.0.5 | `ecd15c9a36b7d5b84c55abd764792faaae5f11ded21bafd34f817c8f94adfda2` |

因此：**如果你装过 1.0.6 之前的版本，需要先卸载一次**，再安装 1.0.6 或更新版本（旧版的私钥随 runner 一起消失，没有任何办法用它再签一份新包）。此后每一版都能直接覆盖安装。

**从 1.0.6 起用一把固定的发布密钥**（定案见 [`docs/开发指导.md`](开发指导.md) 附录 A.30）：私钥只存在于维护者的备份与仓库的 4 条 GitHub Secret 里，仓库变量 `ANDROID_SIGNING_CERT_SHA256` 记录它的证书指纹；CI 缺密钥会直接失败，并在打包后读回证书指纹与变量比对，不一致同样失败（签名「没报错」不等于用的是那把密钥）。

> **发布签名证书 SHA-256**：`36787a438115a9b19842c2fa54f809389dfa501db965643acb9b8dfb1c2ad6b9`（主题 `CN=DailyMusings, O=DailyMusings, C=CN`）。它同时写在仓库 Variable `ANDROID_SIGNING_CERT_SHA256` 里，CI 每次发布都会读回产物证书与之比对，不一致就让发布失败。

自己核对下载到的 APK 是否由这把密钥签名：

```bash
# Android SDK 里有 apksigner；也可以只比对 Release 页给出的 SHA-256
apksigner verify --print-certs DailyMusings-client-<版本>-android.apk
```

### 1.0.5（2026-09-29，CI 构建）

这一版修掉一个**让「自动发布」变成摆设**的缺陷，并把篇幅设置改成区间加公差：
